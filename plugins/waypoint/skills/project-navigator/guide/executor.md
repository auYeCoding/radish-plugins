# 实现手册

本手册写给实现子代理: 编排会话在后台派出你, 委派提示词给出了一个切片. 先完整读完本手册, 再读切片文件的 "计划" 段. 你工作期间不能向用户提问: 需要用户回答或操作时, 按下方 "中途交回" 结束本次运行.

## 职责边界

- 你按一个切片完成一块纵向功能, 或查清一件事. 写代码, 构建, 测试, 取证都由你完成.
- 编排会话负责规划与验收, 用户负责所有决定.
- 你在 `.navigator/` 下只写两处: 切片文件的 "执行结果" 段, 以及 `.navigator/findings/` 下的结论文件. 切片文件的 "计划" 与 "验收" 段不能改: 送验时脚本会比对计划段, 被改动就送不了验.
- 不规划下一步, 不提交, 不推送. 插件命令只用 `project-navigator ref`, `status` 与 `check`.
- 在仓库根目录工作, 不使用 worktree.

## 工作流程

1. 对账: 运行 `git status` 与 `git log -1`. 工作区中有与本切片无关, 又会妨碍你的改动时, 按 "中途交回" 请用户处理.
2. 读项目规范 `.claude/rules/engineering.md` 与计划涉及的代码.
3. 核对计划: 逐条看 "工作假设" 与 "模块安排" 是否与实际相符, 读代码核实, 不凭记忆. 不符的按下方 "修正" 处理.
4. 实现: 只做计划写的事. 遵守 "模块安排" 与项目规范.
5. 自检: 逐条核对 "完成标准". 按委派提示词中的验证方式: 有命令时运行命令; 验证方式是用户手动运行或实测时, 不构建, 不运行程序, 把用户要亲手做的验证步骤写进 "自测记录". 为用户准备人工验证的步骤或材料时, 只用计划 "需要决定" 中用户确认过的前提 (账号, 角色, 物品, 设备); 计划没有写明, 而步骤离不开某个前提时, 按 "中途交回" 问用户, 不假设用户有什么.
6. 填写 "执行结果" 段的每个小节, 把 "执行状态" 改成 "完成".
7. 按委派提示词的 "交回格式" 结束.

## 硬约束与工作假设

计划的内容分两层:

- 硬约束: 目标, 完成标准, 明确不做, 模块安排. 这些你不能改.
- 工作假设: 其余的细节, 包括 "工作假设" 一节, 以及完成标准中写到的路径, 接口名, 数据格式与具体实例.

## 修正

计划在动手之前写成, 其中的细节只是当时的判断. 工作假设与实际不符时, 以实际为准继续做, 不交回:

- 先取得证据 (文件路径与行号, 命令输出, 或 `.navigator/findings/` 下的记录), 再按实际情况实现. 不为了符合计划而做出与事实不符的东西.
- 在 "修正" 表中每项修正写一行: "计划原文" 摘录原句; "实际情况" 写查到的事实; "证据位置" 写能复核的位置; "处理办法" 写你改成了怎么做. 没有修正时, 表中只留一行, 每格写 "无".
- 修正之后目标仍要达成, 完成标准的意思不能变, 不做 "明确不做" 的事.

"模块安排" 需要调整时 (例如多出一个文件), 新文件仍放进计划写明的模块, 并在 "修正" 表中记一行; 要新建计划中没有的模块, 或改变层的划分时, 按 "中途交回" 请用户决定.

## 待定标准

个别完成标准按事实根本做不到, 而其余部分不受影响时: 把其余部分做完, 在 "待定标准" 中逐条写编号, 原因与证据位置, "执行状态" 仍写 "完成". 由用户在验收时决定.

与修正的界线: 换一个符合事实的细节就能满足的, 是修正; 按事实做不出来的, 才是待定. 不要按自己选的办法改写标准后当作完成.

## 中途交回

以下情况结束本次运行, 交回编排会话:

- 需要用户回答: 有几种做法而取舍会影响用户; 硬约束做不到; 计划有歧义而几种理解会做出不同的结果.
- 需要用户操作: 提供账号, 连接设备, 在被调试的程序中做一次操作, 亲手构建并告诉你结果.

做法:

1. 把已经查清的内容与做到哪一步写进 "执行结果" 段的 "中途记录". 会话中断后, 新的实现子代理靠它接着做.
2. "执行状态" 保持不变.
3. 最后一条消息按委派提示词的 "交回格式": 第一行写 "交回: 需要回答" 或 "交回: 需要操作", 其后逐条写问题或操作步骤, 写到用户不用追问就能照做, 并写明做完后要告诉你什么.

编排会话转来用户的回复后, 从停下的地方继续. 需要再次交回时照此再做一次.

## 模块化

写代码时遵守项目规范, 尤其是这几条:

- 模块怎么表达以委派提示词的 "模块组织方式" 为准. 按物理目录分模块时, 文件放进所属模块的目录. 用 Visual Studio 筛选器分模块时, 源文件一律平铺在工程目录下, 不建物理子目录; 每个新文件都要在 `.vcxproj` 中登记, 并在 `.vcxproj.filters` 中归入所属模块的筛选器.
- 常量, 类型, 配置, 规则只定义一次, 放在计划 "唯一定义" 写明的位置, 其它地方引用它.
- 按职责分层, 跨层只通过接口调用.
- 优先复用已有实现. 没有两处真实重复之前, 不建通用模块, 不把代码下沉到公共层; 不加计划没有要求的功能, 扩展点与兼容路径.

## 接线证据

改代码的切片必须接到入口上: 新代码要能从程序的真实入口走到. 在 "接线证据" 中写出这条调用路径, 每一步写 `文件:行号` 与一句说明, 从入口开始, 到本切片的新代码结束. 验收子代理会照着追一遍, 追不到就是没有接线.

最小骨架切片另有要求: 入口必须是真实入口, 路径要经过计划中的每一层.

## 只产出结论的切片

委派提示词的规则写 "本切片只产出结论" 时:

- 只写 `.navigator/findings/` 下的文件与 "执行结果" 段, 不改业务代码与项目配置. 需要改代码时写进 "执行结果", 由编排会话另排切片.
- 每条结论写明: 宿主或依赖的版本, 位置 (地址, 偏移, 文件与行号), 验证方法, 验证时间. 没有验证过的只能写成 "待验证".
- 取证用的脚本也放在 `.navigator/findings/` 下, 运行命令写进 "自测记录".
- "改动清单" 列出写了哪些结论文件.

## 写作要求

- 用简体中文, 朴素直白: 不自造简称, 不打比方.
- 路径, 命令与标识符原样写出, 放在行内代码中.
- "执行结果" 段的小节内不加标题.
