# 骨架, 切片与工单往返

## 阶段 4: 骨架

- 骨架是第一个里程的第一个切片: 主线从头到尾跑通的最小版本. 骨架工单同时按选型结论建立格式化, 检查与测试配置.
- 运行 `milestone <第一个里程> active` 与 `slice <第一个切片> active`, 然后按下方 "工单往返" 发布工单.
- 已有项目: 阶段 4 改为接线, 把盘点发现的断点接通. 主线已经能跑通时, 经用户认可, 写明原因后运行 `skip 4 --from <草稿>`. 项目已有检查命令时, 新建第一张实现工单之前用 `codecheck set` 登记.
- 骨架切片完成后运行 `slice <编号> done` 与 `stage 5`.

## 阶段 5: 切片

1. 取推进路线中下一个未开始的切片, 运行 `slice <编号> active`.
2. 按下方 "工单粒度" 决定这个切片发几张工单; 默认一个切片一张.
3. 工单严格串行: 一张工单结束 (已通过, 不通过或已作废) 之后才能新建下一张.
4. 切片的工单全部通过后, 运行 `slice <编号> done`.
5. 里程的切片全部完成后, 按 `ref change-milestone` 做里程复查.

## 工单粒度

在不超过以下四条上限的前提下, 工单越大越好: 每张工单都要经过一次审阅与一次验收, 拆得越细, 用户要做的确认越多.

1. 执行一次能做完: 执行子代理在一个上下文中能完成, 不需要中途压缩上下文.
2. 验收能看清: 验收子代理能逐条核对全部改动. 改动过大时验收质量先下降.
3. 做完能运行: 做完之后全链路可以运行.
4. 失败代价可接受: 风险高或不确定的部分 (例如自己维护的第三方补丁) 单独成工单, 被拒时只重做这一部分.

在工单 "审阅要点" 的 "粒度依据" 中用一句话写出判断, 例如 "整个切片一张工单: 改动集中在适配层, 预计 8 个文件". 验收不通过时先判断原因: 超出上述能力时拆小 (需要时更新推进路线), 规格不清或实现有误时发修复工单.

## 工单往返

| 工单状态  | 含义                   | 你的动作                                                                                    |
| --------- | ---------------------- | ------------------------------------------------------------------------------------------- |
| drafting  | 起草中                 | 写工单文件, 做发布前核对, 回复 "工单审阅"; 用户选 A 后发布并派出执行子代理, 回复 "工单执行" |
| issued    | 已发布, 执行子代理工作 | 等子代理结束; 读回执后进入受阻处理或验收                                                    |
| blocked   | 受阻                   | 回复 "受阻处理"; 工单没有改动时直接继续, 改动后回复 "工单审阅"                              |
| reviewing | 验收中                 | 派验收子代理, 写验收记录, 回复 "验收报告"                                                   |

用户的决定只有两处: "工单审阅" 中发布工单, "验收报告" 中通过并提交 (或补正). 其余步骤由编排会话按下一动作直接进行.

### 写工单

1. 运行 `order new --kind <类型> --slug <短名> [--slice <切片编号>]`. 类型: implementation 实现, selection 选型, runcheck 运行检查, analysis 分析, fix 修复. 不带 `--slice` 时工单挂在当前切片; 切片编号是 `.navigator/plan/roadmap.md` 中的四位数字, 不是进展行中的序号.
2. 运行 `template order` 取得骨架, 按下表逐项填写后用 Write 写入.
3. 发布前核对: 运行 `precheck-brief`, 把输出原样作为提示词派 `waypoint:navigator-checker`. 它逐条核对工单中写下的事实. 按结果改工单: "不成立" 的改正; "无法核对" 的自己查证, 或改写成能核对的说法; 遗漏的决定写进 "需要决定". 改好后运行 `order precheck`. 每张工单核对一次, 按结果修改之后不用再核对.
4. 运行 `reply approve`, 回复 "工单审阅". 骨架已从工单文件的 "审阅要点" 预填, 核对后原样保留. 没有做发布前核对时 `reply approve` 拒绝. 实现与修复工单要求项目已登记代码检查命令, 且验收判据含有代码检查判据; 没有登记时 `order new` 就会拒绝, 判据不全时 `reply approve` 拒绝, 按输出补救后再取骨架.
5. "工单审阅" 中用户选 A: 运行 `order set issued`, 再运行 `exec-brief`, 把输出原样作为提示词, 用 Agent 工具在后台 (`run_in_background`) 派 `waypoint:navigator-executor`, 然后运行 `reply running`, 回复 "工单执行". 发布只接受用户认可过的内容: 认可之后改过工单文件, `order set issued` 会拒绝.
6. "工单审阅" 中用户选 B: 按要求修改工单文件, 再次回复 "工单审阅".

| 工单中的项 | 写法                                                                                                                                                                                         |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 审阅要点   | 写给用户看, 每项一句: "任务目标" 写使用者可见的行为变化; "需要决定" 写需要用户拍板的事, 没有时写 "无"; "明确不做" 写最容易误解的范围边界; "粒度依据" 见上方 "工单粒度"                       |
| 背景原因   | 为什么现在做, 引用简报或决策编号                                                                                                                                                             |
| 完成标志   | 使用者能观察到的结果                                                                                                                                                                         |
| 基准提交   | 骨架已预填当前提交的完整哈希, 原样保留; 写好工单后仓库又有新提交时, 改为新的当前提交 (`git rev-parse HEAD`), 审阅与发布都会核对                                                              |
| 回执路径   | 同一文件夹中的 `receipt.md`                                                                                                                                                                  |
| 执行守则   | 本工单特有的约束, 例如 "不改 `src/api/` 的公共接口"; 手册与项目规范中已有的规则不重复. 要留存抓包原文, 复现脚本等证据时, 写明放在本工单文件夹的 `artifacts/` 下                              |
| 前提假设   | 执行子代理动手前要核对的事实, 每条都能验证                                                                                                                                                   |
| 工作范围   | 要做的事与不做的事                                                                                                                                                                           |
| 验收判据   | 编号列出, 每条只验证一件事, 写出验证方式: 命令, 操作步骤或文件位置; 要用 MCP 工具核对的写 "取证工具: <工具名>, 按回执取证记录核对". 实现与修复工单的第一条是骨架预填的代码检查判据, 原样保留 |
| 相关材料   | 简报, 决策, 主线流程中相关条目的路径                                                                                                                                                         |

执行子代理工作期间不能向用户提问, 所以工单要写到不用追问就能动手: 前提假设可以核对, 判据可以验证, 需要用户决定的事在审阅时就问清.

工单中的具体事实只写查证过的: 文件路径, 接口名, 数据中的编号或实例, 引用的记录中的结论, 外部资源的发布形式与许可. 凭记忆写下的事实不成立时, 执行子代理要做到一半才发现. 判据尽量写要满足的特征 (例如 "任选一条带附件的记录"), 只在实例本身是要求时才点名实例. 发布前核对会逐条核对这些事实, 但核对子代理只报告, 改工单仍由你完成.

只产出记录的工单: runcheck 与 analysis 的执行子代理只能写回执与本工单的 `artifacts/`, 守卫拒绝改动业务文件; 不需要代码检查命令, 任何阶段都能发布.

- runcheck: 按已有命令构建, 启动, 测试, 原样记录结果, 用于盘点.
- analysis: 逆向, 调研等需要动手查证的任务, 产出文档与证据脚本, 都放在 `artifacts/` 下. 判据写明要回答的问题与每条结论的证据要求, 例如 "结论附证据脚本路径, 脚本能在仓库根目录运行".
- 任务需要改动项目文件 (包括以后要复用的脚本) 时, 不用这两类, 发实现工单.

工单涉及 `.claude/` 下的文件时 (例如接线 Claude Code hook), 执行子代理可以改 `.claude/settings.json` 的 `hooks` 字段与 `.claude/` 下项目自己的文件; 本技能的放行规则与 `.claude/rules/engineering.md` 不由工单修改.

### 执行期间

- "工单执行" 中 "执行方式" 写 "后台执行子代理"; 回复之后本轮结束, 子代理结束时编排会话会收到通知. 这条回复不需要用户选择, 不带选项块.
- 执行期间用户要求停止 (例如回复 "停止执行"): 停止子代理, 运行 `order set drafting` 撤回工单, 按要求修改后回复 "工单审阅".
- 收到子代理结束的通知后运行 `status`. 回执未写入时用 SendMessage 请子代理按回执骨架补写.
- 子代理交回的第一行是 "执行状态: 等待操作" 时, 它没有写回执, 在等用户亲手做一件事: 回复 "等待操作" (`reply paused`), "等待原因" 写一句为什么要用户操作, "操作步骤" 照抄子代理写的操作. 这条回复不带选项块. 用户回复之后, 用 SendMessage 把用户的话原样转给子代理, 再回复 "工单执行". 工单状态不变, 不运行 `order set`. 找不到原子代理时运行 `exec-brief` 重新派出, 并在提示词之后附一句 "先读 artifacts/ 下已有的文档, 接着做".
- 子代理在最终回复中交回了 `artifacts/` 下某个文档的路径与全文 (运行环境拒绝它写这个文件) 时, 按该路径原样写入, 不改内容, 再继续.

### 收回执

- 回执是否写入, 执行状态是什么, 以 `status` 输出的 "工单状态" 一行为准.
- 执行状态为受阻: 读回执, 运行 `order set blocked`, 回复 "受阻处理", 按受阻类型选择选项组:

| 受阻类型                                 | 选项组  |
| ---------------------------------------- | ------- |
| 规格问题: 对账不符, 前提不符, 歧义, 矛盾 | 第 1 组 |
| 范围过大                                 | 第 2 组 |
| 需要用户操作                             | 第 3 组 |
| 需要用户决定, 或执行子代理提出问题       | 第 4 组 |

- 用户完成所需操作, 或回答了问题而工单内容不用改: 运行 `order set issued` (内容没有改动时不需要重新审阅), 用 SendMessage 让原执行子代理继续, 说明用户做了什么或回答了什么; 找不到原子代理时运行 `exec-brief` 重新派出. 然后回复 "工单执行".
- 需要修改工单: 改好工单文件后回复 "工单审阅"; 用户选 A 后发布并重新派出执行子代理. 旧回执在发布时自动改名归档.
- 用户选 "调整范围, 进入变更" 或 "转为变更, 重新评估" 时, 按 `ref change-milestone` 走需求变更.
- 执行状态为完成: 进入验收. 回执 "偏差记录" 的 "待定判据" 不是 "无" 时照常验收, 这几条判据由用户在 "验收报告" 中决定.

### 验收

1. 运行 `order set reviewing`.
2. 运行 `review-brief`, 把输出原样作为提示词派 `waypoint:navigator-reviewer`. 回执 "测试记录" 中列为 "外部影响" 的命令, 验收子代理不运行, 按回执中的输出判断. 子代理在后台运行, 本轮要先结束时回复 "工单验收": "验收方式" 写 "后台验收子代理", "核对重点" 只列执行子代理提请核对的事项, 没有时写 "无"; 不写其它说明.
3. 运行 `template review`, 用子代理交回的结果写 `review.md`. "判据核对" 表的结论照抄子代理的结论, 只能是 通过, 不通过, 未验证 之一. "用户结论" 保留骨架预填的 "待用户确认", 用户选择之后再改写. "人工验收" 写出用户可以亲手验证的步骤, 命令只取自回执; 没有时写 "无".
4. 回复 "验收报告", 按判据结论选择选项组 (`reply review --option <组号>` 会核对). 建议只写在 "处理建议" 一节: "建议选项" 写选项字母, "主要依据" 写一句话; 选项块之前不另加说明:
   - 全部通过: 第 1 组. 用户选 A 或 B: 在 `review.md` 写 "用户结论", 运行 `order set accepted`, 按输出调用 `waypoint:commit-message` 提交 (B 同时推送). 用户选 C: 把用户描述的现象写进 `review.md`, 运行 `order set rejected`, 按输出用第 2 组再回复 "验收报告".
   - 有判据不通过: 运行 `order set rejected`, 按输出使用第 2 组.
   - 没有不通过, 但有未验证的判据: 第 3 组. 其中有回执列为待定的判据时 (证据以 "待定:" 开头), "处理建议" 的 "主要依据" 写明每条待定判据的实际情况与可选的处理办法: 用户选 A 表示按现状接受, 选 B 表示发补正工单. 用户选 A (接受现状): 在 `review.md` 写 "用户结论", 运行 `order set accepted --accept-unverified`, 按输出提交; 未验证的判据用 `risk add` 各登记一条风险. 用户选 B: 运行 `order set rejected`, 按输出新建补正工单.
   - 选型工单: 第 4 组, 见 `ref selection`.
5. 第 2 组用户选 A: 按 `order set rejected` 输出的命令新建补正工单, 判据写明要补正的问题. 实现与修复工单补正时先判断原因: 工单太大就拆小, 否则发修复工单 (`--kind fix`); 运行检查与分析工单补正时重发同类工单.

### 提交

1. 提交消息由 `waypoint:commit-message` 生成并展示, 不另写. 参数照抄 `order set accepted` 输出中的写法.
2. 纳入范围之外还有改动时 (例如编辑器的工程文件), 用文字列出并询问, 按用户的回答处理, 不自行排除.
3. 切片的工单全部通过时运行 `slice <编号> done`.

## 技能产物的提交

推进阶段, 初始化与项目收尾的命令输出中有 "调用 waypoint:commit-message 提交" 一步时, 照抄输出中的参数提交. 这一步只提交 `.navigator/` 与插件管理的项目配置, 其它改动由 commit-message 列出并询问.
