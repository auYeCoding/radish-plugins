# 骨架, 切片与工单往返

## 阶段 4: 骨架

- 骨架是第一个里程的第一个切片: 主线从头到尾跑通的最小版本. 骨架工单同时按选型结论建立格式化, 检查与测试配置.
- 运行 `milestone <第一个里程> active` 与 `slice <第一个切片> active`, 然后按下方 "工单往返" 发布工单.
- 已有项目: 阶段 4 改为接线, 把盘点发现的断点接通. 主线已经能跑通时, 经用户认可, 写明原因后运行 `skip 4 --from <草稿>`. 项目已有检查命令时, 发布第一张实现工单之前用 `codecheck set` 登记.
- 骨架切片完成后运行 `slice <编号> done` 与 `stage 5`.

## 阶段 5: 切片

1. 取推进路线中下一个未开始的切片, 运行 `slice <编号> active`.
2. 把切片拆成工单: 每张工单是一个使用者可见的行为变化, 判据不超过 5 条, 做完之后全链路可以运行.
3. 工单严格串行: 一张工单结束 (已提交, 不通过或已作废) 之后才能新建下一张.
4. 切片的工单全部提交后, 运行 `slice <编号> done`.
5. 里程的切片全部完成后, 按 [change-milestone.md](change-milestone.md) 做里程复查.
6. 同一切片连续 2 次验收不通过时, `order set rejected` 的输出会要求重新拆分. 回复 "验收报告" 第 3 组选项; 用户选 A 后, 把切片拆小写进推进路线草稿, 运行 `roadmap --from <草稿>`.

## 工单往返

| 工单状态   | 含义   | 你的动作                                                         |
| ---------- | ------ | ---------------------------------------------------------------- |
| drafting   | 起草中 | 写工单文件, 运行 `order set issued`, 回复 "工单发布"             |
| issued     | 已发布 | 等回执; 读回执后进入受阻处理, 测试授权或验收                     |
| blocked    | 受阻   | 回复 "受阻处理", 修改工单后运行 `order set issued`               |
| reviewing  | 验收中 | 派验收子代理, 写验收记录, 回复 "验收报告"                        |
| accepted   | 已通过 | 回复 "确认提交"                                                  |
| committing | 提交中 | 调用 `waypoint:commit-message`, 完成后运行 `order set committed` |

### 写工单

1. 运行 `order new --kind <类型> --slug <短名> [--slice <切片编号>]`. 类型: implementation 实现, selection 选型, runcheck 运行检查, fix 修复. 输出给出工单文件的路径.
2. 运行 `template order` 取得骨架, 按下表逐项填写后用 Write 写入.
3. 运行 `order set issued`, 再运行 `reply order` (骨架已带启动提示词), 回复 "工单发布". 实现与修复工单发布时, 脚本核对项目已登记代码检查命令, 且验收判据含有代码检查判据; 不满足时按输出补救.
4. 用户选 B: 按要求修改工单文件, 再次回复 "工单发布".

| 工单中的项 | 写法                                                                                                                                     |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 任务目标   | 一句话, 写使用者可见的行为变化                                                                                                           |
| 背景原因   | 为什么现在做, 引用简报或决策编号                                                                                                         |
| 完成标志   | 使用者能观察到的结果                                                                                                                     |
| 计划要求   | 默认 "必须先计划"; 改动只在一处且没有逻辑分支时写 "免除计划", 并写明原因                                                                 |
| 基准提交   | 当前提交的完整哈希, 用 `git rev-parse HEAD` 查询                                                                                         |
| 编排会话   | 本会话名称, 即 ListAgents 输出的第一行, 供消息汇报使用                                                                                   |
| 回执路径   | 同一文件夹中的 `receipt.md`                                                                                                              |
| 执行守则   | 本工单特有的约束, 例如 "不改 `src/api/` 的公共接口"; 手册与项目规范中已有的规则不重复                                                    |
| 前提假设   | 执行会话动手前要核对的事实, 每条都能验证                                                                                                 |
| 工作范围   | 要做的事与不做的事                                                                                                                       |
| 验收判据   | 编号列出, 不超过 5 条, 每条写出验证方式: 命令, 操作步骤或文件位置. 实现与修复工单的第一条是骨架预填的代码检查判据, 原样保留, 不计入 5 条 |
| 相关材料   | 简报, 决策, 主线流程中相关条目的路径                                                                                                     |
| 执行流程   | 写 "按执行手册 `.navigator/guide/executor.md` 的执行流程", 有特殊顺序时补充                                                              |

### 收回执

- 文档汇报: 用户告知执行完成后, 读工单文件夹中的 `receipt.md`.
- 消息汇报: 收到执行会话的消息后, 运行 `template receipt` (选型工单加 `--option 2`), 按骨架把消息内容写入 `receipt.md`, 不改动原意.
- "执行状态" 为受阻: 运行 `order set blocked`, 回复 "受阻处理", 按受阻类型选择选项组:

| 受阻类型                                 | 选项组  |
| ---------------------------------------- | ------- |
| 规格问题: 对账不符, 前提不符, 歧义, 矛盾 | 第 1 组 |
| 范围过大                                 | 第 2 组 |
| 需要用户操作                             | 第 3 组 |
| 执行会话提出问题                         | 第 4 组 |

- 用户选择后修改工单文件, 运行 `order set issued` (旧回执自动改名归档), 请用户回到执行会话继续. 执行会话要重新开工对齐.
- 用户选 "调整范围, 进入变更" 或 "转为变更, 重新评估" 时, 按 [change-milestone.md](change-milestone.md) 走需求变更.
- "执行状态" 为完成: 进入测试授权与验收.

### 测试授权

- 回执 "测试记录" (选型回执为 "选型结论" 中的检查命令) 中没有外部影响的测试命令 (例如单元测试), 写草稿 `{"commands": [...]}`, 运行 `order tests --from <草稿>` 直接登记.
- 需要真实账号, 会产生费用或外部副作用的测试, 先回复 "测试授权":
  - 用户选 A: 把命令加进草稿, 再运行 `order tests --from <草稿>` 登记. 已登记的命令编排会话与验收子代理都可以运行.
  - 用户选 B: 把命令原样交给用户运行, 用户告知结果后写进验收记录.

### 验收

1. 运行 `order set reviewing`.
2. 运行 `review-brief`, 把输出原样作为提示词派 `waypoint:navigator-reviewer`. 不增删任何文字, 守卫会逐字核对.
3. 运行 `template review`, 用子代理交回的结果写 `review.md`. "判据核对" 表的结论照抄子代理的结论, 只能是 通过, 不通过, 未验证 之一. "人工验收" 写出用户亲手验证的步骤:
   - 命令与操作只取自回执, 不自己编写安装, 建环境或改项目配置的命令.
   - 回执中没有可供用户亲手验证的内容时写 "无".
   - 不建议用户凭公开资料, 文档或经验认可未验证的判据.
4. 回复 "验收报告":
   - 判据核对全部为通过: 使用第 1 组选项, 请用户按人工验收步骤亲手验证. 用户选 A 时, 在 `review.md` 写 "用户结论", 运行 `order set accepted`, 回复 "确认提交". 用户选 B 时, 把用户描述的现象写进 `review.md`, 运行 `order set rejected`, 按输出再回复 "验收报告".
   - 有判据不通过或未验证: 运行 `order set rejected`, 按输出使用第 2 组或第 3 组选项.
   - 脚本会核对: 判据核对不全是通过时, `reply review --option 1` 与 `order set accepted` 都会被拒绝.
5. 第 2 组用户选 A: 新建修复工单 (`--kind fix`, 同一切片), 判据写明要修复的问题. 选型工单改为新建选型工单 (`--kind selection`), 见 [selection.md](selection.md).

### 提交

1. 回复 "确认提交": "业务改动" 取自回执 "改动清单"; "记录改动" 写 `.navigator/` 下的变化; "当前分支" 用 `git branch --show-current` 查询.
2. 用户选择后, 在 `review.md` 的 "提交方式" 写下选择, 运行 `order set committing`.
3. 调用技能 `waypoint:commit-message`, 提交消息由该技能生成并展示, 不另写:
   - 用户选 A: 参数写 "提交, 纳入范围: 回执改动清单中的文件, .navigator/ 下的改动, 以及插件命令改动的 .claude/settings.json 与 .claude/rules/engineering.md".
   - 用户选 B: 参数写 "提交并推送", 纳入范围同上.
   - 用户选 C: 不带参数, 由该技能自己的流程决定.
4. 纳入范围之外还有改动时, 该技能会列出并询问, 按用户的回答处理.
5. 提交完成后运行 `order set committed`. 切片的工单全部完成时运行 `slice <编号> done`.
