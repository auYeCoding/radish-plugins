# 阶段 3: 选型

本阶段先做规范对照, 再回答调研报告中的 "选型问题". 编排会话可以凭调研结果给出建议, 但关键依赖 (语言, 框架, 核心库, 以及难以替换的外部服务) 要用选型工单核实: 执行子代理按源码证据回答 "能不能实现每条需求", 由用户决定是否采用. 次要的库不发选型工单, 由执行子代理在实现工单中按选型守则选定, 写进回执的 "实现决定".

| 步骤标识  | 做什么   | 回复                         |
| --------- | -------- | ---------------------------- |
| standards | 规范对照 | 规范对照                     |
| selection | 选型工单 | 工单审阅, 工单执行, 验收报告 |

## 规范对照 (standards)

1. 运行 `ref standards` 取得插件默认包全文. 派 `waypoint:navigator-reader` 对比三处规范, 默认包全文放进委派提示词; 子代理没回来就要结束本轮时, 回复 "等待结果". 要求交回一致, 只有一方有, 互相矛盾三类条目, 每条附文件路径与原文摘录:
   - 插件默认包: 委派提示词中的全文
   - 项目已有规范: `CLAUDE.md`, `AGENTS.md`, `.claude/rules/`, 格式化与检查配置
   - 本机全局规范: `~/.claude/CLAUDE.md`, `~/.claude/rules/`
2. 回复 "规范对照", 按顺序使用三组选项:
   - 有矛盾条目时用第 1 组. "本轮条目" 每轮最多 3 条, 每条写出双方原文与推荐以哪边为准. 用户逐条回答, 或选 B 全部以插件默认包为准.
   - 矛盾处理完后, 对只有一方有的条目用第 2 组, 问是否纳入.
   - 最后用第 3 组问代码注释的语言, 默认中文.
3. 写草稿 `.navigator/drafts/standards.json`: 注释语言写入 `commentLanguage`, 用户选定的项目约定写入 `conventions`, 每条一句. 运行 `standards --from .navigator/drafts/standards.json`, 脚本写入 `.claude/rules/engineering.md`.
4. 用 `decision add` 登记 "项目规范", 并在 `.navigator/plan/decisions.md` 追加对应条目.
5. 运行 `step selection`.

## 选型工单 (selection)

1. 列出选型问题: 调研报告的 "选型问题", 以及主线流程 "外部依赖" 中标注 "待选型" 的条目. 分成两类: 关键依赖发选型工单; 次要的库写进对应实现工单的 "执行守则", 由执行子代理选定. 回答选型问题之前要先动手查证的 (例如逆向目标程序的数据格式), 先发分析工单 (`--kind analysis`), 见 `ref order-loop` 的 "只产出记录的工单".
2. 每个关键选型问题一张工单: `order new --kind selection --slug <短名>`. 可以在 "背景原因" 中写出你的建议与依据, 由执行子代理核实. 验收判据写:
   - 需求清单: 来自简报与主线流程的具体需求, 有几条写几条, 每条是可以回答 "能" 或 "不能" 的一件事. 判据写明: 回执 "需求核对" 表逐条回答, 结论为能的附源码证据或测试.
   - 按项目规范中的技术选型守则选择候选.
   - 选定语言或技术栈的工单, 另加一条: 选定格式化与代码检查工具, 规则中打开函数长度与复杂度检查, 检查范围排除 `.navigator/` 与 `.claude/`, 给出能在仓库根目录直接运行的检查命令.
   - 只要求回答需求能否实现, 不要求回执中其它说法附证据.
3. 工单往返见 `ref order-loop`. 选型回执使用第 2 种结构 (`template receipt --option 2`).
4. 验收一次完成: 验收子代理只核对需求核对表, 依据是源码的运行 `evidence` 从原仓库取回核对, 依据是测试的重新运行. 编排会话不自己取源码.
5. 写好验收记录后, 回复 "验收报告" 第 4 组选项, 列出每条需求的核对结果, 由用户决定是否采用. 有对不上的需求也照实列出, 不另发补正工单:
   - 用户选 A (采用): 在 `review.md` 写 "用户结论", 运行 `order set accepted`, 按输出提交. 核对没有通过的需求, 用 `risk add` 各登记一条风险.
   - 用户选 B (另选): 运行 `order set rejected`, 按用户给出的方向新建选型工单 (`--kind selection`). 不发布修复工单: 修复工单要求已登记检查命令, 而检查命令在选型采用后才登记.
6. 用户采用后, 用 `decision add` 登记选型结论, 在 `.navigator/plan/decisions.md` 追加条目, 写明决策状态, 批准时间, 来源工单, 决策内容, 决策理由, 可否回退, 影响范围.
7. 选型结论中有检查命令时, 写草稿 `{"commands": ["检查命令"]}`, 运行 `codecheck set --from <草稿>` 登记. 确实没有合适的检查工具时, 经用户同意写 `{"commands": [], "reason": "原因"}` 登记. 登记之前, 实现与修复工单不能新建.
8. 全部关键选型问题都有决策后, 运行 `stage 4`, 按 `ref order-loop` 做骨架.
