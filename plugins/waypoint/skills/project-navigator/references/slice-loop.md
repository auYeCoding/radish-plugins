# 切片循环

同一时间只做一个切片. 一个切片一份文件, 在 `.navigator/slices/` 下, 分三段: "计划" 由编排会话写, "执行结果" 由实现方写, "验收" 由编排会话按验收子代理交回的内容写. 每一步做完都运行 `project-navigator status`, 按 "下一动作" 继续.

## 写计划

1. 先读代码: 本切片要改或要用到的文件, 入口, 相邻模块. 计划里写的路径, 接口名, 数据格式要是读到的, 不是猜的. 文件多时用 Explore 子代理.
2. 运行 `project-navigator slice plan <编号> --slug <短名>`, 命令会建好切片文件.
3. 用 Edit 填 "计划" 段的每个小节, 小节内不加标题:
   - 目标: 做完后使用者能做到什么.
   - 完成标准: 编号列表. 每条写成从入口或界面能看到的结果, 并写明怎么验证. "实现了某个函数" 不是合格的标准.
   - 明确不做: 容易被顺手做掉, 但不属于本切片的事.
   - 需要决定: 必须由用户决定的事; 没有时写 "无".
   - 模块安排 (只有 `build` 切片): 见下方.
   - 结论位置 (只有 `findings` 切片): 结论写进 `.navigator/findings/` 下的哪些文件.
   - 工作假设: 你对细节的判断. 与实际不符时实现方以实际为准.
4. "需要决定" 不是 "无" 时, 先问用户, 把答案写在这一节, 再运行 `slice start --decided`. 没有待定事项时直接运行 `slice start`, 不需要用户先过目.

硬约束是目标, 完成标准, 明确不做与模块安排; 其余都是工作假设. 所以拿不准的细节写进 "工作假设", 不写进完成标准.

### 模块安排

模块怎么表达, 以 `status` 输出的 "项目设置" 为准: 按物理目录分模块的项目, "模块" 一列写目录; 用 Visual Studio 筛选器分模块的项目, 文件一律平铺在工程目录下, "模块" 一列写筛选器名, 不建物理子目录.

- 表格每行一个新增或改动的文件: 文件, 所属模块, 所属的层 (表现, 业务, 数据, 或项目自己定义的层), 这个文件承担的那一件事.
- 唯一定义: 本切片新增的常量, 类型, 配置, 规则, 各自的权威定义放在哪个文件. 同一条知识只定义一次.
- 复用: 用到了哪些已有实现; 没有时写 "无".

安排时遵守项目规范 `.claude/rules/engineering.md`: 一个文件只承担一件事; 跨层只通过接口; 优先复用已有实现; 没有两处真实重复之前, 不建通用模块, 不把代码下沉到公共层.

## 开工

- 普通切片: `slice start` 之后, 用 Agent 工具在后台 (`run_in_background`) 派出 `waypoint:navigator-executor`, 提示词是 `project-navigator brief exec` 的输出原文. 然后告诉用户切片已开工, 结束本轮; 子代理结束时会自动通知.
- 交互式切片: 不派子代理, 见下方 "交互式切片".

## 中途交回

实现子代理不能向用户提问. 它结束时最后一条消息的第一行说明情况:

- "交回: 完成": 运行 `status`, 按下一动作送验.
- "交回: 需要回答" 或 "交回: 需要操作": 把它写的问题或操作步骤原样转告用户. 用户回复后, 用 SendMessage 把回复转给原来的子代理, 它会接着做; 找不到它时重新运行 `brief exec` 派一个新的, 新的子代理靠 "执行结果" 段的 "中途记录" 接着做.

用户的回答改变了计划时 (例如换了一种做法), 先用 Edit 改计划, 运行 `slice replan`, 再让子代理继续. 切片状态一直是实现中, 不需要重新开工.

## 计划与实际不符

实现方发现工作假设与实际不符时, 取得证据后按实际做, 在 "执行结果" 段的 "修正" 表中逐行记录, 不交回. 个别完成标准按事实做不到时, 做完其余部分, 列进 "待定标准". 这两种情况都在验收时由验收子代理核对, 由用户决定. 你不需要在中途处理.

## 送验与验收

1. "执行状态" 为 "完成" 后运行 `project-navigator slice review`. 命令会核对计划段没有被改动, 执行结果已填好.
2. 用 Agent 工具派出 `waypoint:navigator-reviewer`, 提示词是 `project-navigator brief review` 的输出原文.
3. 验收子代理交回后, 用 Edit 把内容原样写入切片文件的 "验收" 段: 每个小节对应它交回的一节, 不改结论, 不删证据. "用户结论" 先保留占位.
4. 运行 `status`, 按下一动作向用户报告并请用户决定. 报告写: 每条标准的结论, 接线与结构核对中的问题, 成立与不成立的修正, 需要用户亲手验证的步骤.

验收结论只有通过, 不通过, 未验证三种. 三种情况下用户的选择:

| 情况                 | 选项                                  | 用户选择之后                                                           |
| -------------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| 全部通过             | A 通过并提交; B 通过, 提交并推送      | 把原话写入 "用户结论", 运行 `slice accept`                             |
| 有未验证, 没有不通过 | A 接受现状并提交; B 补做              | A: 写入 "用户结论", 运行 `slice accept --accept-unverified`; B: 见补做 |
| 有不通过             | A 补做; B 放弃这个切片 (骨架只能补做) | A: 见补做; B: 运行 `slice drop`                                        |

- 需要用户亲手验证的标准 (验证方式为 `manual` 或 `measured` 的项目很常见) 会被判为未验证, 并写在 "人工验收" 中. 把步骤给用户, 用户确认结果后选 A, 在 "用户结论" 中写明用户看到了什么.
- `slice accept` 之后按输出调用 `waypoint:commit-message` 提交. 提交消息不附加任何署名.
- 补做: 把要补的内容写入计划段的 "补做" (替换掉 "无"), 运行 `slice redo`. 命令把本轮验收归档在文件中, 并在文末给出新的 "验收" 段. 然后用 SendMessage 让原来的实现子代理继续, 找不到时重新派出.
- 接线没有接上的切片不能通过: 相关标准会被判为不通过, 只能补做或放弃. 不要用 "下个切片再接" 绕过.

## 交互式切片

逆向, 实测这类任务每一步都要用户配合, 子代理不能与用户对话, 所以由你在对话中直接做. 它只产出结论, 不改业务代码.

1. `slice start` 之后, 在本会话按计划逐步做. 需要用户操作时直接说, 写到用户不用追问就能照做.
2. 每确认一条结论, 立即用 Write 或 Edit 写入 `.navigator/findings/` 下的文件, 再做下一步. 每条结论写明: 宿主或依赖的版本, 位置 (地址, 偏移, 文件与行号), 验证方法, 验证时间. 没有验证过的只能写成 "待验证".
3. 调试输出会占用上下文. 结论都在文件里, 进度在状态里, 所以随时可以让用户新开一个会话调用本技能接着做.
4. 不需要对话的重活 (例如在一份转储里批量搜索) 可以派给后台的通用子代理, 结果回到本会话.
5. 做完后填写 "执行结果" 段, 把 "执行状态" 改成 "完成", 运行 `slice review`, 照常派验收子代理.
6. 需要改业务代码时, 不在这个切片里改: 把结论写好, 在路线中排一个 `build` 切片.

## 待办

当前切片之外的想法, 不论是你的还是用户的, 都用 Edit 追加到 `.navigator/backlog.md`, 每条一行: 内容, 来源, 日期. 文件不存在时用 Write 新建, 一级标题写 "待办". 不顺手做, 也不塞进当前切片的计划.

## 里程复查

当前里程的切片全部结束后:

1. 对照里程目标, 向用户说明达成了什么, 没达成什么.
2. 与用户一起整理 `.navigator/backlog.md`: 每项归入下一个里程, 继续留着, 或删除.
3. 为下一个里程排出切片, 用 `roadmap --from <草稿>` 写入 (已有的里程与切片带上 `id`). 还没有下一个里程而用户有新的目标时, 一并加上.
4. 用户确认后运行 `project-navigator milestone done <编号>`, 按输出提交.

全部里程完成后, 见 `ref change` 的 "收尾".
