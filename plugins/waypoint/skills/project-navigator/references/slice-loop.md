# 切片循环

同一时间只做一个切片. 一个切片一份文件, 在 `.navigator/slices/` 下, 分三段: "计划" 由编排会话写, "执行结果" 由实现方写, "验收" 由编排会话按验收子代理交回的内容写. 每一步做完都运行 `project-navigator status`, 按 "下一动作" 继续.

## 写计划

1. 先读代码: 本切片要改或要用到的文件, 入口, 相邻模块. 计划里写的路径, 接口名, 数据格式要是读到的, 不是猜的. 文件多时用 Explore 子代理.
2. 运行 `project-navigator slice plan <编号> --slug <短名>`, 命令会建好切片文件, 并列出归属本切片的遗留问题. 本切片目标要用到的写进完成标准; 用不到的先请用户决定是否标为不处理, 不为它写完成标准.
3. 用 Edit 填 "计划" 段的每个小节, 小节内不加标题:
   - 目标: 做完后使用者能做到什么.
   - 完成标准: 编号列表. 每条写成从入口或界面能看到的结果, 并写明怎么验证. "实现了某个函数" 不是合格的标准. `findings` 切片的每条标准写明结论给哪个切片的哪件事用, 范围只到那件事需要的程度; "写明全部触发时机", "每个字段的含义" 这类没有边界的写法不合格, 改成 "写明出手层发包要用到的字段".
   - 明确不做: 容易被顺手做掉, 但不属于本切片的事.
   - 需要决定: 必须由用户决定的事; 没有时写 "无". 有完成标准要用户亲手验证时 (进程序看效果, 连设备, 登录账号), 验证要用到的前提也写在这里问用户: 用哪个账号或角色, 手头有哪些物品, 在什么环境里. 取用户最容易满足的前提, 不替用户假设他有什么.
   - 模块安排 (只有 `build` 切片): 见下方.
   - 结论位置 (只有 `findings` 切片): 结论写进 `.navigator/findings/` 下的哪些文件.
   - 工作假设: 你对细节的判断. 与实际不符时实现方以实际为准.
4. "需要决定" 不是 "无" 时, 先问用户, 把答案写在这一节, 再运行 `slice start --decided`. 没有待定事项时直接运行 `slice start`, 不需要用户先过目.

硬约束是目标, 完成标准, 明确不做与模块安排; 其余都是工作假设. 所以拿不准的细节写进 "工作假设", 不写进完成标准.

### 模块安排

模块怎么表达, 以 `status` 输出的 "项目设置" 为准: 按物理目录分模块的项目, "模块" 一列写目录; 用 Visual Studio 筛选器分模块的项目, 文件一律平铺在工程目录下, "模块" 一列写筛选器名, 不建物理子目录.

- 表格每行一个新增或改动的文件: 文件, 所属模块, 所属的层 (表现, 业务, 数据, 或项目自己定义的层), 这个文件承担的那一件事.
- 唯一定义: 本切片新增的常量, 类型, 配置, 规则, 各自的权威定义放在哪个文件. 同一条知识只定义一次.
- 复用: 用到了哪些已有实现; 没有时写 "无".

安排时遵守项目规范 `.claude/rules/engineering.md`: 一个文件只承担一件事; 跨层只通过接口; 优先复用已有实现; 没有两处真实重复之前, 不建通用模块, 不把代码下沉到公共层.

## 开工

- 普通切片: `slice start` 之后, 用 Agent 工具在后台 (`run_in_background`) 派出 `waypoint:navigator-executor`, 提示词是 `project-navigator brief exec` 的输出原文. 然后告诉用户切片已开工, 结束本轮; 子代理结束时会自动通知.
- 交互式切片: 不派子代理, 见下方 "交互式切片".

## 中途交回

实现子代理不能向用户提问. 它结束时最后一条消息的第一行说明情况:

- "交回: 完成": 运行 `status`, 按下一动作送验.
- "交回: 需要回答" 或 "交回: 需要操作": 把它写的问题或操作步骤原样转告用户. 用户回复后, 用 SendMessage 把回复转给原来的子代理, 它会接着做; 找不到它时重新运行 `brief exec` 派一个新的, 新的子代理靠 "执行结果" 段的 "中途记录" 接着做.

用户的回答改变了计划时 (例如换了一种做法), 先用 Edit 改计划, 运行 `slice replan`, 再让子代理继续. 切片状态一直是实现中, 不需要重新开工.

## 计划与实际不符

实现方发现工作假设与实际不符时, 取得证据后按实际做, 在 "执行结果" 段的 "修正" 表中逐行记录, 不交回. 个别完成标准按事实做不到时, 做完其余部分, 列进 "待定标准". 这两种情况都在验收时由验收子代理核对, 由用户决定. 你不需要在中途处理.

## 送验与验收

1. "执行状态" 为 "完成" 后运行 `project-navigator slice review`. 命令会核对计划段没有被改动, 执行结果已填好.
2. 用 Agent 工具派出 `waypoint:navigator-reviewer`, 提示词是 `project-navigator brief review` 的输出原文. 这时按 "等待" 版式回复, 不转述实现方自己报告的结果: 它还没有被核实, 验收之后会再说一遍. 有可以和验收同时做的人工验证时, 只给出步骤.
3. 验收子代理交回后, 用 Edit 把内容原样写入切片文件的 "验收" 段: 每个小节对应它交回的一节, 不改结论, 不删证据. "用户结论" 先保留占位.
4. "遗留核对" 列出的事, 按下方 "遗留问题" 的判断决定登记还是不登记; 能当场解决的直接解决. 与标准无关的未验证观察不登记.
5. 处理用户已经确认过的标准, 见下方 "用户已确认".
6. 运行 `status`, 按下一动作向用户报告. 报告依次写:
   - 第一句结论: 通过 (含用户已确认), 不通过, 未验证各几条, 归属本切片的遗留问题几条, 要用户做什么.
   - 选项代码块 (见下表), 或要用户亲手验证的编号步骤. 同一批步骤只完整给一次, 之前给过的只说 "步骤同前".
   - 需要用户知道的问题: 不通过的标准, 接线与结构核对中的问题, 不成立的修正. 没有时不写.

   通过的标准与成立的修正不逐条复述, 给出切片文件的路径.

验收子代理给出的结论只有通过, 不通过, 未验证三种. 各情况下怎么做:

| 情况                                     | 做法                                                                                                     |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| 全部通过或用户已确认, 本切片没有遗留问题 | 请用户选: A 通过并提交; B 通过, 提交并推送. 把原话写入 "用户结论", 运行 `slice accept`                   |
| 有未验证, 没有不通过                     | 把验证步骤给用户; 用户验不了的, 请用户在补做与收窄之间选. 未验证的标准不能通过                           |
| 有不通过, 或有归属本切片的遗留问题       | 补做, 收窄或标为不处理, 由用户选; 用户决定不要这个切片时, 放弃 (`slice drop`, 骨架只能补做)              |
| 已经补做了 2 轮                          | 不再默认补做: 推荐收窄标准或把剩下的遗留问题标为不处理, 再补一轮只在用户明确要求时做. 以 "下一动作" 为准 |

### 收窄与不处理

补做只为切片目标要用到的东西做. 没验证或没通过的部分, 以及归属本切片的遗留问题, 先问一句: 下游切片或需求要用到它吗? 用不到的, 推荐下面两种做法, 由用户决定:

- 收窄标准: 用 Edit 改写计划中的那条完成标准, 只留目标要用到的部分; 结论改成 "用户已收窄", 证据写用户的原话, 移出了什么, 移到了哪里 (待办, 或遗留问题标为不处理). 不需要再补一轮或重新验收.
- 不处理: 遗留问题的状态改成 "不处理", "处理结果" 写理由与用户的原话.

要用到的, 不能收窄, 也不能标为不处理: 补做, 或在用户同意后放弃切片.

### 用户已确认

需要用户亲手验证的标准 (验证方式为 `manual` 或 `measured` 的项目很常见), 验收子代理看不到用户的屏幕, 只能判为未验证. 这不表示还欠着什么: 用户亲手验过并说了结果, 就是验证本身.

- 用户确认之后, 用 Edit 把这条标准的结论改成 "用户已确认", 证据写用户的原话与日期. 它与通过同样对待, 不走 "接受现状".
- 用户在送验之前已经看过结果的 (交互式切片中当场确认的, 或验收期间同时做完人工验证的), 验收子代理的证据会以 "用户实测: " 开头. 这些直接改成 "用户已确认", 不让用户再做一遍, 也不让用户重新选择.
- 只有用户明确说了结果的才能改; 用户没有验证, 或结果与预期不符的, 保持未验证或按不通过处理.
- 还没有确认的, 把 "人工验收" 的步骤给用户. 步骤中的前提 (物品, 账号, 设备) 用户做不到时, 换成他做得到的重新准备, 不把寻找替代品的工作推给用户.
- 补做之后的验收会沿用上一轮的 "用户已确认", 不让用户为没有改动的标准再验一次. 验收子代理没有沿用而补做又没有改动到的, 你按上一轮归档的验收段改回 "用户已确认", 证据写 "沿用第 N 轮: " 加原证据.
- 标准本身不成立时 (例如要求的东西根本不存在), 经用户同意按上方 "收窄与不处理" 改掉这条标准, 不能放着不验.
- `slice accept` 之后按输出调用 `waypoint:commit-message` 提交. 提交消息不附加任何署名.
- 补做: 把要补的内容写入计划段的 "补做" (替换掉 "无"), 运行 `slice redo`. 命令把本轮验收归档在文件中, 并在文末给出新的 "验收" 段. 然后用 SendMessage 让原来的实现子代理继续, 找不到时重新派出.
- 接线没有接上的切片不能通过: 相关标准会被判为不通过, 只能补做或放弃. 不要用 "下个切片再接" 绕过.

## 交互式切片

逆向, 实测这类任务每一步都要用户配合, 子代理不能与用户对话, 所以由你在对话中直接做. 它只产出结论, 不改业务代码.

1. `slice start` 之后, 在本会话按计划逐步做. 需要用户操作时, 按下方 "请用户实测" 给步骤.
2. 每确认一条完成标准要用到的结论, 立即用 Write 或 Edit 写入 `.navigator/findings/` 下的文件, 再做下一步. 每条结论写明: 宿主或依赖的版本, 位置 (地址, 偏移, 文件与行号), 验证方法, 验证时间. 标准要用到而没有验证过的, 写成 "待验证 (遗留问题 <编号>)", 同时登记进 `.navigator/issues.md`. 用户亲眼确认的结论, 验证方法写 "用户实测", 并写明用户看到了什么; 验收时它直接记为 "用户已确认". 后面的切片查清了以前的 "待验证" 时, 回头改掉原文并把遗留问题标为已解决.
3. 结论文件只写完成标准用得到的结论. 顺带看到的现象 (某个字节的取值, 某个分支) 不写解释与推测, 不起名字; 确实值得留下的, 只在文件末尾 "未验证的观察" 一节记一行原始现象, 不登记遗留问题, 不为它补测. 每多写一条结论, 就多一条要证据的东西.
4. 每查一步之前先想: 这条结论会用在哪个切片, 没有它哪项需求做不成. 答不出时停下来问用户还要不要查, 不为了把规则查全而让用户反复操作.
5. 调试输出会占用上下文. 结论都在文件里, 进度在状态里, 所以随时可以让用户新开一个会话调用本技能接着做.
6. 不需要对话的重活 (例如在一份转储里批量搜索) 可以派给后台的通用子代理, 结果回到本会话.
7. 做完后填写 "执行结果" 段, 把 "执行状态" 改成 "完成", 运行 `slice review`, 照常派验收子代理.
8. 需要改业务代码时, 不在这个切片里改, 用户说 "你直接改" 也一样: 说明原因, 把结论写好, 在路线中排一个 `build` 切片.

### 请用户实测

1. 开始记录之前, 先给出完整的编号步骤与前提 (在哪个场景, 用什么角色与物品), 用户说准备好了才开始. 不边录边补步骤.
2. 用到的采样或调试工具先自己空跑一次, 确认超时, 记录条数上限这类设置够用, 不让用户因为工具问题重做.
3. 录制不定时长: 用户说开始就开始, 用户说结束才停.
4. 状态变化很快的, 优先请用户按顺序做完, 再把整段日志或记录文件发过来, 由你对照.

## 遗留问题

遗留问题是已做部分中还没有解决, 又与完成标准, 需求或已交付的行为有关的事. 它们记在 `.navigator/issues.md` 的表格中, 表头与填写说明由脚本写好, 编排会话用 Edit 维护.

登记之前先判断, 三种情况才登记:

- 它会改变某条完成标准的结论 (例如标准要用的结论没有验证).
- 它是本切片交付的代码或结论中的已知缺陷.
- 需求文件 "必须要做" 中的某一条要用到它, 而本切片本来就该给出.

其余都不登记: 与标准无关的未验证观察, 顺带想到的 "为什么", 以后切片自己会去查的事. 它们不是债. 想留下的观察按 "交互式切片" 第 3 条记一行; 是新想法的记进待办.

- 登记时每个问题一行, "归属切片" 写当前切片. 只有后面某个还没有结束的切片的目标本来就要做这件事时, 才写那个切片, 并在 "问题" 中写明在等什么. 不为安置遗留问题新建切片, 也不把它塞进以后某个里程.
- 解决后把状态改成已解决, "处理结果" 写怎么解决的或结论在哪里.
- 用户决定不处理的 (见 "收窄与不处理"), 状态改成不处理, "处理结果" 写理由与用户的原话. 不处理要用户决定, 你只能推荐.
- `slice accept` 与 `slice drop` 会拒绝: 归属本切片或已经结束的切片而没有关闭的问题; `finish` 要求全部关闭.
- 用户问遗留问题时, 只按这个文件回答, 见技能 "回复" 一节.

## 待办

还没有开始的新想法, 不论是你的还是用户的, 都用 Edit 追加到 `.navigator/backlog.md`, 每条一行: 内容, 来源, 日期. 文件不存在时用 Write 新建, 一级标题写 "待办". 不顺手做, 也不塞进当前切片的计划. 已做部分欠下, 又符合上面登记条件的事, 记进遗留问题.

## 里程复查

当前里程的切片全部结束后:

1. 对照里程目标, 向用户说明达成了什么, 没达成什么.
2. 与用户一起整理 `.navigator/backlog.md`: 每项归入下一个里程, 继续留着, 或删除. 确认 `.navigator/issues.md` 中没有归属已结束切片而没有关闭的问题; 归属下一个里程切片的问题, 那个切片的目标要用到的写进它的计划, 用不到的请用户决定是否标为不处理.
3. 为下一个里程排出切片 (每个切片都要过 `ref intake` 的 "新增切片之前"), 用 `roadmap --from <草稿>` 写入 (已有的里程与切片带上 `id`). 还没有下一个里程而用户有新的目标时, 一并加上.
4. 用户确认后运行 `project-navigator milestone done <编号>`, 按输出提交.

全部里程完成后, 见 `ref change` 的 "收尾".
