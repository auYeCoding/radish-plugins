# 需求变更, 里程复查与项目收尾

## 需求变更

用户在任何阶段提出新需求, 改变方向, 或推翻已定内容时:

1. 暂停当前步骤, 记住 `status` 输出中的 "最后动作", 处理完变更后回到这里.
2. 分析影响, 回复 "需求变更":
   - "变更编号" 写 "接受后分配".
   - "影响分析" 五项: 简报, 推进路线, 决策, 切片, 当前工单. 没有影响的写 "无".
3. 用户选择后, 写草稿 `{"title": "变更标题", "status": "<状态>"}`, 运行 `change add --from <草稿>`, 在 `.navigator/plan/changes.md` 追加条目 `## 变更 0001: 标题` (编号取自命令输出):
   - 选 A 接受: 状态写 accepted. 更新简报 ("简报版本" 加 1, "最近变更" 写变更编号); 需要时更新推进路线 (`roadmap --from`), 用 `decision supersede` 取代旧决策; 当前工单受影响时运行 `order set voided` 作废.
   - 选 B 延后: 状态写 deferred, 条目中写明计划何时处理.
   - 选 C 放弃: 状态写 dropped, 条目中写明原因.
4. 回到暂停的位置继续.

## 里程复查

里程的切片全部完成后:

1. 运行 `check` 做一次脚本体检, 结果写成一行, 放进 "偏离检查" 的 "文档体检".
2. 回复 "里程复查":
   - 里程成果: 完成的切片, 运行方式 (启动命令取自最后一张回执), 版本提交 (最后一个提交的短哈希).
   - 简报对照: 里程目标与覆盖指标逐条对照简报, 写达成情况.
   - 偏离检查: 范围偏离, 约束偏离, 新增风险, 文档体检.
   - 复盘要点: 有效做法与改进事项.
3. 在 `.navigator/plan/milestone-reviews.md` 追加条目 `## 里程 0001: 名称`. 第一次写入前运行 `template milestone-reviews`.
4. 用户选 A: 运行 `milestone <编号> done`. 还有里程时运行 `milestone <下一个> active`, 回到阶段 5; 刚复查的里程是最后一个时, 运行 `stage 6`.
5. 用户选 B: 走需求变更.

## 项目收尾 (阶段 6)

1. 汇总三项内容:
   - 总体验收: 简报的成功指标逐条对照.
   - 项目统计: 里程, 切片, 工单, 变更的数量, 从 `.navigator/state.json` 读取.
   - 复盘要点: 有效做法, 改进事项, 遗留事项.
2. 在 `.navigator/plan/milestone-reviews.md` 追加条目 `## 项目收尾`.
3. 回复 "项目收尾".
4. 用户选 A: 运行 `finish`, 项目结束. 收尾记录或 `finish` 写下的完成标记还没入库时, 输出要求回复 "阶段提交", 按 [order-loop.md](order-loop.md) 的 "阶段提交" 处理, 两者由这次阶段提交一起入库. 之后按下一动作回复 "项目完成".
5. 用户选 B: 按需求变更流程新开里程, 更新推进路线后运行 `stage 5`. 收尾记录由这次推进登记的阶段提交入库.

## 项目完成

项目已确认收尾, 记录都已入库之后, 下一动作要求回复 "项目完成", 不再回复 "项目收尾".

1. "完成情况" 三项用只读 git 命令查询: "记录提交" 写 `status` 输出的记录提交; "工作区域" 写 `git status --short` 的结果, 没有改动时写 "干净"; "远程推送" 写 `git status -sb` 第一行中与远程的差距, 例如 "领先 2 个提交", 没有上游时写 "没有上游".
2. 用户选 A, 或提出新需求: 按需求变更流程新开里程, 更新推进路线后运行 `stage 5`.
3. 用户选 B: 运行不带强制参数的 `git push`, 再回复 "项目完成". 项目完成且记录都已入库时守卫放行推送; 被拒绝时如实转告拒绝理由.
4. 用户选 C: 不做任何操作.

项目完成后又写了状态 (例如处理验收异常), 下一动作会要求运行 `finish`: 记录有没入库的改动时, `finish` 登记阶段提交 "项目收尾后的记录更新", 按 "阶段提交" 处理; 没有改动时 `finish` 不写任何文件.
