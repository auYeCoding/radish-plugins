# 立项

立项阶段的目标: 一份用户确认过的需求文件, 登记好的项目设置, 一条从最小骨架开始的路线. 立项全程是对话, 不派子代理, 不写代码.

## 确认需求

1. 读用户给的初始需求. 已有项目先读一遍项目: 入口在哪里, 有哪些模块, 沿用什么约定. 文件多时用 Explore 子代理.
2. 向用户复述你的理解, 不超过 5 条, 只写会影响路线的要点.
3. 含糊, 缺失, 互相冲突的地方都是待定问题: 自己列成清单, 不一次全部展示给用户. 每条回复只提一个, 先说还剩几个, 再按技能 "回复" 一节的选项代码块提问, 不自行假设. 用户说 "你定" 时给出建议与理由, 由用户确认.
4. 讨论中冒出的, 不属于本项目范围的想法, 记进 `.navigator/backlog.md`.

## 需求文件

需求确认后, 用 Write 写入 `.navigator/requirements.md`. 它是需求的唯一权威来源, 之后的路线与每个切片的计划都从它出发. 依次写这几节:

- `## 目标`: 一段话, 做出来的东西给谁用, 解决什么问题.
- `## 必须要做`: 编号列表, 每条是使用者能感知的一项能力.
- `## 明确不做`: 讨论中决定不做的事, 写明原因.
- `## 约束`: 运行环境, 技术栈, 工程形态, 不能做的操作等硬性条件.
- `## 现状`: 只在已有项目中写: 入口, 模块, 已有约定.
- `## 已确认的结论`: 每个待定问题的结论, 一条一行.

需求文件写朴素的话, 不贴代码. 用户的原话有约束力时原样摘录.

## 选型

- 用户已经定下的技术栈直接写进 "约束", 不再讨论.
- 需要选的关键依赖 (语言, 框架, 核心库), 逐条回答 "它能不能实现每条需求", 依据写明来源: 已安装依赖的源码, 官方文档中的明确说法, 或一次实际运行. 只凭记忆的结论要说明是没有核实的.
- 需要动手才能确认的 (写一段临时测试, 读一个库的源码, 在目标程序里实测), 不在立项时做: 在路线里排一个 `findings` 切片, 放在最小骨架之后. 骨架本身依赖这个结论时, 先与用户商量用最保守的做法搭骨架.
- 重要的取舍用 `decision add` 记一条决策.

## 项目设置

1. 运行 `project-navigator setup`, 看脚本对模块组织方式的建议与依据.
2. 与用户确认两件事:
   - 模块组织方式: `directories` 是按物理目录分模块, 适用于 Python, Web, Go 等多数项目; `filters` 是源码文件平铺在工程目录下, 用 Visual Studio 虚拟筛选器 (`.vcxproj.filters`) 分模块, 适用于 Visual Studio 项目.
   - 验证方式: `auto` 是有能在仓库根目录直接运行的检查或测试命令; `manual` 是要用户亲手构建或运行才能确认; `measured` 是要在真实环境中实测. 不能由你构建或运行的项目不选 `auto`.
3. 项目有自己的约定时 (注释语言, 类的骨架写法, 命名习惯), 写进草稿的 `conventions`.
4. 写草稿, 运行 `project-navigator setup --from <草稿>`. 命令同时把工程规范写入 `.claude/rules/engineering.md`, 项目内所有会话与子代理都会自动加载它. 要调整时重新运行 `setup`.

## 路线

路线分里程与切片:

- 里程: 一个对用户有意义的阶段成果, 写明目标.
- 切片: 一次实现加一次验收能做完的一块纵向功能. 做完后从入口或界面能看到它.

排路线的规则:

1. 第一个里程的第一个切片是最小骨架: 从真实入口 (可执行文件, 导出函数, 页面) 进入, 经过规划中的每一层, 每层只做最少的事, 能按验证方式确认它跑通了. 骨架不追求功能, 只证明各层接得上.
2. 之后的每个切片在骨架上加一项能力, 纵向切: 一个切片同时包含它需要的界面, 逻辑与数据, 不按层横着切. "先把数据层全写完" 这样的切片不合格.
3. 只把当前里程的切片排全; 之后的里程只写名称与目标, 到了再排. 提前排细的切片多半会作废.
4. 切片的种类 `kind`: `build` 是改代码 (默认); `findings` 是只产出结论, 例如逆向, 实测, 调研.
5. `findings` 切片默认是交互式 (`interactive` 为 true): 由编排会话在对话中直接做, 适合每一步都要用户配合的任务. 纯读代码或读文档, 不需要用户配合的, 写 `"interactive": false`, 交给后台的实现子代理.
6. 切片宜大不宜碎: 一次实现能做完, 验收能看清, 做完能运行, 就不再拆. 高风险的部分单独成一个切片.

### 新增切片之前

每排一个切片 (立项时, 里程复查时, 中途追加时都一样), 先回答两个问题:

1. 不做它, 需求文件 "必须要做" 中的哪一条做不成? 答不出的不排进路线, 记进待办.
2. 有没有更省事的办法达到同样的目的? 例如让用户自己选或自己填, 而不是由程序推算; 用已有的资料, 而不是去逆向或实测.

有更省事的办法时, 把它作为推荐项问用户, 费事的办法排在后面并写明多花什么. `findings` 切片尤其要过这一关: 只有结论确实会被后面的切片用到, 又没有别的办法得到时才排. 用户随口提到的一个现象不等于一项需求, 先问清楚他要不要软件处理它.

写好草稿后运行 `project-navigator roadmap --from <草稿>`. 编号由脚本分配, 之后修改路线时已有的里程与切片带上 `id`. 路线视图在 `.navigator/roadmap.md`.

向用户展示路线并取得认可, 然后按命令输出的提交步骤提交, 再运行 `status` 进入切片循环.
