# Maintaining project-navigator

English | [简体中文](project-navigator-maintaining.md)

[Back to the usage guide](project-navigator.en.md)

This document is for maintainers: design overview, design decisions, component map, troubleshooting, change workflow, tests, and measured findings. Repository-wide conventions are in [MAINTAINING.md](../../../MAINTAINING.md).

## Design overview

The skill has three layers, each with one job:

| Layer   | Location                                          | Job                                                                                        |
| ------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Rules   | `SKILL.md`, `references/`, `guide/executor.md`    | Written for the model: workflow, steps, which reply to use when                            |
| Scripts | `runtime/navigator.mjs`, `runtime/hook.mjs`       | Commands change state; hooks guard a few write boundaries and reply structure              |
| Spec    | `spec/templates.json`, `standards/engineering.md` | Single source of truth for replies, record files, writing rules, and engineering standards |

Plugin-level wiring:

| Location                    | Contents                                                                                                             |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `hooks/hooks.json`          | Four events (PreToolUse matching write tools only, UserPromptSubmit, SessionStart, Stop) all call `runtime/hook.mjs` |
| `bin/project-navigator`     | Command entry for the Bash tool: `exec node .../navigator.mjs "$@"`                                                  |
| `bin/project-navigator.cmd` | Command entry for the PowerShell tool                                                                                |
| `agents/navigator-*.md`     | Executor, reviewer, researcher, and reader subagents                                                                 |

In a user's project, the skill uses these locations:

| Location                       | Contents                                                                                | Committed |
| ------------------------------ | --------------------------------------------------------------------------------------- | --------- |
| `.navigator/`                  | State file, plan records, work order folders                                            | Yes       |
| `.navigator/drafts/`           | JSON drafts the orchestrator passes to commands                                         | No        |
| `.claude/settings.json`        | Permission rules                                                                        | Yes       |
| `.claude/settings.local.json`  | Local copy of the permission rules, excluded via `.git/info/exclude`                    | No        |
| `.claude/rules/engineering.md` | Project standards, loaded by every session in the project                               | Yes       |
| `.git/navigator/`              | Work order approval record (`order-approval.json`), source evidence cache (`evidence/`) | No        |

## Design decisions

Each entry states the decision, the reason, and what happens if it is changed.

### Sessions and execution

- **Orchestration and execution are separate; execution runs in a background subagent.** The orchestrator uses the Agent tool in the background (`run_in_background`) to dispatch `waypoint:navigator-executor` with the output of `exec-brief`; when the subagent finishes, the orchestrator is notified and continues on its own. 0.x had the user open an executor session: each work order meant switching sessions, pasting a launch prompt, confirming a kickoff alignment, choosing how to report, and confirming the receipt back in the orchestrator, about seven choices per order. The cost of a subagent is that it cannot ask the user questions while it works, so the kickoff alignment is gone and anything needing a user decision ends the run as blocked; the module plan goes into the receipt and the reviewer checks it. If changed: back to the multi-session round trip, or the orchestrator writes code itself and planning and implementation mix again.
- **No "open an executor session by hand" fallback.** Keeping it would keep the whole launch prompt registration, kickoff alignment, fork claiming, and orchestrator address machinery, which produced most entries of the 0.x troubleshooting table. Very large tasks are split into several orders. If changed: two execution paths, with guards and reminders duplicated for each.
- **The orchestrator is not registered; it is recognized by a marker in the transcript.** `enter` outputs "编排标记: project-navigator 编排标记 <id>", where the id is the first 12 hex digits of the SHA-256 of the project path (lowercased on Windows). The output is injected into the skill content, which is recorded in the session transcript, and the hook looks for the marker through `transcript_path`. The source code contains only the prefix, so a session that reads the source is not mistaken for the orchestrator; `status` does not print the marker, so a subagent running `status` does not affect the main session. A forked session copies the transcript and carries the marker, so rewinding or editing a message needs no handling. 0.x registered the identity in `.git/navigator/orchestrator.json`, with rules for taking over, being superseded, claiming forks, and re-registering. If changed: back to registration and claiming, with a chance of misjudging identity every time the session id changes.
- **An unchanged blocked order continues with the same executor.** `order set issued` records a digest of the order file at issue time (`issuedDigest`). When a blocked order's file still matches, no new review is needed, and the output tells the orchestrator to resume the original subagent with SendMessage (measured: SendMessage resumes a finished subagent with its context), or to dispatch a new one if it cannot. A changed order needs a new review. If changed: a small user action costs a new review, or the subagent starts over every time.
- **The executor subagent omits `tools` and inherits every tool of the session.** It writes code, runs builds and tests, and may need the user's MCP tools. Plugin subagents do not support the `hooks`, `mcpServers`, and `permissionMode` fields (official documentation); its write scope is limited by the plugin-level guard. If changed: listing `tools` misses the user's tools.
- **Delegation prompts are generated by scripts and used verbatim; the guard does not compare them.** `exec-brief`, `review-brief`, and `research-brief` are the single source of the prompts. The 0.x guard compared the review prompt character by character and occasionally refused a dispatch over whitespace. If changed: prompts scatter across rule files and drift between versions.

### Guard and reply checks

- **The guard looks only at the target path of write tools, with four rules.** Nobody writes the state file or the generated views directly; the reviewer writes no files; under `.navigator/` the executor writes only the current order's receipt and `artifacts/`, writes no business files on record-only orders, and writes no business files when the order is not running; the orchestrator writes only under `.navigator/`. Subagents are told apart by `agent_type` in the hook input (`waypoint:navigator-executor` and so on; measured: plugin subagents report "<plugin>:<name>"). 0.x also parsed Bash command text, whitelisted the orchestrator's tools, and checked prompts, record structure, user test output, and changes to `.claude/settings.json`; most of these rules were added for cross-session scenarios and past incidents, and they caused most denials and misjudgments. If changed: each rule added back blocks some normal operation.
- **"The orchestrator writes no business files" stays.** It is not about malice but about role collapse: one "just fix it" from the user and the model writes code, and the orchestrator's context is muddled from then on. The transcript is read only when the main session writes a project file outside `.navigator/`. If changed: the orchestrator gradually turns into an executor.
- **Stop checks only reply structure: the heading is a reply type, the first line under it is the conclusion, there is exactly one option block matching the spec, code blocks are closed, and no placeholder remains.** The heading identifies the reply type and the option block identifies the user's choice (order review approval depends on it), so these two cannot be relaxed. A reply whose `optionSets` is empty in the spec (currently only "工单执行") needs no choice from the user and has no option block; adding one sends the reply back. In 1.0.0 and 1.1.0 "工单执行" had a "wait" option, and users thought they had to choose A before the wait started. Sections, keys, progress values, and writing rules are reminders in the fill-in instructions. 0.x sent replies back for writing rules and summary length, leaving two copies on screen. A reply is sent back at most once (`stop_hook_active` passes) and is not checked while background tasks run. If changed: writing rules become frequent send-backs again.
- **Option groups with two choices also become buttons; the option block stays.** The Claude desktop app has a tool that fills its "next step" box (`mcp__ccd_turn__wrap_up`, see `BUTTON_TOOL` in `lib/reply-guide.mjs`). The box takes at most 2 buttons, and a click sends the button text as the user's reply. The fill-in instructions from `reply` include a "按钮" (buttons) line; the button text is the first clause of each choice (`choiceLead`), so a click is recognized the same way as a typed answer (`isChoiceSelected`). Groups with three or more choices get no buttons, and neither do groups marked `"buttons": false` in the spec (the user must type more after choosing, or the choice leads to a commit: the app does not allow a reply button to approve a commit). Buttons never replace the option block: the box can be dismissed and is not kept in the transcript, and both the Stop check and order review approval read the option block. The tool is internal to the app with no public contract, and no hook checks that it was called; if it is renamed or removed, replies fall back to the option block alone without errors. If changed: without the option block, other environments and users who dismiss the box cannot see the choices.
- **Replies start with a one-line conclusion; the human summary block at the end is gone.** A reader with little time sees only what comes first; the summary at the end repeated the conclusion. The conclusion length is only a reminder (`conclusionMaxLength`). Progress went from four lines to one. If changed: the key information ends up at the bottom.
- **Record files are not checked at write time; `check <file>` self-checks after writing.** Scripts that read records (review point prefill, the receipt's execution status, the review's verdicts) read key lines and tables and give a clear reason when they cannot. `check` with files assigns no checkup number and writes no state, so the executor can use it too. If changed: writes are denied as often as in 0.x.

### Work orders and review

- **A work order needs two user decisions: publish it in "工单审阅" (order review), and accept and commit it in "验收报告" (review report).** The review card lists only the "审阅要点" (review points: goal, decisions needed, out of scope, sizing reason) and the order file path, prefilled by `reply approve` from the order file. Approval is still bound to the digest of the order file (the hook records the digest when the review reply ends and the choice when the user answers), so a shorter display does not weaken the binding. 0.x quoted five sections of the order verbatim; users could not read it in a few seconds, and most details were beyond their judgment anyway. If changed: the review becomes a formality, or users read every order in full.
- **Test authorization is gone.** The executor does not run tests with external effects and lists them under "外部影响" (external effects) in the receipt's test record; the reviewer runs the code checks and the receipt's other test commands, not the external ones, and judges those from the receipt's output. MCP evidence tools are no longer registered; the reviewer makes read-only queries at the places named in the receipt's evidence record, with the constraint stated in the prompt and the subagent definition. If changed: every order with an external test costs one more user choice.
- **Unverified criteria can be accepted explicitly by the user.** The third option group of "验收报告" (only unverified, nothing failed) lets the user accept as is and commit, via `order set accepted --accept-unverified`; the unverified criteria are recorded as risks. 0.x always failed the order, so criteria that depend on external evidence were rejected over and over. Failed criteria still cannot be accepted. If changed: orders cannot converge when external conditions are missing.
- **Committing is not an order state.** Order states are drafting, issued, blocked, reviewing, accepted, rejected, and voided; after `order set accepted` the orchestrator calls commit-message as the output says, and the state file goes in with that commit. 0.x had committing and a commit settlement record to match `lastCommit`; without reconciliation, neither is needed. When old state is read, accepted and committing orders count as accepted and ended. If changed: the state file stays modified after each commit.
- **Order size follows four limits, not the number of criteria.** One executor run can finish it, one review can check it, it runs afterwards, risky parts are separate; within these, bigger is better, one slice per order by default, with the reasoning in "粒度依据" (sizing reason). 0.x capped criteria at 5, so criteria became denser; consecutive rejections only ever led to smaller slices. A rejection now first asks why. If changed: orders split ever finer, and user confirmations grow with them.
- **Orders that change code check for registered check commands at creation (`creationBlocker`), and again before issue.** Run-check and analysis orders only produce records, need no check commands, and are followed by an order of the same kind when rejected. A rejected selection is followed by a new selection order, not a fix order: fix orders require check commands, which are registered only after a selection is adopted. If changed: an order rejected before check commands are registered has no way forward.
- **Check commands exclude `.navigator/` and `.claude/`.** Some formatters also process Markdown by default and would pull the records in. If changed: the record format fails every implementation order's check criterion.
- **A selection answers only "can the library do each requirement", is reviewed in one round, and the user decides whether to adopt it.** The `evidence` command fetches the cited lines from the original repository at that version (https only, git reads no credentials). The orchestrator may recommend technologies; only key dependencies get selection orders, and minor libraries are chosen by the executor within implementation orders. If changed: every small dependency needs an order, or key dependencies go without evidence.

### Installation and upgrade

- **Hooks live at plugin level and exit at once in projects that are not initialized.** `hooks.json` uses the shell-free form (`"command": "node"`, `"args": ["${CLAUDE_PLUGIN_ROOT}/..."]`), measured to work with spaces and Chinese characters in paths. `hook.mjs` first checks for `.navigator/state.json` and exits without it, and also exits when the project is marked uninstalled. 0.x had `init` write hooks into the project settings and copy the scripts into `.navigator/bin/`: about 60 scripts committed per project, a manual upgrade after every plugin update, and copies that could not upgrade themselves. The cost is that in every project with the plugin enabled, each write tool call and each message starts Node once. If changed: back to copied scripts and manual upgrades.
- **Commands run through the plugin's `bin/`, written as `project-navigator <command>`.** Official documentation: files in a plugin's `bin/` are on the Bash tool's PATH; measured: the PowerShell tool runs the `.cmd` of the same name. The name is the full `project-navigator`, to avoid clashing with tools on the user's PATH (the plugin directory comes after the user's PATH, so the user's tool would win). `bin/project-navigator` needs the executable bit in the repository. The skill's `enter` still runs `node "${CLAUDE_SKILL_DIR}/runtime/navigator.mjs"`, because the PATH of `!` commands is not documented. If changed: commands depend on a copy inside the project.
- **Reference files and the executor guide are printed by `ref <name>`.** In the default permission mode, reading plugin files outside the project with Read needs user approval; the permission rules cover the plugin command, so its output needs no confirmation and is always the current version. If changed: either copy into the project, or a prompt on every read.
- **Permission rules go into both `settings.json` and `settings.local.json`, and broad writes are not allowed.** The rules are `Bash(project-navigator *)`, `PowerShell(project-navigator *)`, and `Edit(.navigator/**)`. Rules in the project's `settings.json` take effect only after the user accepts the workspace trust dialog and never in headless mode; the local file needs no trust. Confirmations for the executor's business file writes follow the user's permission mode: measured, a background subagent's write prompt appears in the main session (without saying it comes from the subagent), and "Always allow" switches the session to Accept edits. So `init` adds no `Edit(**)`, and the usage guide suggests Accept edits while an order runs. `SKILL.md`'s `allowed-tools` also allows node and the `project-navigator` command, only for the turn that invokes the skill, for initialization. If changed: a broad rule stops confirming every edit in the project.
- **Upgrading from 0.x is done by `init`; entering first removes the old orchestrator registration.** `init` removes the project-level hooks and old permission rules, deletes `.navigator/bin/` and `.navigator/guide/`, cleans the old files in `.git/navigator/` and `refs/navigator/snapshots`, and moves an issued order without a receipt back to drafting. Until the upgrade, the old project-level hook still runs; it identifies the orchestrator by `orchestrator.json` and blocks commands by whitelist. So when `enter` finds an old installation it deletes that file first, the old hook treats the session as an ordinary one, and `project-navigator init` is no longer blocked. If changed: running the upgrade from an old orchestrator session is denied by the old guard.
- **Everything under `.navigator/` except drafts is committed, and ignore rules are checked at entry and initialization.** `.navigator/.gitignore` re-includes directories, the file types the plugin writes, and everything under each order's `artifacts/`, then excludes `drafts/`. `init` and every entry run `git check-ignore --no-index` on the paths that must be committed (state file, glossary, a sample location of each record type, `.claude/settings.json`, and `engineering.md`), and stop with the offending rule if a parent rule ignores them. If changed: records are incomplete after switching machines or cloning.
- **Committing skill products is a step in command output, not a reply type.** When skill products are uncommitted, the output of `init`, stage changes, and `finish` gives the arguments for calling commit-message (committing only `.navigator/` and plugin-managed settings; commit-message asks about other changes); `finish` counts the state file, since no later commit would carry the completion mark. 0.x had the "阶段提交" (stage commit) reply and the `stagecommit` command, one more three-way choice per stage. If changed: every stage costs one more user choice.
- **Scripts use only Node.js 22 built-in modules.** The hooks run on user machines and cannot require installing dependencies.

### State and records

- **`state.json` is the single source of state and is written only by plugin commands.** Writes compare a revision number and write a temporary file before renaming; reads migrate old structures (schema 5 drops session registration, `lastCommit`, `stageCommit`, `pendingAnomaly`, `evidenceTools`, and the order's `authorizedTests`). The guard denies changing it with write tools. If changed: concurrent writes overwrite each other, or the model edits state by hand.
- **Snapshots and reconciliation are removed.** `.navigator/` is already in Git, so rollbacks and manual edits are visible with git. 0.x snapshots, pending writes, reconciliation, and the "验收异常" (review anomaly) reply guarded against manual edits but could stall the workflow after any `git reset` or formatter hook. Now a rollback continues from the current records; when they do not match reality, the orchestrator replies with "运行受阻" (blocked run) for the user to decide. If changed: every rollback needs anomaly handling again.
- **`spec/templates.json` is the single source for replies, record files, and writing rules.** Reply checks, skeletons, checkups, and reference documents all read the spec. If changed: documents and checks drift apart.
- **Replies and record files start from a skeleton, and progress is computed by the script.** Models miscount progress or miss sections.
- **There is one way to count characters** (`lib/text-units.mjs`): a Chinese character, an English word, a number, or a path counts as one; spaces and punctuation do not. Sentence length and conclusion length share it.
- **Chinese content is passed to commands through JSON drafts under `.navigator/drafts/`.** Windows PowerShell 5.1 garbles Chinese arguments.

### Skill anomalies and problem reports

- **The scripts record only the signs they can be sure of and do not judge causes.** Four signs: a command or hook throws an internal error (not a `WorkflowError` and not a mistyped argument); the self-check in `status` finds an inconsistent state; a command named in the previous "下一动作" (next action) is refused by a workflow rule; the same next action is given 4 times in a row while the state revision does not change (not counted while waiting for the executor). Ordinary refusals by workflow rules are not recorded. If changed: every slip produces a report, or the model works around skill problems and maintainers never see them.
- **Anomalies are recorded in `.git/navigator/`, and reports are written to `.navigator/drafts/reports/`.** Neither is committed: the records are local runtime facts, and reports go to the maintainers, not into the project records. An identical unreported anomaly is recorded once, and at most 30 are kept; once written into a report they are marked as reported, so one problem is not reported twice.
- **A report states only what happened.** The script fills in the environment, a state summary, and the recorded anomalies; the model fills in the course of events in a draft (what it was doing, expected, actual, how to reproduce). No guesses about causes and no advice: whether and how to fix is for the maintainers to judge, and a model's guess easily misleads the investigation. A report contains no work order text or business code, and the project and skill directory paths are replaced with placeholders. If changed: reports leak project content or carry unfounded conclusions.
- **Orchestration pauses only when it cannot continue.** For an internal command error or an inconsistent state, or when the draft says `"blocked": true`, "问题报告" (problem report) uses option group 2 and waits for a fix; otherwise it uses group 1 and continues after recording. When the state is inconsistent, the next action in `status` becomes the report itself.
- **A failed recording never affects commands or hooks.** A failing hook still lets the action through and only adds an anomaly, and the orchestrator is reminded to report it on the user's next message; `report` runs even when the state file is corrupt.

| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |

| `project-navigator` is not found                                                           | The plugin is not enabled, or the session started before the plugin update; PowerShell cannot find the `.cmd`                                                                     | `bin/`                                         | Check with `claude plugin list`; restart the session                                                                                      |
| Plugin commands or record writes ask for permission                                        | The local settings lack the rules, or the command does not start with `project-navigator`                                                                                         | `lib/settings.mjs`                             | Check the rules in `.claude/settings.local.json`                                                                                          |
| The orchestrator's write outside `.navigator/` is denied                                   | This is rule 4; issue a work order instead                                                                                                                                        | `lib/guard.mjs`                                | Drive `hook.mjs` through stdin with an orchestrator transcript                                                                            |
| A session that is not the orchestrator cannot write business files                         | The project's orchestrator marker appears in its transcript, for example it once invoked the skill                                                                                | `lib/orchestrator-marker.mjs`                  | Search the transcript for "project-navigator 编排标记"                                                                                    |
| The executor's business file write is denied                                               | The order is not issued, or it is a run-check or analysis order                                                                                                                   | `lib/guard.mjs`, `lib/workflow-orders.mjs`     | The "工单状态" (order status) line of `status`                                                                                            |

## Measured findings

### Basis for 1.0.0 (Claude Code 2.1.321, Windows 10, 2026-11-10)

Measured in `claude -p --plugin-dir` with a probe plugin containing only hooks, `bin/`, and one subagent, with spaces and Chinese characters in paths:

| Question                             | Finding                                                                                                                                                                         |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Plugin-level hooks                   | Both the exec form and the shell form in `hooks.json` fire, and `${CLAUDE_PLUGIN_ROOT}` expands correctly                                                                       |
| Subagent identity                    | A plugin subagent's PreToolUse input has `agent_id` and `agent_type: "<plugin>:<name>"`                                                                                         |
| Transcript                           | PreToolUse input has `transcript_path`; at the first tool call the transcript already contains this turn's marker; scanning a 0.5 MB transcript takes 1 to 2 ms                 |
| Plugin `bin/`                        | The Bash tool runs an extensionless script directly (Git Bash); the PowerShell tool runs the `.cmd` of the same name                                                            |
| Background subagents                 | Headless mode waits for a background subagent and processes its result; in the desktop app its completion notification wakes the main session                                   |
| Resuming subagents                   | SendMessage resumes a finished subagent with its earlier context                                                                                                                |
| Subagent write permission            | Without rules, writes are denied in headless mode; a bare `Edit` rule does not allow Write, `Edit(**)` allows foreground and background subagent writes                         |
| Desktop app, default permission mode | A background subagent's write prompt appears in the main session ("Allow Claude to write x.txt?", not naming the subagent); "Always allow" switches the session to Accept edits |

Official documentation (2026-11-10): files in a plugin's `bin/` are on the Bash tool's PATH, after the user's PATH; plugin subagents do not support `hooks`, `mcpServers`, or `permissionMode`; a skill's `allowed-tools` applies only to the turn that invokes it.

### Earlier findings (Claude Code 2.1.280 to 2.1.284)

| Question                | Finding                                                                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `!` commands in a skill | Without `allowed-tools`, the whole invocation aborts in the default mode; `${CLAUDE_SESSION_ID}` matches the hook's `session_id`; they do not trigger PreToolUse    |
| The skill `shell` field | In a child session without Git Bash, a skill with `shell: bash` fails                                                                                               |
| Stop send-back          | A top-level `{"decision": "block"}` works, and the second Stop has `stop_hook_active` set to true                                                                   |
| Denials in bypass mode  | PreToolUse `permissionDecision: "deny"` still applies                                                                                                               |
| Context injection       | The model reads `additionalContext` returned by UserPromptSubmit; slash commands also trigger the event                                                             |
| Permission rules        | Rules in the project `settings.json` need workspace trust and never apply in headless mode; `settings.local.json` needs none; an `Edit(...)` rule also covers Write |
| Session forks           | `--fork-session`, rewinding, and resending after an interrupt in the desktop app all change the session id, and the forked transcript copies the original history   |
| Parallel hooks          | All hooks of one event run in parallel, and Claude Code waits for all of them                                                                                       |

Fetching source evidence (git 2.55, 2026-09-23): fetching a few lines of one file from GitHub by tag or full commit, depth 1 with on-demand blobs, takes about 2 seconds; a wrong tag or path fails at once; a missing repository fails within about 2 seconds without a credential prompt; a local remote falls back to a full fetch with the same result.

Without limits, one framing research ran more than 80 web calls and took about 13 minutes; the frame now caps them at 20 in total.

## Manual tests before a release

In a temporary repository with `claude --plugin-dir ./plugins/waypoint`, confirm each item:

### Initialization and sessions

1. Before initialization the reply is "初始设置" (initial setup); after A, `init` writes the state directory and permission rules and the output is committed; B changes nothing. In a repository that is not initialized, writing files is not restricted at all.
2. Before and after accepting the workspace trust dialog, `project-navigator` commands ask for no permission, and they run in both Bash and PowerShell.
3. A new session invoking the skill replies with "恢复进度" (resume progress) and continues from the records; the old session still works.
4. After rewinding a message of the orchestrator in the desktop app and sending another, the orchestrator keeps working and business file writes are still denied.
5. After context compaction, the orchestrator receives a position reminder.
6. After uninstalling, the permission rules are gone, business file writes are no longer denied, and records are kept.
7. Upgrading a project initialized by 0.11.0 with an issued order: old hooks, old permission rules, and `.navigator/bin/` are removed, the order is moved back to drafting, and records are kept; after invoking the skill in the old orchestrator session, the upgrade command runs there.

### Framing and selection

1. Framing a new project: requirement understanding, problem-domain research, research report; with B in the research report the skill skips brainstorming and drafts the brief; with A it brainstorms, diverging then converging.
2. Surveying an existing project, including a run-check order.
3. Standards comparison: the orchestrator gets the bundled standards with `ref standards` and passes them to the reader subagent; at most 3 conflicts per round, choosing the comment language, writing `.claude/rules/engineering.md`.
4. The evidence table of a selection receipt: the executor self-checks with `evidence check`; the reviewer runs `evidence`; a wrong version or path is judged unverified.
5. After the language selection, register the code check commands; before that, creating an implementation order is refused, and afterwards the order skeleton prefills the check criterion.
6. A run-check order rejected before check commands are registered: the next action is a new run-check order in the same slice.
7. An analysis order: the executor can write documents and scripts under `artifacts/`, and its business file writes are denied with a reason pointing to an implementation order.

### Work order round trip

1. "工单审阅" (order review) shows only the review points and the order file path, matching the order file; after B the order is changed and reviewed again; after A it is issued, an executor is dispatched in the background, and the reply is "工单执行" (order running); changing the order file after approval makes the issue fail.
2. While the executor works in the background, the user can keep talking to the orchestrator; when it finishes, the orchestrator runs `status` on its own and starts the review.
3. In the default permission mode, the executor's write prompts appear in the orchestrator session; after switching to Accept edits they stop.
4. The executor is blocked (for example it needs an account): the reply is "受阻处理" (blocked handling); after the user acts, no new review is needed and the original subagent continues through SendMessage.
5. "工单执行" has no option block; replying "停止执行" (stop) during execution: the subagent stops, the order goes back to drafting, and it is reviewed again after changes.
6. The reviewer returns verdicts and evidence and is denied when it tries to write files; it does not run tests the receipt lists as external effects.
7. After a passing review, A commits and B commits and pushes; with unverified criteria the third group is used, and A accepts the order and records risks; with failures a follow-up order is issued, and for an implementation order the orchestrator first judges whether it was too large.
8. The executor's writes to records other than its order's receipt and `artifacts/` are denied; the orchestrator's business file writes are denied.

### Changes, milestone reviews, and anomalies

1. A requirement change, a milestone review (with an automatic checkup), a manual checkup. After A in "项目收尾" (project closing), `finish` runs and its output is committed, then the reply is "项目完成" (project complete) and `git status` is clean.
2. Choosing B in "项目完成" pushes successfully.
3. Asking for a problem report gets a "自由答复" (free answer) reply, and a body with code blocks is not sent back.
4. After rolling the records back with `git reset`, the orchestrator continues from the current records, and replies with "运行受阻" (blocked run) when they do not match reality.
5. A reply without the conclusion line is sent back once and passes the second time.

## Known limitations

- Writing rules rely on prompts and checkups only; replies are not sent back for them, and the script checks are approximate.
- A reply that is sent back stays on screen.
- The guard checks only the target paths of write tools: writing files from the command line or a script, installing dependencies, and running state-changing plugin commands are not checked and rely on the skill's rules. Changes made this way to the state file show up in git.
- The plugin's hooks fire in every project, starting Node.js once more for each write tool call and each message, about 70 ms on a local measurement; in projects that are not initialized the script exits before reading any state.
- Recognizing the orchestrator depends on the marker in the transcript, whose format is internal to Claude Code; when the transcript cannot be read, rule 4 does not apply (the write is allowed).
- The executor subagent belongs to the session that started it; closing that session interrupts its work, and a new session continues according to whether the receipt was written.
- A background subagent's write prompt does not name the subagent; users can infer it only from the "工单执行" (order running) reply and the task list.
- Source evidence supports only public git repositories over https; `evidence` checks only the cited lines, and whether they support the "说明" (note) is still up to the reviewer.
