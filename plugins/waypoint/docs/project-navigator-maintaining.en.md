# project-navigator maintainer guide

English | [简体中文](project-navigator-maintaining.md)

[Back to the user guide](project-navigator.en.md)

This guide is for maintainers: the design overview, design decisions, component map, troubleshooting, change process, tests, and measured behavior. For repository-wide conventions, see [MAINTAINING.en.md](../../../MAINTAINING.en.md).

## Design overview

The skill has three layers, each with one job:

| Layer   | Location                                          | Job                                                                                      |
| ------- | ------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Rules   | `SKILL.md`, `references/`                         | Written for the model: the workflow, the steps, which reply type to use when             |
| Runtime | `runtime/navigator.mjs`, `runtime/hook.mjs`       | Commands change the state and hooks enforce the boundaries; the model cannot bypass them |
| Spec    | `spec/templates.json`, `standards/engineering.md` | The single source of the replies, record files, writing rules, and engineering standards |

In a user's project, the skill uses these locations:

| Location                       | Contents                                                                                     | Committed |
| ------------------------------ | -------------------------------------------------------------------------------------------- | --------- |
| `.navigator/`                  | State file, record files, executor guide, copies of the runtime and reference files (`bin/`) | Yes       |
| `.navigator/drafts/`           | JSON drafts that the orchestrator passes to commands                                         | No        |
| `.claude/settings.json`        | Guard hooks and allow rules                                                                  | Yes       |
| `.claude/settings.local.json`  | Machine-local copy of the allow rules, excluded via `.git/info/exclude`                      | No        |
| `.claude/rules/engineering.md` | Project standards, loaded automatically by every session in the project                      | Yes       |
| `.git/navigator/`              | Executor session registrations, self-check request and heartbeat                             | No        |
| `refs/navigator/snapshots`     | Snapshots of the state directory, outside any branch history                                 | No        |

## Design decisions

Each entry states the decision, the reason, and what breaks if it changes.

### Sessions and boundaries

- **Orchestration and execution run in separate sessions, and reviews run in a subagent.** Planning and implementation each keep a clean context, and reviews are free of the orchestrator's bias. If changed: the orchestrator starts writing code, and planning and implementation mix again.
- **The orchestrator's tools are allow-listed and denied by default.** New tools (such as Monitor, Workflow, or MCP write tools) cannot bypass the limits. If changed: every new tool becomes a loophole.
- **Delegation prompts are generated by the scripts and checked by the guard.** The review prompt is compared verbatim, and the research prompt must start with the fixed frame. If changed: the orchestrator could add biased instructions to the prompts.
- **The orchestrator never uses the question box.** When a question box appears, text earlier in the same reply may not be displayed. If changed: users do not see what the options are based on.
- **Executor sessions work in the repository root, never in a worktree.** A worktree cannot see work orders that are not committed yet. If changed: executors cannot find their work order.

### Installation and configuration

- **Hooks are installed at project level by an explicit `init`, not at plugin level.** Some repositories are not ordinary software projects, so users must opt in. If changed: every project with the plugin installed is restricted.
- **Hooks use the shell-free form** (`"command": "node"`, `"args": ["${CLAUDE_PROJECT_DIR}/..."]`). This avoids quoting differences between Git Bash and PowerShell and paths with spaces. If changed: hooks fail when the path contains spaces or Chinese characters.
- **`SKILL.md` sets `allowed-tools: Bash(node *) PowerShell(node *)` and no `shell` field.** Without it, the `!` command in the skill aborts the whole invocation in the default permission mode, and child sessions may not find Git Bash. This is the only exception to the repository convention of not setting `allowed-tools`. If changed: the skill cannot open in the default mode.
- **Allow rules go into both `settings.json` and `settings.local.json`.** There are two kinds of rules: the plugin commands, and `Edit(.navigator/**)` (measured to cover the Write tool as well). Allow rules in the project's `settings.json` apply only after the user accepts workspace trust and never apply in headless mode; the machine-local file needs no trust. The rules only skip the approval prompt; the guard still decides who may write which file. If changed: every plugin command and every record write asks for approval.
- **Plugin commands are always written as `node .navigator/bin/runtime/navigator.mjs <command>`, with no quotes around the path.** The allow rules match this exact form. If changed: commands ask for approval.
- **`init` copies the reference files into `.navigator/bin/references/`, and `SKILL.md` points to that project copy.** In the default permission mode, reading plugin files outside the project needs user approval. If changed: every reference read asks for approval.
- **The runtime uses only Node.js 22 built-in modules.** Hooks run on users' machines, which cannot be required to install dependencies. If changed: every project needs a dependency install after initialization.

### State and records

- **`state.json` is the single source of state, and hooks never write it.** Writes compare the revision, then write a temporary file and rename it. If changed: concurrent writes overwrite each other or leave half-written files.
- **`spec/templates.json` is the single source of replies, record files, and writing rules.** Stop checks, write checks, skeletons, checkups, and reference documents all read the spec. If changed: documentation and checks drift apart.
- **Replies and record files start from a skeleton, and the scripts compute the current progress.** The model easily miscounts progress or drops sections. If changed: replies are sent back far more often.
- **Rules arrive while the reply is being filled in, and the end-of-reply check is only the backstop.** `reply` prints fill-in requirements before the skeleton, generated from the spec with the same thresholds and word lists as the checks. Executor replies are checked for layout only, so executors get only the layout and summary items. If changed: the model writes replies without seeing the rules, and more replies are sent back.
- **"字" (character count) has one definition** (`lib/text-units.mjs`): each Han character, English word, number, or path counts as 1, while spaces and punctuation do not; sentence length and the human summary share it. Counting raw characters makes the spaces after punctuation and English paths push a summary well past the model's estimate. If changed: human summaries often exceed the limit.
- **A Stop check sends a reply back at most once, and the reason asks to fix only the listed problems.** When `stop_hook_active` is true, the reply passes, avoiding loops; the rewritten reply is not checked again, and rewriting everything tends to introduce new errors. If changed: the model may rewrite the same reply over and over, or bring in new errors while rewriting.
- **A reply starts at the first level-1 heading; a process note before the heading is not sent back, but it cannot contain code blocks or headings.** The model often adds a lead-in sentence before the reply. Sending it back only shows the user the same reply twice, and an executor's "开工对齐" would not be recognized, so choosing A would still leave business files locked. If changed: many replies are sent back, and executors get stuck at alignment.
- **Chinese text reaches commands through JSON drafts under `.navigator/drafts/`.** Child sessions may only have PowerShell, and Windows PowerShell 5.1 garbles Chinese arguments. If changed: Chinese text is garbled, or commands fail on differing heredoc syntax.

### Reconciliation and snapshots

- **Snapshots live in a hidden ref and store raw bytes (`hash-object --no-filters`).** They stay out of branch history, ignore `core.autocrlf` and `.gitattributes`, and restore byte for byte. If changed: restored files get different line endings on Windows.
- **Snapshot commits use a fixed identity, `project-navigator`.** On a machine without a configured Git user name and email, `git commit-tree` fails and snapshots are silently skipped. If changed: reconciliation loses its basis on such machines, including CI.
- **The `lastCommit` committed in a navigator commit equals that commit's parent.** Reconciliation recognizes its own commits this way without extra markers, which is also why `init` records the HEAD at that time. If changed: every navigator commit looks foreign.
- **While a reconciliation anomaly is unresolved, snapshots and most commands pause.** Otherwise the next snapshot would store the anomalous content as normal. If changed: the anomaly is reported once and then silently disappears.

### Execution and commits

- **The launch prompt is generated by the scripts, and the hook registers an executor session by its first line "执行工单 NNNN".** Reading the current work order file is the fallback, and current or former orchestrator sessions are never registered. If changed: executors are not recognized, or an orchestrator is registered as an executor.
- **Every issue of a work order increments its round, and alignment is valid only for that round.** A work order reissued after being blocked has changed, so the plan must be confirmed again. If changed: the executor keeps coding against the old plan.
- **All commits go through `waypoint:commit-message`, and the guard allows `git add`, `git commit -F -`, and `git push` without force flags only during the commit step.** There is one set of commit message rules. If changed: two sets of commit message rules exist.
- **"开工对齐" must include "模块划分" (new modules, changed modules, entry changes).** The code structure is settled before any code is written and is visible before the user chooses A; the end-of-reply check requires the section. If changed: structural problems surface only at review, when rework is expensive.
- **Mechanical modularity checks belong to the project's code check tools; the plugin does not parse code.** Selection picks a check tool with function length and complexity rules enabled, and `codecheck set` registers the check commands. Skeletons of implementation and fix orders prefill a "代码检查通过" (code checks pass) criterion, `order set issued` verifies the criterion text, and the check commands count as authorized tests. When no suitable tool exists, a reason must be registered instead. If changed: modularity relies only on reminders and judgment, and ever-growing functions still pass review.
- **The reviewer subagent lists both Bash and PowerShell.** Child sessions may not find Git Bash; with Bash alone the reviewer cannot run any command, and every criterion that needs a run becomes "unverified". The guard applies the same rules to both. If changed: every review fails in PowerShell-only environments.

## Troubleshooting

| Symptom                                                            | Root cause                                                                                    | Files                                         | How to verify                                                                |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------------- |
| Invoking the skill aborts with a permission check failure          | `allowed-tools` was removed or changed                                                        | `SKILL.md`                                    | Invoke it once in the default permission mode                                |
| The self-check fails                                               | The session did not load the new hooks, or a global setting disables hooks                    | `commands/init.mjs`, `lib/settings.mjs`       | Restart the session and check again; drive `hook.mjs` through standard input |
| Plugin commands ask for approval                                   | The command form differs from the allow rules, or the machine-local file is missing           | `lib/settings.mjs`, `lib/guard-commands.mjs`  | Compare the rules in `.claude/settings.local.json` with the command          |
| Replies keep being sent back                                       | The reply ignored the skeleton, or the spec and the reference files disagree                  | `lib/reply-checks.mjs`, `spec/templates.json` | Fill a skeleton from `reply` and check it; run `npm test`                    |
| After pasting the launch prompt, the session is still "other"      | The first line was edited, the order is not issued, or the session was an orchestrator        | `lib/executors.mjs`, `lib/briefs.mjs`         | Inspect `.git/navigator/sessions/<session id>.json`                          |
| The user chose A, but the executor still cannot edit files         | "开工对齐" failed the format check, or the order was reissued and the round changed           | `runtime/hook.mjs`, `lib/executors.mjs`       | Check `isAwaitingAlignment` and `alignedRound` in the registration           |
| Every invocation reports that the records differ from the snapshot | Something rewrote `.navigator/` after the snapshot, and the end-of-reply snapshot did not run | `runtime/hook.mjs`, `lib/snapshots.mjs`       | Check the latest snapshots with `git log refs/navigator/snapshots`           |
| Every command reports an unresolved anomaly                        | `state.json` contains `pendingAnomaly`                                                        | `commands/support.mjs`, `commands/enter.mjs`  | Follow the anomaly flow and run `adopt` or `restore`                         |
| Issuing an implementation order is denied, mentioning code checks  | No check commands are registered, or the criteria lack the exact code check criterion         | `lib/code-checks.mjs`, `commands/order.mjs`   | Check `codeChecks` in `state.json`; fetch `template order` again             |
| After upgrading the plugin, the project behaves the same           | `version` in `plugin.json` was not bumped, so the project copy never asks to upgrade          | `lib/version.mjs`                             | Compare `.navigator/bin/runtime-version.json` with the plugin version        |
| Dispatching the reviewer subagent is denied                        | The prompt is not the verbatim output of `review-brief`                                       | `lib/guard.mjs`                               | Run `review-brief` again and paste it unchanged                              |

## Measured behavior

Measured on Claude Code 2.1.280, Node.js 24.21.0, and Windows 10 (2026-09-23), with a project path containing spaces and Chinese characters:

| Point                     | Result                                                                                                                                                      |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `!` commands in a skill   | Without `allowed-tools`, the whole invocation aborts in the default mode; `${CLAUDE_SESSION_ID}` equals the hook's `session_id`; no PreToolUse is triggered |
| The skill `shell` field   | When a child session cannot find Git Bash, a skill with `shell: bash` fails outright                                                                        |
| Subagent identity         | Hook input in a subagent carries the main `session_id`, plus `agent_id` and `agent_type`; plugin subagent `tools` limits apply                              |
| Sending a reply back      | A top-level `{"decision": "block"}` works, and the second Stop has `stop_hook_active` set to true                                                           |
| Denials in bypass mode    | PreToolUse `permissionDecision: "deny"` still applies                                                                                                       |
| Context injection         | The model reads `additionalContext` returned by UserPromptSubmit; slash commands trigger the event too                                                      |
| Settings take effect live | Hooks written to the project `settings.json` mid-session apply immediately                                                                                  |
| Session name              | The first line of the ListAgents output is the session's name                                                                                               |
| Allow rules               | Allow rules in the project `settings.json` need workspace trust and never apply in headless mode; `settings.local.json` needs no trust                      |

Additional findings from smoke tests (`claude -p`, default permission mode):

- Reading the plugin's reference files outside the project, and writing files under `.navigator/`, both need user approval. Copying the references and the `Edit(.navigator/**)` allow rule solve these.
- An `Edit(...)` allow rule also covers the Write tool.
- Without a scope limit in the research frame, one framing research took more than 80 web calls and about 13 minutes; the frame now limits it to 20 calls in total.

Still to be tested interactively: whether leaving plan mode in bypass mode shows a prompt, the session identity of Agent Team members, and whether a new turn opened by a cross-session message triggers UserPromptSubmit. The design no longer depends on the first two, and Agent Teams are disabled in the orchestrator session by default.

## Pre-release manual tests

In a temporary repository with `claude --plugin-dir ./plugins/waypoint`, confirm each item:

### Setup and sessions

1. Before initialization, the reply is "初始设置"; A completes the self-check, and B changes nothing.
2. Plugin commands ask for no approval, both before and after accepting the workspace trust dialog.
3. A new session resumes progress, and the previous orchestrator can no longer write records.
4. After context compaction, the orchestrator receives the position reminder.
5. Uninstalling removes the hooks and allow rules and keeps the records.

### Framing and selection

1. Framing a new project: requirement understanding, problem-domain research, the research report, divergent and convergent brainstorming, and the project brief.
2. Surveying an existing project, including the run-check work order.
3. Standards comparison: at most three conflicts per round, the comment language, and writing `.claude/rules/engineering.md`.
4. When a selection receipt lacks source evidence, the reviewer subagent marks it unverified.
5. After the language selection, register the code check commands; before registration, issuing an implementation order is denied; after it, order skeletons prefill the check criterion and the reviewer subagent can run the check commands.

### Work order round trip

1. One work order round trip each with a document report and a message report.
2. After a blocked order is revised and reissued, the executor must align again.
3. The executor is denied when editing business files before the user chooses A, and when committing; "开工对齐" includes "模块划分", and a reply without it is sent back.
4. Tests with external effects are preceded by "测试授权".
5. The reviewer subagent returns conclusions with evidence, and is denied when it tries to write a file.
6. One accepted and one rejected review; two rejections in a row on the same slice suggest splitting it.
7. All three commit options go through `commit-message`, and reconciliation is consistent afterwards.

### Changes, reviews, and anomalies

1. A requirement change, a milestone review (with the automatic checkup), and a manual checkup.
2. A `git reset` rollback, a squash merge, and a hand-edited record file each lead to the matching anomaly.
3. The orchestrator is denied when writing code, installing dependencies, or using the question box.
4. A reply with a format violation is sent back once and passes the second time.

## Known limitations

- The semantic writing rules (invented abbreviations, metaphors, unclear references) rely on prompts, checkups, and the banned-word lists; the script checks are approximations.
- When a reply is sent back, the faulty version stays on the screen.
- Writes made through shell commands are checked only roughly from the command text; for example, a file written from a scripting language is not detected.
- The hooks do not restrict the user; hand edits to record files are caught by reconciliation.
- Every tool call starts Node.js once more, about 70 milliseconds in local measurements, and only in initialized projects.
