[English](project-navigator-maintaining.en.md) | 简体中文

本文面向维护者: 设计总览, 设计决策, 组件地图, 排查手册, 修改流程, 测试与实测结论. 仓库级的维护约定见 [MAINTAINING.md](../../../MAINTAINING.md).

## 设计总览

技能由三层组成, 每层只做一件事:

| 层       | 位置                                              | 职责                                         |
| -------- | ------------------------------------------------- | -------------------------------------------- |
| 规则     | `SKILL.md`, `references/`, `guide/executor.md`    | 写给模型: 流程, 步骤, 何时回复哪种类型       |
| 运行脚本 | `runtime/navigator.mjs`, `runtime/hook.mjs`       | 命令修改状态, hook 守几条写入边界与回复结构  |
| 规格     | `spec/templates.json`, `standards/engineering.md` | 回复, 记录文件, 写作规则与工程规范的唯一来源 |

插件层面的接线:

| 位置                        | 内容                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------ |
| `hooks/hooks.json`          | 四个事件 (PreToolUse 只匹配写入类工具, UserPromptSubmit, SessionStart, Stop) 都调用 `runtime/hook.mjs` |
| `bin/project-navigator`     | Bash 工具中的命令入口, `exec node .../navigator.mjs "$@"`                                              |
| `bin/project-navigator.cmd` | PowerShell 工具中的命令入口                                                                            |
| `agents/navigator-*.md`     | 执行, 验收, 调研与阅读子代理                                                                           |

在用户项目中, 技能会用到以下位置:

| 位置                           | 内容                                                             | 是否入库 |
| ------------------------------ | ---------------------------------------------------------------- | -------- |
| `.navigator/`                  | 状态文件, 计划记录, 工单文件夹                                   | 入库     |
| `.navigator/drafts/`           | 编排会话传给命令的 JSON 草稿                                     | 不入库   |
| `.claude/settings.json`        | 放行规则                                                         | 入库     |
| `.claude/settings.local.json`  | 放行规则的本机副本, 由 `.git/info/exclude` 排除                  | 不入库   |
| `.claude/rules/engineering.md` | 项目规范, 项目内所有会话自动加载                                 | 入库     |
| `.git/navigator/`              | 工单审阅记录 (`order-approval.json`), 源码证据缓存 (`evidence/`) | 不入库   |

## 设计决策

每条写明决定, 原因, 以及改掉会怎样.

### 会话与执行

- **编排会话与执行分开, 执行用后台子代理.** 编排会话用 Agent 工具在后台 (`run_in_background`) 派 `waypoint:navigator-executor`, 提示词是 `exec-brief` 的输出; 子代理结束时编排会话收到通知, 自动接着处理. 0.x 让用户另开执行会话: 一张工单要切换会话, 粘贴启动提示词, 确认开工对齐, 选汇报方式, 回编排会话确认回执, 用户约做 7 次选择. 子代理的代价是工作期间不能向用户提问, 所以开工对齐取消, 需要用户决定的事以受阻结束; 模块划分写进回执, 由验收子代理核对. 改掉的后果: 回到多会话往返, 或让编排会话自己写代码, 规划与实现重新混在一起.
- **不保留 "手动开执行会话" 的备选.** 只要保留, 启动提示词登记, 开工对齐, 分叉认领, 编排地址这一整套机制就删不掉, 而这套机制是 0.x 排查手册中大部分条目的来源. 超大的任务拆成多张工单. 改掉的后果: 两套执行方式并存, 守卫与提醒都要分两路.
- **编排会话不做登记, 按转录中的编排标记认出.** `enter` 的输出带 "编排标记: project-navigator 编排标记 <编号>", 编号是项目路径 SHA-256 的前 12 位 (Windows 上先转小写); 输出注入技能内容, 技能内容记在会话转录中, hook 读 `transcript_path` 找这个标记. 源代码里只有前缀, 读源代码的会话不会被误认; status 不输出标记, 子代理运行 status 不影响主会话. 分叉出的会话复制了转录, 自然带着标记, 回退与编辑消息之后不需要任何处理. 0.x 把身份登记在 `.git/navigator/orchestrator.json`, 为此有接管, 被接管, 分叉认领, 重新登记一系列规则. 改掉的后果: 回到登记与认领, 每次换编号都可能误判身份.
- **受阻后工单没有改动时直接继续, 由原执行子代理接着做.** `order set issued` 记下发布时工单文件的摘要 (`issuedDigest`); 受阻工单的文件与摘要一致时不要求重新审阅, 输出要求用 SendMessage 让原子代理继续 (实测 SendMessage 能带着上下文续接已结束的子代理), 找不到时重新派出. 工单改过就要重新审阅. 改掉的后果: 用户完成一个小操作也要重新审阅一次, 或子代理每次从头再来.
- **执行子代理不写 `tools`, 继承会话的全部工具.** 它要写代码, 运行构建与测试, 用户装的 MCP 工具也可能用到. 插件子代理不支持 `hooks`, `mcpServers`, `permissionMode` 字段 (官方文档), 写入范围由插件级 hook 的守卫限制. 改掉的后果: 列出 `tools` 时漏掉用户的工具.
- **委派提示词由脚本生成, 编排会话原样使用, 守卫不核对.** `exec-brief`, `review-brief`, `research-brief` 是提示词的唯一来源. 0.x 守卫逐字核对验收提示词, 偶尔因空白差异拒绝派出. 改掉的后果: 提示词散落在规则文件里, 版本之间不一致.

### 守卫与回复校验

- **守卫只看写入类工具的目标路径, 四条规则.** 状态文件与生成的视图谁都不能直接写; 验收子代理不写文件; 执行子代理在 `.navigator/` 下只写当前工单的回执与 `artifacts/`, 只产出记录的工单不写业务文件, 工单不在执行中时不写业务文件; 编排会话只写 `.navigator/`. 子代理按 hook 输入的 `agent_type` 区分 (`waypoint:navigator-executor` 等, 实测插件子代理的值为 "<插件>:<名称>"). 0.x 还解析 Bash 命令文字, 按白名单放行编排会话的工具, 核对提示词, 记录文件结构, 用户测试输出与 `.claude/settings.json` 的改动; 这些规则多数为跨会话场景与历次事故补上, 也是拒绝与误判的主要来源. 改掉的后果: 加回去的每条规则都会在某个正常操作上误伤.
- **保留 "编排会话不写业务文件".** 目的不是防恶意, 是防角色坍塌: 用户一句 "顺手改一下", 模型就会自己写代码, 编排会话的上下文从此混乱. 只在主会话写项目内 `.navigator/` 之外的文件时才读转录判断身份. 改掉的后果: 编排会话逐渐变成执行会话.
- **Stop 只校验回复结构: 标题是回复类型, 标题下第一行是结论, 恰好一个与规格一致的选项块, 代码块都关闭, 没有占位标记.** 标题用来识别回复类型, 选项块用来识别用户的选择 (工单审阅的认可依赖它), 这两项不能放松. 规格中 `optionSets` 为空的回复 ("工单执行", "工单验收" 与等待调研, 阅读子代理的 "等待结果") 不需要用户选择, 不带选项块, 带了会被打回: 1.0.0 与 1.1.0 的 "工单执行" 有 "等待完成" 选项, 用户以为要先选 A 才开始等待. 节, 键名, 进展值与写作规则只在填写要求中提醒. 0.x 按写作规则与总结字数打回, 打回后屏幕上留着两遍回复. 打回最多一次 (`stop_hook_active` 时放行). 有后台任务时照常校验: 1.2.1 及之前不校验, 验收子代理在后台时模型写了一段没有标题的说明, 与前后的回复混在一起; 现在等待子代理的两种情况都有回复类型. 进展行的工单编号之后写环节 (`format.orderStages`, "验收报告" 用 `orderStage` 写 "待你决定"), 连续几条回复靠它区分. 建议只写在 "验收报告" 的 "处理建议" 一节, 填写要求写明各节之外不加文字. 改掉的后果: 写作规则重新变成频繁打回.
- **两个选项的组同时做成按钮, 选项块照常保留.** Claude 桌面应用有一个填写 "下一步框" 的工具 (`mcp__ccd_turn__wrap_up`, 见 `lib/reply-guide.mjs` 的 `BUTTON_TOOL`), 最多 2 个按钮, 点按钮等于把按钮文字作为回复发出. `reply` 的填写要求给出 "按钮" 一条, 按钮文字是选项的第一个分句 (`choiceLead`), 与打字回复走同一条识别 (`isChoiceSelected`). 三项以上的组, 以及规格中写了 `"buttons": false` 的组 (选择后还要打字补充, 或选了就会提交: 应用规定提交不能用回复按钮) 不做按钮. 选项块不能因为有按钮而去掉: 框可以被关掉, 不留在对话记录中, Stop 的校验与工单审阅的认可都读选项块. 这个工具是应用内部的, 没有公开约定, hook 也不核对是否调用; 工具改名或消失时退回只有选项块, 不会出错. 改掉的后果: 去掉选项块, 其它环境与关掉框的用户看不到选项.
- **回复以一行结论开头, 删掉末尾的人类总结块.** 读者注意力有限, 结论放在最前面才看得到; 末尾的总结与结论重复. 结论字数只作提醒 (`conclusionMaxLength`). 进展从四行压成一行. 改掉的后果: 关键信息落到回复末尾.
- **记录文件写入时不校验结构, 写完用 `check <文件>` 自查.** 读记录的脚本 (审阅要点预填, 回执的执行状态, 验收记录的判据结论) 按键值行与表格读取, 读不到时命令给出明确原因. `check` 带文件时不分配体检编号, 不写状态, 执行子代理也能用. 改掉的后果: 写入被拦下的次数回到 0.x 的水平.

### 工单与验收

- **一张工单只要用户做两次决定: 工单审阅中发布, 验收报告中通过并提交.** 审阅卡片只列 "审阅要点" (任务目标, 需要决定, 明确不做, 粒度依据) 与工单文件路径, 由 `reply approve` 从工单文件预填. 认可仍按工单文件的摘要绑定 (hook 在回复工单审阅时记下摘要, 用户回答时记下选择), 展示的内容变短不影响绑定. 0.x 原样摘录工单五节, 用户三秒内读不完, 而且多数细节用户判断不了. 改掉的后果: 审阅变成走过场, 或用户每张工单都要读完整工单.
- **测试授权去掉.** 执行子代理不运行有外部影响的测试, 写进回执 "测试记录" 的 "外部影响"; 验收子代理运行代码检查与回执中其它测试命令, 不重跑外部影响的命令, 按回执输出判断. MCP 取证工具不再登记, 验收子代理按回执 "取证记录" 做只读查询, 约束写在提示词与子代理定义中. 改掉的后果: 每张带外部测试的工单多一次用户选择.
- **未验证的判据可以由用户明确接受.** "验收报告" 第 3 组 (只有未验证, 没有不通过) 由用户选择接受现状并提交, 对应 `order set accepted --accept-unverified`, 未验证的判据登记为风险. 0.x 一律判不通过, 依赖外部取证的判据反复被拒. 不通过的判据仍然不能接受. 改掉的后果: 外部条件不足时工单无法收敛.
- **提交不是工单状态.** 工单状态为 drafting, issued, blocked, reviewing, accepted, rejected, voided; `order set accepted` 之后编排会话按输出调用 commit-message, 状态文件随这次提交入库. 0.x 有 committing 与提交结算记录, 用来对上 `lastCommit`; 去掉对账之后不再需要. 读取旧状态时, accepted 与 committing 的工单视为已通过并结束. 改掉的后果: 每次提交后状态文件留在工作区.
- **工单粒度按四条上限判断, 不按判据条数.** 执行一次能做完, 验收能看清, 做完能运行, 高风险部分单独成工单; 在此之内工单越大越好, 默认一个切片一张, "粒度依据" 写出判断. 0.x 规定判据不超过 5 条, 结果判据越写越密; 连续不通过只会拆小. 现在不通过时先判断原因. 改掉的后果: 工单越拆越细, 用户确认次数随之增加.
- **会改动代码的工单在新建时就核对检查命令已登记 (`creationBlocker`), 发布前仍再核对一次.** 运行检查与分析工单只产出记录, 不需要检查命令, 被拒后重发同类工单. 选型工单被否决时新建选型工单, 不发修复工单: 修复工单要求已登记检查命令, 而检查命令在选型采用后才登记. 改掉的后果: 检查命令登记之前被拒的工单无法继续.
- **检查命令的检查范围排除 `.navigator/` 与 `.claude/`.** 有的格式化工具默认也处理 Markdown, 会把编排记录纳入检查. 改掉的后果: 编排记录的格式让每张实现工单的检查判据都通不过.
- **选型只回答 "库能不能实现每条需求", 一轮验收完, 由用户决定是否采用.** 证据表由 `evidence` 命令从原仓库按版本取回被引用的行核对 (只接受 https 地址, git 不读凭据). 编排会话可以给出技术建议, 只有关键依赖发选型工单, 次要的库由执行子代理在实现工单中选定. 改掉的后果: 每个小依赖都要一张工单, 或关键依赖没有证据.

### 安装与升级

- **hook 放在插件级, 未初始化的项目中立即结束.** `hooks.json` 用不经过 shell 的写法 (`"command": "node"`, `"args": ["${CLAUDE_PLUGIN_ROOT}/..."]`), 实测在含空格与中文的路径下正常. `hook.mjs` 第一步检查项目中有没有 `.navigator/state.json`, 没有就结束; 项目标为已卸载时也结束. 0.x 由 init 把 hook 写进项目配置, 并把运行脚本复制进 `.navigator/bin/`: 每个项目入库约 60 个脚本, 插件更新后要用户手动升级, 还出现过副本不能升级自己的问题. 代价是装了插件的所有项目中, 每次写入类工具调用与每条消息都启动一次 Node. 改掉的后果: 回到复制脚本与手动升级.
- **命令经插件 `bin/` 调用, 写成 `project-navigator <命令>`.** 官方文档: 插件 `bin/` 中的文件在 Bash 工具的 PATH 中; 实测 PowerShell 工具运行同名的 `.cmd`. 命令名用完整的 `project-navigator`, 避免与用户 PATH 中的工具重名 (插件目录排在用户 PATH 之后, 重名时用户的工具优先). `bin/project-navigator` 在仓库中要有可执行位. 技能加载时的 `enter` 仍用 `node "${CLAUDE_SKILL_DIR}/runtime/navigator.mjs"`, 因为 `!` 命令的 PATH 没有文档保证. 改掉的后果: 命令依赖项目中的副本路径.
- **参考文件与执行手册由 `ref <名称>` 输出.** 默认权限模式下, 用 Read 读取项目之外的插件文件需要用户批准; 放行规则覆盖插件命令, 输出内容不弹确认, 也总是当前版本. 改掉的后果: 要么复制进项目, 要么每读一次都弹确认.
- **放行规则同时写进 `settings.json` 与 `settings.local.json`, 不放行宽泛的写入.** 规则是 `Bash(project-navigator *)`, `PowerShell(project-navigator *)` 与 `Edit(.navigator/**)`. 项目 `settings.json` 中的规则要等用户接受工作区信任后才生效, 无头模式不生效; 本机文件不需要信任. 执行子代理写业务文件的确认按用户的权限模式处理: 实测后台子代理的写入确认弹在主会话中 (不写明是子代理), 选 "Always allow" 会把会话切到 Accept edits. 所以 init 不加 `Edit(**)`, 使用说明建议执行期间切到 Accept edits. `SKILL.md` 的 `allowed-tools` 另外放行 node 与 `project-navigator` 命令, 只在调用技能的那一轮有效, 用于初始化. 改掉的后果: 宽泛的放行规则让整个项目的编辑都不再确认.
- **从 0.x 升级由 init 完成, 进入时先删旧的编排登记.** init 移除项目级 hook 与旧放行规则, 删除 `.navigator/bin/` 与 `.navigator/guide/`, 清理 `.git/navigator/` 中的旧文件与 `refs/navigator/snapshots`, 已发布但没有回执的工单撤回为起草中. 升级之前旧的项目级 hook 仍会运行, 它按 `orchestrator.json` 判断编排会话并按白名单拦下命令; 所以 `enter` 发现旧版本安装时先删掉这个文件, 旧 hook 把会话当成其它会话, 不再拦下 `project-navigator init`. 改掉的后果: 旧编排会话中运行升级命令被旧守卫拒绝.
- **`.navigator/` 除草稿外全部入库, 进入与初始化时检查忽略规则.** `.navigator/.gitignore` 重新纳入各级目录与插件写的文件类型以及工单 `artifacts/` 下的全部文件, 最后排除 `drafts/`. init 与每次进入用 `git check-ignore --no-index` 检查必须入库的路径 (状态文件, 术语表, 每种记录文件的示例位置, `.claude/settings.json` 与 `engineering.md`); 上级规则忽略了它们时停下并报告是哪条规则. 改掉的后果: 换机器或 clone 之后记录不全.
- **技能产物的提交是命令输出中的一步, 不是回复类型.** init, 推进阶段与确认收尾的输出在有未入库的技能产物时写出调用 commit-message 的参数 (只提交 `.navigator/` 与插件管理的配置, 其它改动由 commit-message 询问); 确认收尾把状态文件算进去, 因为完成标记之后没有别的提交能带上它. 0.x 有 "阶段提交" 回复与 `stagecommit` 命令, 每个阶段多一次三选一. 改掉的后果: 每推进一个阶段多一次用户选择.
- **运行脚本只用 Node.js 22 内置模块.** hook 在用户机器上运行, 不能要求安装依赖.

### 状态与记录

- **`state.json` 是状态的唯一来源, 只由插件命令写入.** 写入比较版本号, 先写临时文件再改名; 读取时迁移旧结构 (结构版本 5 去掉会话登记, `lastCommit`, `stageCommit`, `pendingAnomaly`, `evidenceTools` 与工单的 `authorizedTests`). 守卫拒绝用写入类工具直接改它. 改掉的后果: 并发写入互相覆盖, 或模型手改状态.
- **删除快照与对账.** `.navigator/` 已经在 Git 中, 回退与手工改动用 git 就能看到. 0.x 的快照, 待并入写入, 对账与 "验收异常" 用来防手工改记录, 却让每次 `git reset` 或格式化 hook 都可能卡住流程. 现在回退之后按当前记录继续, 与实际情况对不上时编排会话回复 "运行受阻" 请用户决定. 改掉的后果: 回到每次回退都要处理验收异常.
- **`spec/templates.json` 是回复, 记录文件与写作规则的唯一来源.** 回复校验, 骨架生成, 体检与参考文档都从规格读取. 改掉的后果: 文档与校验逐渐不一致.
- **回复与记录文件先取骨架再填写, 进展由脚本计算.** 模型容易数错进度或漏写节.
- **"字" 只有一种算法** (`lib/text-units.mjs`): 汉字, 英文单词, 数字, 路径各算 1 字, 空格与标点不算, 句长与结论字数共用.
- **中文内容用 `.navigator/drafts/` 下的 JSON 草稿传给命令.** Windows PowerShell 5.1 传中文参数会乱码.

### 技能异常与问题报告

- **脚本只记自己能确定的迹象, 不判断原因.** 四种迹象: 命令或 hook 抛出内部错误 (不是 `WorkflowError`, 也不是参数写错); `status` 自检发现状态不自洽; 上一次 "下一动作" 写明的命令被流程规则拒绝; 状态版本不变时同一个 "下一动作" 连续给出 4 次 (等执行子代理期间不计数). 流程规则的正常拒绝不记. 改掉的后果: 每次操作失误都生成报告, 或技能的问题被模型换写法绕开, 维护者看不到.
- **异常记在 `.git/navigator/`, 报告写在 `.navigator/drafts/reports/`.** 两处都不入库: 记录是本机运行期的事, 报告是交给维护者的, 不属于项目记录. 相同的未上报异常只记一次, 最多保留 30 条; 写进报告后标为已上报, 同一个问题不重复上报.
- **报告只写遇到的情况.** 脚本填环境, 状态摘要与异常记录, 模型在草稿中填经过 (当时在做, 预期, 实际, 复现); 不写原因推测与处理建议. 修不修, 怎么修由维护者判断, 模型的推测容易把排查带偏. 报告不含工单正文与业务代码, 项目与技能目录的路径替换成占位写法. 改掉的后果: 报告泄露项目内容, 或混入没有依据的结论.
- **只有无法继续时才暂停.** 命令内部错误与状态不自洽, 或草稿写了 `"blocked": true` 时, "问题报告" 用第 2 组选项, 等修复后再继续; 其余情况用第 1 组, 记录后继续推进. 状态不自洽时 `status` 的下一动作直接改为上报.
- **记录失败不影响命令与 hook.** hook 出错仍然放行, 只多记一条异常, 下次用户发消息时提醒编排会话上报; `report` 在状态文件损坏时也能运行.

## 实测结论

### 1.0.0 的设计依据 (Claude Code 2.1.321, Windows 10, 2026-11-10)

用只含 hook, `bin/` 与一个子代理的探针插件在 `claude -p --plugin-dir` 中实测, 路径含空格与中文:

| 待验证点             | 结论                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 插件级 hook          | `hooks.json` 的 exec 写法与 shell 写法都触发, `${CLAUDE_PLUGIN_ROOT}` 展开正常                                            |
| 子代理身份           | 插件子代理的 PreToolUse 输入带 `agent_id` 与 `agent_type: "<插件>:<名称>"`                                                |
| 转录                 | PreToolUse 输入带 `transcript_path`; 第一次工具调用时转录已含本轮的标记; 约 0.5 MB 的转录扫描 1 至 2 毫秒                 |
| 插件 `bin/`          | Bash 工具能直接运行无扩展名的脚本 (Git Bash), PowerShell 工具运行同名的 `.cmd`                                            |
| 后台子代理           | 无头模式会等后台子代理结束并处理结果; 桌面应用中, 后台子代理的完成通知会自动唤醒主会话                                    |
| 子代理续接           | SendMessage 能让已结束的子代理带着原上下文继续                                                                            |
| 子代理的写入权限     | 无头模式下没有放行规则时写入被拒; 裸 `Edit` 规则没有放行 Write, `Edit(**)` 放行前台与后台子代理的写入                     |
| 桌面应用默认权限模式 | 后台子代理的写入确认弹在主会话 ("Allow Claude to write x.txt?", 不写明是子代理); "Always allow" 会把会话切到 Accept edits |

官方文档 (2026-11-10): 插件 `bin/` 在 Bash 工具的 PATH 中, 排在用户 PATH 之后; 插件子代理不支持 `hooks`, `mcpServers`, `permissionMode`; 技能的 `allowed-tools` 只在调用技能的那一轮有效.

### 更早的结论 (Claude Code 2.1.280 至 2.1.284)

| 待验证点            | 结论                                                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 技能中的 `!` 命令   | 不设 `allowed-tools` 时默认模式下整个调用中止; `${CLAUDE_SESSION_ID}` 与 hook 的 `session_id` 一致; 不触发 PreToolUse       |
| 技能的 `shell` 字段 | 子会话中找不到 Git Bash 时, `shell: bash` 的技能直接报错                                                                    |
| Stop 打回           | 顶层 `{"decision": "block"}` 生效, 第二次 Stop 的 `stop_hook_active` 为 true                                                |
| bypass 模式下的拒绝 | PreToolUse 的 `permissionDecision: "deny"` 仍然生效                                                                         |
| 上下文注入          | UserPromptSubmit 返回的 `additionalContext` 模型能读到; 斜杠命令也触发该事件                                                |
| 放行规则            | 项目 `settings.json` 的放行规则需要工作区信任, 无头模式不生效; `settings.local.json` 不需要; `Edit(...)` 规则同时覆盖 Write |
| 会话分叉            | `--fork-session` 与桌面应用中回退, 中断后重发都会换会话编号, 分叉出的转录复制了原会话的历史                                 |
| 并行 hook           | 同一事件的全部 hook 并行运行, Claude Code 等它们全部结束后再继续                                                            |

源码证据的获取 (git 2.55, 2026-09-23): 按 tag 或完整提交号从 GitHub 取一个文件的若干行, 深度为 1 且文件按需下载, 约 2 秒; tag 或路径写错时直接报错; 仓库不存在时约 2 秒内失败, 不弹凭据窗口; 远端是本机路径时改为完整获取, 结果相同.

调研框架不设范围时, 一次立项调研超过 80 次网络调用, 耗时约 13 分钟; 框架现在限制为合计 20 次.

## 发版前手动测试

在临时仓库中用 `claude --plugin-dir ./plugins/waypoint` 逐项确认:

### 初始化与会话

1. 未初始化时回复 "初始设置"; 选 A 后 init 写入状态目录与放行规则, 按输出提交; 选 B 不做任何修改. 没有初始化的仓库中写文件不受任何限制.
2. 接受工作区信任对话框之前与之后, `project-navigator` 命令都不弹权限确认; Bash 与 PowerShell 中都能运行.
3. 新会话调用技能, 回复 "恢复进度" 并按记录继续; 原会话照常可用.
4. 在桌面应用中回退编排会话的一条消息后再发消息, 编排会话照常工作, 写业务文件仍被拒.
5. 上下文压缩后, 编排会话收到位置提醒.
6. 卸载后放行规则被移除, 写业务文件不再被拒, 记录保留.
7. 用 0.11.0 初始化, 有一张已发布工单的项目升级: 旧 hook, 旧放行规则与 `.navigator/bin/` 被移除, 工单撤回为起草中, 记录保留; 在原来的旧编排会话中调用技能后能运行升级命令.

### 立项与选型

1. 新建项目的立项: 需求理解, 问题域调研, 调研报告; 调研报告选 B 时跳过头脑风暴直接写简报草稿; 选 A 时头脑风暴的发散与收敛.
2. 已有项目的盘点, 含运行检查工单.
3. 规范对照: 编排会话用 `ref standards` 取得默认包交给阅读子代理; 矛盾条目每轮不超过 3 条, 选定注释语言, 写入 `.claude/rules/engineering.md`.
4. 选型回执的证据表: 执行子代理用 `evidence check` 自查; 验收子代理运行 `evidence` 核对; 版本或路径写错时判为未验证.
5. 语言选型后登记代码检查命令; 登记之前新建实现工单被拒, 登记之后工单骨架预填检查判据.
6. 登记检查命令之前, 运行检查工单验收不通过: 下一动作是在同一切片新建运行检查工单.
7. 分析工单: 执行子代理能写 `artifacts/` 下的文档与脚本, 写业务文件被拒, 理由指向实现工单.

### 工单往返

1. "工单审阅" 只有审阅要点与工单文件路径, 与工单文件一致; 选 B 后修改再审阅; 选 A 后发布并在后台派出执行子代理, 回复 "工单执行"; 认可之后改工单文件, 发布被拒.
2. 执行子代理在后台工作时, 能继续与编排会话对话; 子代理结束后编排会话自动运行 status 并进入验收.
3. 默认权限模式下, 执行子代理的写入确认弹在编排会话中; 切到 Accept edits 后不再弹出.
4. 执行子代理受阻 (例如需要用户提供账号): 回复 "受阻处理"; 用户完成操作后不需要重新审阅, 原子代理用 SendMessage 继续.
5. "工单执行" 没有选项块; 执行期间回复 "停止执行": 子代理停止, 工单撤回为起草中, 修改后重新审阅.
6. 验收子代理交回结论与证据, 它尝试写文件时被拒绝; 回执中列为外部影响的测试它不运行.
7. 验收通过选 A 提交, 选 B 提交并推送; 有未验证判据时用第 3 组, 选 A 后工单通过并登记风险; 有不通过时补正, 实现工单先判断是否太大.
8. 执行子代理写本工单回执与 `artifacts/` 之外的编排记录被拒; 编排会话写业务文件被拒.

### 变更, 复查与异常

1. 需求变更, 里程复查 (含自动体检), 手动体检. "项目收尾" 选 A 后运行 `finish`, 按输出提交, 之后回复 "项目完成", `git status` 干净.
2. "项目完成" 选 B 时编排会话推送成功.
3. 用户要求写一份问题报告, 编排会话回复 "自由答复", 正文含代码块也不被打回.
4. `git reset` 回退记录后, 编排会话按当前记录继续; 对不上时回复 "运行受阻".
5. 回复缺少结论行被打回一次, 第二次放行.

## 已知限制

- 写作规则只靠提示词与体检, 回复结束时不打回; 脚本检查是近似的.
- 打回时不合格的回复仍留在屏幕上.
- 守卫只检查写入类工具的目标路径: 用命令行或脚本语言写文件, 安装依赖, 运行改变编排状态的插件命令都不检查, 只靠技能规则. 状态文件被这样改动时, 由 git 看到.
- 插件的 hook 在所有项目中触发, 每次写入类工具调用与每条消息多启动一次 Node.js, 本机实测约 70 毫秒; 未初始化的项目中脚本在读取状态文件之前结束.
- 编排会话的认定依赖转录中的标记, 转录格式是 Claude Code 的内部格式; 读不到转录时规则 4 不生效 (放行).
- 执行子代理属于启动它的会话, 会话关闭后子代理的工作中断; 新会话按回执是否写入继续.
- 后台子代理的写入确认不写明是子代理, 用户只能从 "工单执行" 回复与任务列表推断.
- 源码证据只支持公开 git 仓库的 https 地址; `evidence` 只核对被引用的行, 这些行是否真能支持 "说明" 仍由验收子代理判断.
