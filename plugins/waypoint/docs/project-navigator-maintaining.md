## 设计总览

技能由三层组成, 每层只做一件事:

| 层       | 位置                                              | 职责                                         |
| -------- | ------------------------------------------------- | -------------------------------------------- |
| 规则     | `SKILL.md`, `references/`                         | 写给模型: 流程, 步骤, 何时回复哪种类型       |
| 运行脚本 | `runtime/navigator.mjs`, `runtime/hook.mjs`       | 命令行修改状态, hook 执行边界; 模型无法绕过  |
| 规格     | `spec/templates.json`, `standards/engineering.md` | 回复, 记录文件, 写作规则与工程规范的唯一来源 |

在用户项目中, 技能会用到以下位置:

| 位置                           | 内容                                                                                                                                                                                                                                                                     | 是否入库 |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------- |
| `.navigator/`                  | 状态文件, 记录文件, 执行手册, 运行脚本与参考文件的副本 (`bin/`)                                                                                                                                                                                                          | 入库     |
| `.navigator/drafts/`           | 编排会话传给命令的 JSON 草稿                                                                                                                                                                                                                                             | 不入库   |
| `.claude/settings.json`        | 防护 hook 与放行规则                                                                                                                                                                                                                                                     | 入库     |
| `.claude/settings.local.json`  | 放行规则的本机副本, 由 `.git/info/exclude` 排除                                                                                                                                                                                                                          | 不入库   |
| `.claude/rules/engineering.md` | 项目规范, 项目内所有会话自动加载                                                                                                                                                                                                                                         | 入库     |
| `.git/navigator/`              | 编排会话登记与编排地址 (`orchestrator.json`), 执行会话登记, 工单审阅记录 (`order-approval.json`), 提交结算记录 (`commit-settlement.json`), 自检请求与心跳, 源码证据缓存 (`evidence/`), 编排会话最近的用户消息 (`prompts.json`), 待并入快照的写入标记 (`pending-writes/`) | 不入库   |
| `refs/navigator/snapshots`     | 状态目录的快照, 不进入分支历史                                                                                                                                                                                                                                           | 不入库   |

## 设计决策

每条写明决定, 原因, 以及改掉会怎样.

### 会话与边界

- **编排与执行分会话, 验收用子代理.** 规划与实现各自保持干净的上下文, 验收不受编排会话的倾向影响. 改掉的后果: 编排会话会开始写代码, 规划与实现重新混在一起.
- **编排会话的身份登记在 `.git/navigator/orchestrator.json`, 不写进状态文件.** 身份描述的是本机正在运行的会话, 不是项目历史. 以前登记在 `state.json` 中, 实例: `git reset --hard` 回到上一次提交, `state.json` 中的会话回到更早的会话, 在线编排会话被悄悄降级为其它会话, 写草稿被拒, 拒绝理由却让它去粘贴启动提示词; 同一会话运行插件命令却能改状态. `restore` 早已把会话当作环境信息保留, 放进运行期登记目录与这一定位一致. 旧状态文件中的会话字段在读取时迁移 (只读), `init` 升级时写入登记并从状态文件中移除. 改掉的后果: 回退或恢复记录会改变会话身份.
- **被接管的原编排会话单独成一类身份 (`superseded`).** 权限与其它会话相同, 但拒绝理由与提醒写明 "编排已由另一个会话接管" 与重新接管的办法, 收到消息与会话开始时都注入提醒. 改掉的后果: 原编排会话不知道自己被接管, 拒绝理由把它当成执行会话.
- **分叉出的会话按转录中的编排会话标记自动接管.** 桌面应用中回退或编辑消息, 以及 `--fork-session`, 都以新的会话编号继续, hook 输入中没有指向原会话的字段, 但分叉出的转录复制了原会话的历史. enter 的输出与分叉接管的提醒都带 "编排会话编号: <编号>"; SessionStart 的 `source` 为 `fork` 且身份为其它会话时, hook 在 `transcript_path` 指向的转录中找当前编排会话的标记, 找到就接管, 只找到曾经的编排会话的标记时按被接管的会话提醒. 实例: 用户在桌面应用中回退了一条被中断的消息, 编排会话换了编号, 插件命令全部被拒, 回复把原因说成 "编排已被接管". 改掉的后果: 每次回退都要用户重新调用技能, 拒绝理由还让模型误报接管.
- **从执行会话分叉出的会话按转录中的执行会话标记沿用执行登记, 对齐状态取分叉点时的状态.** 执行提醒带 "执行会话编号: <编号>", 已对齐时另带 "已对齐的发布轮次"; 登记, 对齐与会话开始时都注入这条提醒, 所以转录中最后一个标记就是分叉点时的执行身份. 分叉出的会话以新编号复制原登记 (`inheritedFrom` 记下原编号), 对齐按标记而不是原登记当前的状态: 回退到开工对齐之前时不能沿用之后的对齐. 编排会话的标记优先, 转录来自当前或曾经的编排会话时不沿用. 除了 SessionStart 的 `fork`, 工单已发布时其它会话每次收到消息也查一次转录: 实例中桌面应用中断后重发消息分叉出的会话, 转录中没有新会话的 SessionStart 记录, 无法确认一定触发该事件; 只在工单已发布时读取, 与执行无关的会话不付出这份开销. 实例: 执行会话写回执之前用户中断并重发 "A", 会话换了编号, 写 `receipt.md` 被拒, 拒绝理由让用户新开会话重跑. 改掉的后果: 执行中途任何一次回退都让工单卡在汇报阶段.
- **编排地址登记在运行期登记中, 不写进工单.** 执行会话消息汇报要知道编排会话的名称 (ListAgents 输出第一行), 名称后的编号在进程重启或分叉后会变, 本机还可能有多个同名会话; 已发布的工单不能再改. 编排会话每次接管与恢复后用 `address set` 登记, 接管时登记随之清空; 执行会话运行 `status` 取 "编排地址", 用 ListAgents 核对列表中有一行的名称与编号和这个地址完全相同, 再按完整地址发送; 地址未登记, 没有相同的一行或发送失败时改为文档汇报. 工单概况的 "编排会话" 一项由骨架预填说明. 改掉的后果: 工单中的地址在重启或接管后失效, 消息汇报发不出去或发错会话.
- **编排地址是名称加方括号中的编号, 本机有其它同名会话不回退.** SendMessage 只接受 ListAgents 中的名称, 名称不唯一时附上编号; 不接受会话编号 (见实测结论). 执行手册以前写 "发给会话名称", "同名会话不止一个时改为文档汇报", 而登记的地址本来就带编号. 实例: 本机有两个 "编排会话" (每个项目一个), 登记的地址是 `编排会话 [b76883]`, 执行会话放弃消息汇报, 请用户到编排会话中选 A. 按角色给会话起名很常见, 回退几乎每次都发生. 现在 `address set` 拒绝不带编号的地址, 手册要求列表中有一行与地址完全相同时才发送: 名称相同而编号不同的会话不是编排会话. 脚本做不了这项核对 (ListAgents 是模型工具), 所以 "消息汇报" 的选项总是给出. 改掉的后果: 本机有同名会话时消息汇报必然失败, 或发错会话.
- **编排地址未登记时, hook 在编排会话每次收到消息与会话开始时附上登记做法.** enter 接管时输出 "地址登记" 一行, 但首次调用技能时 enter 停在 "初始设置", 没有这一行, 之后的 `init`, `status` 与 `reply` 也不输出. 实例: 工单 0001 中编排会话从未登记, `status` 同时显示 "已有编排会话登记" 与 "编排地址: 未登记", 执行会话选消息汇报必然退回文档汇报. 提醒只看登记中有没有地址, 登记后不再出现; 恢复会话时地址可能已变, 另有一条重新登记的提醒. 改掉的后果: 新初始化的项目永远走不通消息汇报.
- **插件命令按访问级别放行, 访问级别表只有 `lib/command-access.mjs` 一处.** 改变编排状态或会接管编排的命令只有编排会话能运行; 执行会话与其它会话只能运行只读命令, 执行手册中的清单由生成脚本从同一张表生成. 判定放在守卫中: 命令行脚本无法可靠地知道调用它的会话 (Bash 环境中的 `CLAUDE_CODE_SESSION_ID` 没有写进官方文档), hook 输入中的 `session_id` 是文档化的. 守卫按命令文字识别 `node ... navigator.mjs <命令>`, 复合命令与带引号的路径也能识别. 改掉的后果: 任何会话都能用放行规则中的命令改动编排状态, 例如执行会话自己把工单转为已通过.
- **编排会话的工具按白名单放行, 默认拒绝.** 新出现的工具 (例如 Monitor, Workflow, MCP 写工具) 不能绕过限制. 改掉的后果: 每个新工具都是一个旁路.
- **各种身份的主会话都能写 `.waypoint/defects/` 下的 JSON 缺陷记录, 编排会话另外可以运行缺陷汇总脚本.** `/waypoint:review` 由用户在遇到问题时调用: 代理把本会话遇到的技能问题按事实写出来, 存成缺陷记录, 再运行汇总脚本. 本技能的问题大多出在编排会话, 以前那里只能写 `.navigator/`, 汇总脚本也不在命令白名单中, 两步都被拒, 只剩一段描述, 记录攒不起来; 执行会话在开工对齐之前与工单结束之后同样写不了. 缺陷记录是给技能维护用的, 不是业务代码, 也不是编排记录, 不进快照. 放行只看路径与扩展名: 目录是 `lib/paths.mjs` 的 `DEFECT_INBOX_DIRECTORY`, 运行脚本复制进项目后不能引用插件目录, 所以与插件 `runtime/lib/defect-paths.mjs` 各写一份, 由 `guard.test.mjs` 核对一致. 汇总脚本按 `node <路径>/runtime/tools/review-defects.mjs` 的写法识别, 它只读缺陷记录并打印; 与插件命令一样, 带管道或重定向的写法按复合命令拒绝. 编排会话派出的子代理仍然只读. 改掉的后果: 编排会话中发现的技能缺陷只能由用户到普通会话里转述补记, 多数不会被记下.
- **委派提示词由脚本生成, 守卫核对.** 验收提示词逐字核对, 调研提示词核对开头的固定框架. 改掉的后果: 编排会话可以在提示词中加入倾向性说明.
- **编排会话不用提问框.** 提问框出现时, 同一条回复中位于它之前的文字可能不会显示. 改掉的后果: 用户看不到选项所依据的内容.
- **流程之外的内容用 "自由答复" 回复.** 编排会话的每条回复都必须带回复类型, 用户要求解释或报告 (例如写给维护者的问题报告) 时, 以前只能借用其它回复类型. "自由答复" 只有一节自由正文 (规格中标 `"freeform": true`), 按用户要求的格式撰写, 可以放代码块与三级及以下的标题, 不按写作规则打回 (`lib/freeform-sections.mjs`); 当前进展, 选项块与人类总结照常校验, 所以用户总能看到位置与回到流程的选项. 禁令不变: 写代码仍被守卫拒绝. 改掉的后果: 流程之外的回复被打回, 或被塞进不相干的回复类型.
- **执行会话在 `.navigator/` 下只能写本工单的回执与本工单文件夹的 `artifacts/`.** 工单可以要求留存抓包原文, 复现脚本等证据, 供验收子代理独立复核. 以前只放行回执: 实例中工单要求把抓包落盘到工单文件夹, 执行会话被拒后把复现脚本放进会话临时目录, 验收看不到, 换机器也找不回. 证据文件只能在开工对齐之后写, 不做结构校验; 命令行写 `.navigator/` 仍被拒绝, 否则对账会把其它程序写的文件当成手工改动. 改掉的后果: 证据文件要么撑大回执, 要么留在仓库之外无法复核.
- **`.claude/settings.json` 对编排会话之外的会话只放行 `hooks` 字段内的改动, 插件的分组原样保留.** 项目自己的 hook (例如改完文件后运行代码检查) 与插件的防护 hook 接线在同一个文件里. 以前这个文件一律不许会话改动: 实例中工单要求接线两个前端 hook, 执行会话已写好 hook 脚本, 改 `settings.json` 时被拒, 只能把接线片段放进证据文件, 请用户手工合并; 这条限制在执行手册中只在 "代码检查" 一节顺带提到, 编排会话写工单时也不知道. 现在守卫重建写入后的全文 (`lib/settings-edits.mjs`), 核对三点: 内容是合法的配置; `hooks` 之外的字段没有变化 (含放行规则与 `disableAllHooks`); 含有插件 hook 的分组原样保留, 新 hook 只能写成独立的分组. 执行会话另外要满足写业务文件的条件; 无法重建内容的编辑一律拒绝. 同一事件有多个 hook 时拒绝优先, 新增的 hook 改变不了守卫的判定. `settings.local.json` 不入库, `engineering.md` 由 `standards` 命令写入, 两者仍然全拒; 命令行改写也仍然拒绝, 否则内容无从核对. 执行手册单列 "受保护的文件" 一节, `order-loop.md` 写明工单能要求哪些改动. 改掉的后果: 需要 hook 的工单每次都要用户手工合并配置; 或放开后会话可以删掉防护 hook.
- **命令行改写检查按写入目标判断, 先去掉运行插件脚本的部分与不写文件的重定向.** 检查是 "命令提到受保护路径, 且含写操作"; 插件脚本本身位于 `.navigator/bin/` 下, `2>&1` 又含 `>`, 以前任何带重定向的插件命令都被拒, 理由却说 "不能用命令行改写". 现在只去掉 node 之后的脚本路径 (作为复制目标等其它参数出现时仍受保护), 以及文件描述符复制与写到空设备的重定向. 不按 "只读子命令" 放行: `status > .navigator/state.json` 会被放过. 实例: 执行会话运行 `status 2>&1 | head -40` 被拒, 模型把原因误判为授权丢失. 改掉的后果: 常见的截取输出写法被拒, 拒绝理由误导排查.
- **执行会话在仓库根目录工作, 不使用 worktree.** worktree 中看不到尚未入库的工单. 改掉的后果: 执行会话找不到工单文件.
- **MCP 取证工具只给验收子代理, 编排会话一律不能调用.** 服务端状态机驱动的流程只能对照抓包等外部记录确认, 重放会推进服务端状态, 所以独立证据只能是验收子代理用只读工具重新查看外部工具自己记下的内容. 编排会话自己核对会让它的倾向进入验收结论. 工具由用户在 "测试授权" 中按完整名称认可, `tools set` 按项目登记, 不接受通配符: 编排会话判断不了一个 MCP 工具有没有副作用. 改掉的后果: 这类判据只能判为未验证, 工单必然不通过; 或编排会话开始替验收子代理下结论.

### 安装与配置

- **hook 装在项目级, 由 `init` 显式安装, 不放在插件级.** 有的仓库不是常规开发工程, 必须由用户显式选择. 改掉的后果: 装了插件的所有项目都会受限.
- **hook 用不经过 shell 的写法** (`"command": "node"`, `"args": ["${CLAUDE_PROJECT_DIR}/..."]`). 避开 Git Bash 与 PowerShell 的引号差异和含空格的路径. 改掉的后果: 路径含空格或中文时 hook 失败.
- **`SKILL.md` 设置 `allowed-tools: Bash(node *) PowerShell(node *)`, 不写 `shell` 字段.** 没有这项设置时, 默认权限模式下技能中的 `!` 命令会使整个调用中止; 子会话可能找不到 Git Bash. 该设置是仓库 "技能不设 `allowed-tools`" 约定的唯一例外. 改掉的后果: 技能在默认模式下无法打开.
- **放行规则同时写进 `settings.json` 与 `settings.local.json`.** 规则有两类: 插件命令, 以及 `Edit(.navigator/**)` (实测同时覆盖 Write 工具). 项目 `settings.json` 中的放行规则要等用户接受工作区信任后才生效, 无头模式永远不生效; 本机文件不需要信任. 放行只免去确认, 谁能写哪个文件仍由守卫决定. 改掉的后果: 每条插件命令与每次写记录文件都要用户确认.
- **插件命令一律写成 `node .navigator/bin/runtime/navigator.mjs <命令>`, 路径不加引号.** 放行规则按这个写法匹配. 改掉的后果: 命令弹出权限确认.
- **`init` 是上一条的例外: 初始化, 修复与升级只能由技能目录中的脚本运行, 下一动作写出完整的命令, 项目副本拒绝运行.** 升级就是把技能目录中的脚本复制进项目, 副本没有别的来源. 实例: 项目停在 0.7.4, 插件已是 0.8.0; 进入时的下一动作只写 "运行 init 修复", 编排会话照 "命令一律用项目副本" 运行了副本的 `init`, 副本发现来源就是自己, 跳过复制却输出 "已升级, 技能版本 0.7.4". 之后 `status` 也由旧副本运行, 再没有提示; 0.7.5 与 0.8.0 对项目收尾的修复都没有生效, 用户看到的仍是已修复的问题. 现在进入时的下一动作写出带技能目录绝对路径与会话编号的命令 (`lib/runtime-source.mjs`), 旧版本的副本也放行这条命令; 副本运行 `init` (自检的 `--verify` 除外) 以错误结束并写明正确的命令, 不改动项目. 改掉的后果: 升级悄悄失效, 发布的修复到不了已初始化的项目.
- **参考文件由 `init` 复制进 `.navigator/bin/references/`, `SKILL.md` 指向项目中的这一份.** 默认权限模式下, 读取项目之外的插件文件需要用户批准. 改掉的后果: 每读一次参考文件都弹出确认.
- **`.navigator/` 除草稿外全部入库, 插件在三处检查.** 入库的 hook 指向 `.navigator/bin/` 下的脚本, 对账依赖入库的状态文件. 项目模板中的 `lib/`, `bin/` 之类规则会漏掉运行脚本 (实例: Python 模板的 `lib/` 让 `.navigator/bin/runtime/lib/` 从未入库); `git add` 按目录暂存时遇到被忽略的文件不报错, 直接跳过.
  - init 写入的 `.navigator/.gitignore` 重新纳入各级目录与插件写的文件类型 (`.md`, `.mjs`, `.json`, `.gitignore`), 以及工单 `artifacts/` 下的全部文件 (证据文件类型不固定), 系统与编辑器的杂项文件仍按项目规则处理, 最后排除 `drafts/`.
  - init 与每次进入 (`enter`, `status`) 用 `git check-ignore --no-index` 检查必须入库的路径: 运行脚本副本, 固定文件, 规格中每种记录文件的示例位置, 以及 `.claude/settings.json` 与 `.claude/rules/engineering.md`. 这项检查覆盖项目各级 `.gitignore`, `.git/info/exclude` 与全局忽略文件. 上级规则忽略了 `.navigator/` 本身, 或忽略了 `.claude/` 下的配置时, 插件无法自己纳入: init 在改动其它文件之前停下, 进入时回复 "运行受阻", 都报告是哪条规则.
  - `order set committed` 核对 `.navigator/` 与上述两个配置文件中没有未入库的文件, 有则拒绝并列出, 要求在提交步骤中补交.
  - 改掉的后果: 换机器或 clone 之后 hook 找不到脚本, 守卫失效; 记录悄悄漏提交.
- **运行脚本只用 Node.js 22 内置模块.** hook 在用户机器上运行, 不能要求安装依赖. 改掉的后果: 初始化后还要在每个项目中装依赖.

### 状态与记录

- **`state.json` 是状态的唯一来源, hook 不写它.** 写入比较版本号, 先写临时文件再改名. 改掉的后果: 并发写入互相覆盖, 或写出半个文件.
- **运行期登记目录中的文件一律原子写入** (`lib/atomic-file.mjs`, 与状态文件共用). hook 每次事件都读编排登记与执行登记. 改掉的后果: 读到写了一半的登记时, 编排会话的工具调用被当成守卫出错拦下.
- **`spec/templates.json` 是回复, 记录文件与写作规则的唯一来源.** Stop 校验, 写入校验, 骨架生成, 体检与参考文档都从规格读取. 改掉的后果: 文档与校验逐渐不一致.
- **回复与记录文件先取骨架再填写, "当前进展" 由脚本计算.** 模型容易数错进度或漏写节. 改掉的后果: 回复被打回的次数大幅增加.
- **规则在填写时给出, 回复结束时与写入时的校验只做兜底.** `reply` 在骨架之前输出填写要求, 由规格生成, 与校验用同一份阈值与词表. 执行会话的回复只校验版式, 所以只给版式与人类总结两条. `template` 同样在骨架之前输出记录文件的填写要求 (`lib/file-guide.mjs`): 键值节每个键只占一行, 列出本文件的键值节, 表格节与可以放多行内容的节. 实例: 执行会话在回执 "测试结果" 下放了一张表格, 手册只列键名, 第一次写入被拦下. 改掉的后果: 模型写回复与记录时看不到规则, 打回与拦截次数增加.
- **"字" 只有一种算法** (`lib/text-units.mjs`): 汉字, 英文单词, 数字, 路径各算 1 字, 空格与标点不算, 句长与人类总结共用. 按字符计数时, 标点后的空格和英文路径会让总结比模型估计的长出一截. 改掉的后果: 人类总结频繁超出上限.
- **Stop 打回最多一次, 打回原因要求只改列出的问题.** `stop_hook_active` 为 true 时放行, 避免循环; 重写后的回复不再校验, 整条重写容易引入新错误. 改掉的后果: 模型可能反复重写同一条回复, 或在重写时带进新的错误.
- **回复从第一个一级标题算起, 标题之前的过程说明不打回, 但其中不能有代码块或标题.** 模型常在回复前加一句引导语. 打回只会让用户看到两遍同样的回复; 执行会话的开工对齐还会认不出来, 用户选 A 之后仍不能写业务文件. 改掉的后果: 许多回复被打回, 执行会话卡在开工对齐.
- **中文内容用 `.navigator/drafts/` 下的 JSON 草稿传给命令.** 子会话可能只有 PowerShell, Windows PowerShell 5.1 传中文参数会乱码. 改掉的后果: 中文内容乱码, 或命令因 heredoc 写法不同而失败.

### 对账与快照

- **快照存在隐藏引用中, 按原始字节存入 (`hash-object --no-filters`).** 不进分支历史, 不受 `core.autocrlf` 与 `.gitattributes` 影响, 恢复后逐字节一致. 改掉的后果: Windows 上恢复出的文件换行符改变.
- **快照只增量并入受控的写入, 回复结束时不整体拍摄.** 工具调用后事件只为本次写入的文件留下标记 (`.git/navigator/pending-writes/`), 等插件命令对账之前, 以及用户发消息, 会话开始, 回复结束时, 再把标记过的文件并入上一个快照: 同一次工具调用的 hook 并行运行, 用户装的格式化 hook 可能在插件拍快照之后才改写文件. 实例: 执行会话写回执, 编排会话写验收记录, 都被全局格式化 hook 改写了列表缩进与表格对齐, 每张工单都报 "状态目录与快照不符". 插件命令只并入自己写的状态文件, 视图文件与归档的回执; 只有初始化自检, `adopt` 与 `restore` 按当前内容整体拍摄, 这些时刻用户已确认当前内容. 引用更新时核对旧值, 并发时重试. 以前每次回复结束都整体拍摄, 每条命令也整体拍摄, 实例: 用户 `git reset` 回退了记录, 编排会话的下一条命令把回退后的内容拍进快照, 对账从此报 "一致". 改掉的后果: 回退与手工改动在下一次写入时被悄悄并入快照, 对账失去依据.
- **对账遇到 "自己的提交" 时也比对快照.** 自己的提交会被自动纳入; `git reset --hard` 回到自己的提交, 丢掉之后未入库的记录时, 提交历史看起来正常, 只有快照能发现. 改掉的后果: 回退被当成正常的提交收尾.
- **改变编排状态的命令先核对快照与提交历史** (`openProject`): 状态目录在最近的快照之后被改动过, 或提交历史出现陌生提交, 回退, 分叉与 squash 合并时拒绝, 列出改动的文件或提交, 要求先运行 `status` 按验收异常处理. 提交步骤中不比较提交历史: 补交的第二个提交在历史上看是陌生提交, 而记录本身没有被改动. 以前只核对快照, 实例: 用户在编排中途手动提交了两次, 命令照常运行, 下一次 `order set committed` 把这两个提交悄悄并入记录. 改掉的后果: 命令在被回退的记录上继续推进, 例如把已回退的工单状态改掉; 或手动提交不经用户确认就被并入.
- **快照提交使用固定身份 `project-navigator`.** 用户机器没有配置 Git 用户名与邮箱时, `git commit-tree` 会失败, 快照就悄悄拍不上. 改掉的后果: 在这类机器 (包括 CI) 上对账失去依据.
- **导航提交中入库的 `lastCommit` 等于其父提交.** 对账凭这一点认出自己的提交, 不需要额外标记; `init` 因此记录当时的 HEAD. 改掉的后果: 编排提交都被当成陌生提交.
- **对账异常未处理时, 暂停快照与大部分命令.** 否则下一个快照会把异常内容当成正常内容保存. 改掉的后果: 异常只提示一次, 之后悄悄消失.

### 执行与提交

- **启动提示词由脚本生成, hook 以首行 "执行工单 NNNN" 登记执行会话**, 读取当前工单文件作兜底; 当前或曾经的编排会话一律不登记. 改掉的后果: 执行会话无法被识别, 或编排会话被误登记为执行会话.
- **工单已发布而回执未写入时, 回复 "等待回执".** 编排会话的每条回复都必须带回复类型, 用户在 "工单发布" 中选 A 后, 编排会话无事可做也要回复. 以前这个状态没有回复类型, 模型只能重发 "工单发布", 用户每次选 A 都回到原处; 恢复进度与升级之后也会落到这个状态. 回执是否写入以 `status` 输出为准, 守卫不放行 `ls`. 改掉的后果: 发布工单之后编排会话反复重发 "工单发布".
- **工单每次发布时 "发布轮次" 加一, 对齐只对本轮有效.** 受阻后重新发布的工单内容已经改变, 需要重新确认计划. 改掉的后果: 执行会话按旧计划继续写代码.
- **工单发布之前经用户审阅, 认可与工单内容绑定.** "工单审阅" 的概况, 工作范围, 前提假设, 执行守则与验收判据由 `reply approve` 从工单文件原样摘录 (规格中标 `"source": "order"`), 回复结束时核对与文件一致, 摘录部分不按回复的写作规则打回. hook 在回复结束时记下工单内容的摘要, 在用户回答时记下选择, `order set issued` 只接受摘要与当前文件一致的认可, 发布时用掉. 以前 "工单发布" 只显示路径与判据数量, 启动提示词就在同一条回复里, 用户来不及看工单内容. 改掉的后果: 用户看到的内容与发布的内容可能不同, 或工单不经用户过目就交给执行会话.
- **已发布的工单可以撤回为起草中 (`order set drafting`).** "工单发布" 与 "等待回执" 的选项 B 是修改工单; 以前原地修改, 发布轮次不变, 已开工的执行会话仍按旧计划工作. 撤回期间执行会话的写入被拒绝, 重新发布时轮次加一, 旧回执归档. 改掉的后果: 修改后的工单不经审阅, 执行会话也不重新对齐.
- **初始化与阶段完成之后有阶段提交.** 编排会话只在提交步骤能提交, 以前提交步骤只有工单验收之后一处: init 写入的文件与阶段 0 到 3 的产出长期不能入库, 最后被扫进第一张工单的提交; 仓库还没有提交时连工单都建不了. 实例: 用户只好绕过编排手动提交立项产出, 提交中的 `lastCommit` 与父提交对不上, 之后一直被当成陌生提交. 现在 init 自检通过, 或推进阶段时上一阶段有尚未入库的技能产物 (不算只改了状态文件), 状态中登记 `stageCommit`, 下一动作是回复 "阶段提交", 由用户选只提交技能产物, 提交全部改动或暂不提交; `stagecommit start` 进入提交步骤, `stagecommit done` 核对入库并按 HEAD 结算 (见 "提交完成的命令不改写状态文件"). 未处理时 `stage` 与 `order new` 拒绝, 避免多个阶段的成果挤进一次提交. 改掉的后果: 阶段成果不入库, 回退或换机器时丢失, 或被迫手动提交引发对账异常.
- **项目收尾选 A 后运行 `finish`, 收尾记录由它登记的阶段提交入库.** 阶段提交只在推进阶段时登记, 而收尾记录在进入阶段 6 之后才写, 阶段 6 之后不再推进. 实例: 用户在 "项目收尾" 中选 A 后, `milestone-reviews.md` 的收尾一节留在工作区, 下一动作仍是 "继续阶段 6 的步骤 start", `stagecommit start` 报没有待选择的阶段提交, 守卫拒绝 `git add`. `finish` 只能在最后一个阶段运行, 把步骤设为 `finished` (`step` 不接受这个标识), 并且总是登记阶段提交: 它写下的完成标记在 `state.json` 中, 之后没有别的提交能带上. 实例: 收尾记录已先行入库 (从 0.7.2 的问题恢复时手动提交), `finish` 只看技能产物, 不登记阶段提交, 写下的完成标记留在工作区, 守卫拒绝 `git add`. 选 B 时新里程回到阶段 5, 由 `stage 5` 登记的阶段提交带上收尾记录. 改掉的后果: 选 A 的项目最后一份记录或完成标记无法入库, 只能手动提交而引发对账异常.
- **项目完成后回复 "项目完成", 不再回到 "项目收尾"; 此后 `finish` 只在记录有未入库的改动时登记阶段提交, 否则不写状态.** 项目完成后仍然没有后续提交, 写下的状态没有提交途径 (见下一条的结算). 实例: 0.7.5 收尾之后下一动作仍是回复 "项目收尾", 用户选 A 又运行一次 `finish`, 它不登记阶段提交, 却把结算后的状态写回 `state.json`; 用户手动提交之后纳入这个提交 (`adopt`) 又写一次状态, 永远无法收敛. 现在下一动作分两种: 记录 (含状态文件) 有未入库的改动时运行 `finish`, 由它登记阶段提交 "项目收尾后的记录更新"; 没有改动时回复 "项目完成", 选项是继续迭代, 推送远程与暂无安排. 改掉的后果: 收尾之后每一次写状态都在工作区留下没有提交途径的改动.
- **提交完成的命令不改写状态文件, 结算记在运行期登记中.** 提交步骤开始时写下的 `state.json` 随提交入库, 而完成提交步骤要写的 `lastCommit` 是这次提交的哈希, 只有提交之后才知道. 以前 `stagecommit done` 与 `order set committed` 把它连同清除 `stageCommit`, 工单转为已提交一起写回 `state.json`, 每次提交后工作区都留着一处未入库的改动, 平时由下一次提交带走. 实例: 项目收尾的阶段提交之后再没有提交, 项目已确认收尾, `state.json` 却一直显示为已修改. 现在这两条命令在 `.git/navigator/commit-settlement.json` 中记下 "内容为某个摘要的状态文件, 其提交步骤由某个提交完成" (`lib/commit-settlement.mjs`); 命令与 hook 读取状态时, 状态文件与摘要一致就按记录结算, 守卫随之收回提交步骤的放行; 下一次写入状态时写入结算后的内容, 随下一次提交入库, 摘要不同后记录自然失效. 提交步骤中 enter 发现自己的提交时同样按提交结算. 记录不入库: clone 之后状态停在提交步骤, 下一次进入时按 "自己的提交" 结算. 这套做法依赖 "写下的状态由下一次提交带走", 项目完成后没有下一次提交, 由上一条的 `finish` 补上. 改掉的后果: 每次提交后 `state.json` 都未入库, 收尾之后无法消除.
- **提交统一经过 `waypoint:commit-message`, 守卫只在提交步骤 (工单提交与阶段提交) 放行 `git add`, `git commit -F -` 与不带强制参数的 `git push`.** 提交消息规则只有一份. 唯一的例外是项目完成且记录都已入库之后, 单独放行不带强制参数的 `git push`: 之后不再有提交步骤, 推送也不产生提交. 实例: 收尾后用户要求推送, 守卫拒绝, 理由只说 "只运行三类命令", 编排会话无路可走. 其它时候推送被拒, 理由写明何时能推送, 以及可以请用户自己运行. 是否有未入库的记录只在命令是推送时才查询. 改掉的后果: 出现两套提交消息规则; 或收尾之后编排会话无法推送.
- **提交步骤中的拒绝理由写出放行的提交写法, 编排会话的位置提醒也附上这段写法.** 技能规则要求 "按拒绝理由调整, 不换写法重试". 实例: 编排会话的 `&&` 复合命令被拒, 理由提到 "重定向", 模型以为 heredoc 也不行, 改用 `-m`; `-m` 又被拒, 通用理由没有提到提交写法, 模型就转交用户手动提交. 写法说明只有 `COMMIT_COMMAND_FORMS` 一处. 改掉的后果: 编排会话在提交步骤声称无权提交.
- **开工对齐必须写 "模块划分" (新增模块, 改动模块, 入口改动).** 代码结构在动手之前定下, 用户选 A 之前能看到; 回复结束时校验这一节存在. 改掉的后果: 结构问题要到验收时才发现, 返工成本高.
- **模块化的机械检查交给项目的代码检查工具, 插件不解析代码.** 选型时选定检查工具并打开函数长度与复杂度规则, `codecheck set` 登记检查命令; 实现与修复工单的骨架预填 "代码检查通过" 判据, `order set issued` 核对判据原文, 检查命令自动算作已授权测试. 没有合适工具时必须写明原因登记. 改掉的后果: 模块化只靠提示与判断, 函数越写越长也能通过验收.
- **验收子代理不写 `tools`, 继承会话的全部工具, 由守卫按白名单放行; `disallowedTools` 去掉写工具.** 插件无法预知用户装了哪些 MCP, 列在 `tools` 中的工具名又必须写死; 继承之后, 取证工具与 Bash, PowerShell 都能用 (子会话可能找不到 Git Bash, 守卫对两者使用同一套规则). `disallowedTools` 是 hook 失效时的第二道防线. 改掉的后果: 列出 `tools` 时验收子代理拿不到任何 MCP 工具; 去掉 `disallowedTools` 时, hook 失效的项目中验收子代理可以写文件.

### 选型与验收结论

- **选型的源码证据写成表格, 由 `evidence` 命令从原仓库按版本取回被引用的行, 验收子代理只运行这条命令核对.** 证据在仓库之外, 而编排会话与验收子代理都不能联网, 以前验收子代理只能核对证据的格式, 核不了内容. git 取的是原始内容, 行号准确, 版本名或路径写错会直接报错; 网页抓取要经过模型转述, 行号不可靠, 所以不给验收子代理开联网工具. 每次只取深度为 1 的提交, 文件按需下载, 缓存在 `.git/navigator/evidence/`; 只接受 https 地址, git 不读凭据, 不弹提示. 守卫只放行不带参数的 `evidence`, 验收子代理不能借它访问任意地址. 改掉的后果: 源码证据无法独立核对, 只能靠执行会话自证, 或推给用户手工核对.
- **判据结论只有 通过, 不通过, 未验证 三种, 由脚本把关.** 取值写在规格的判据核对表中, `review.md` 写入时校验; 判据核对不全是通过时, `order set accepted` 与 `reply review --option 1` 都拒绝. 改掉的后果: 验收子代理可以自造 "部分验证" 之类的结论, 编排会话据此请用户人工补验, 绕过 "有未验证就不通过".
- **用户亲手运行的测试输出由编排会话原文写进 `user-tests.md`, 守卫核对逐字一致, 结论仍由验收子代理给出.** 以前 "测试授权" 选 B 时结果只写进验收记录, 验收子代理看不到, 判据只能是未验证, 工单必然不通过. UserPromptSubmit 事件把编排会话收到的消息存进 `.git/navigator/prompts.json` (最近 20 条), 写入时只核对新增的输出, 已有的输出当初写入时核对过. 用 `!` 运行的命令不触发该事件, 输出需要用户粘贴. 改掉的后果: 测试授权选 B 等于判不通过; 或编排会话可以改写用户的输出.
- **验收记录中等用户选择后才写的键由骨架预填 "待用户确认".** "用户结论" 与 "提交方式" 在写验收记录时还不知道, 而写入校验拒绝任何占位标记; 实例: 编排会话只好编出 "未到提交步骤" 之类的值. 预填值写在规格的 `presets` 中, 写入校验放行; `order set accepted` 与 `order set committing` 分别要求这两个键已改写. 改掉的后果: 记录中出现编造的用户选择, 或用户没选就进入提交.
- **选型工单不通过时新建选型工单, 不发布修复工单.** 修复工单发布前要求已登记检查命令, 而检查命令在选型通过后才登记. 改掉的后果: 选型不通过之后流程卡住.
- **检查命令的检查范围排除 `.navigator/` 与 `.claude/`.** 有的格式化工具默认也处理 Markdown, 会把编排记录纳入检查, 而执行会话不能改这两个目录. 改掉的后果: 编排记录的格式让每张实现工单的 "代码检查通过" 判据都通不过.

## 实测结论

在 Claude Code 2.1.280, Node.js 24.21.0, Windows 10 上实测 (2026-09-23), 项目路径含空格与中文:

| 待验证点            | 结论                                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 技能中的 `!` 命令   | 不设 `allowed-tools` 时默认模式下整个调用中止; `${CLAUDE_SESSION_ID}` 与 hook 的 `session_id` 一致; 不触发 PreToolUse |
| 技能的 `shell` 字段 | 子会话中找不到 Git Bash 时, `shell: bash` 的技能直接报错                                                              |
| 子代理身份          | 子代理的 hook 输入带主会话的 `session_id`, 另有 `agent_id` 与 `agent_type`; 插件子代理的 `tools` 限制生效             |
| Stop 打回           | 顶层 `{"decision": "block"}` 生效, 第二次 Stop 的 `stop_hook_active` 为 true                                          |
| bypass 模式下的拒绝 | PreToolUse 的 `permissionDecision: "deny"` 仍然生效                                                                   |
| 上下文注入          | UserPromptSubmit 返回的 `additionalContext` 模型能读到; 斜杠命令也触发该事件                                          |
| 配置即时生效        | 会话中途写入项目 `settings.json` 的 hook 立即生效                                                                     |
| 会话名称            | ListAgents 输出的第一行是本会话名称                                                                                   |
| 放行规则            | 项目 `settings.json` 的放行规则需要工作区信任, 无头模式不生效; `settings.local.json` 不需要                           |

冒烟测试中的补充结论 (`claude -p`, 默认权限模式):

- 读取项目之外的插件参考文件, 以及写入 `.navigator/` 下的文件, 都需要用户批准; 分别由复制参考文件与 `Edit(.navigator/**)` 放行规则解决.
- `Edit(...)` 放行规则同时覆盖 Write 工具.
- 调研框架不设范围时, 一次立项调研超过 80 次网络调用, 耗时约 13 分钟; 框架现在限制为合计 20 次.

源码证据的获取 (git 2.55, 2026-09-23):

- 按 tag 或完整提交号从 GitHub 取一个文件的若干行, 深度为 1 且文件按需下载, 约 2 秒, 缓存约 100 KB.
- tag 写法不对 (例如少了 `v`) 与路径不对 (例如少了 `src/`) 都直接报错; 仓库不存在时约 2 秒内失败, 不弹凭据窗口.
- 远端是本机路径时, git 提示不支持按需下载并改为完整获取, 结果相同; 测试据此使用本机临时仓库.

子代理与 MCP (Claude Code 2.1.282, 2026-09-25, 用只含一个子代理的探测插件在 `claude -p` 中实测):

- 插件子代理不写 `tools` 时继承会话的全部工具, 含延迟加载的 MCP 工具; 用 ToolSearch 加载后可以调用.
- 子代理调用 MCP 工具时触发 PreToolUse, 输入带 `agent_id` 与 `agent_type`.
- 插件子代理的 `disallowedTools` 生效, 列出的工具在子代理中不存在, ToolSearch 也加载不到.
- 用户用 `!` 运行的命令不触发 UserPromptSubmit: 会话记录中只有 `bash-input` 与 `bash-stdout`, 没有 hook 注入.
- 交互界面中粘贴的大段文字 (输入框显示为占位符), UserPromptSubmit 的 `prompt` 收到的是原文, 外面包一层 `<pasted_content>` 标签, 换行保留. 用户测试输出的逐字核对依赖这一点.

命令行中的会话编号 (Claude Code 2.1.283, 2026-09-26):

- Bash 工具运行的命令在环境变量 `CLAUDE_CODE_SESSION_ID` 中带有会话编号, 与 hook 输入的 `session_id` 相同, 但官方文档没有记载. 插件命令因此不据此判断调用方, 访问级别由守卫按 hook 输入判断.

会话恢复, 分叉与 hook 的执行顺序 (Claude Code 2.1.283, 2026-09-27, `claude -p` 配合探测 hook, 以及 Claude 桌面应用的日志):

- `--resume` 与 `--continue` 保留会话编号, SessionStart 的 `source` 为 `resume`; `--fork-session` 得到新的会话编号, `source` 为 `fork`. hook 输入带 `transcript_path`, 但没有指向原会话的字段, 分叉出的转录中也没有原会话编号.
- 桌面应用中回退 (rewind) 之后, 下一条消息以 `resumeSessionAt` 加 `forkSession` 重新启动底层会话, 会话编号改变, 界面上仍是同一个对话 (应用的会话文件在 `rewindEdges` 中记下父子关系).
- 桌面应用中中断一条消息后重发, 同样分叉出新会话 (2026-09-27, 用户报告的转录): 新转录复制了中断之前的历史, 每一行的 `sessionId` 都改成新编号, 被中断的那一轮不在其中. 转录中没有新会话的 SessionStart 记录, 本机其它转录也只记下过 `startup`, 无法据此确认这种分叉触发了 SessionStart. hook 注入的文字 (含 UserPromptSubmit 的 `additionalContext`) 以 `hook_additional_context` 附件记在转录中, 执行会话标记依赖这一点.
- 同一事件的全部 hook 并行运行, Claude Code 等它们全部结束后再继续 (官方文档). 格式化 hook 因此可能在插件的 PostToolUse hook 读过文件之后才改写它.

跨会话消息的地址 (Claude Code 2.1.284, 2026-10-01, Claude 桌面应用):

- SendMessage 不接受会话编号: 用本会话的完整会话编号作收件地址, 返回 `No agent named '<编号>' is reachable`. 收件地址只能是 ListAgents 中的名称, 名称不唯一时附上 ` [编号]`.
- 带编号的名称可以解析: 用本会话自己的 `名称 [编号]` 作收件地址, 工具识别出指向本会话. 用带编号的名称发给其它会话尚未在这里实测.
- ListAgents 每行有名称, 编号, 类型与忙闲, 没有会话编号.
- `~/.claude/sessions/<pid>.json` 记录每个运行中会话的会话编号, 名称与状态, 但没有方括号中的编号; 这个编号也不是会话编号, pid, 进程启动时间, 宿主会话编号或消息管道名的常见哈希 (SHA-256, SHA-1, MD5, SHA-512) 的前缀或后缀. 这份文件没有官方文档. 所以脚本拿不到地址, 只能由编排会话从 ListAgents 读取.

尚待交互实测: bypass 模式下退出计划模式是否弹框, Agent Team 成员的会话身份, 跨会话消息开启的新回合是否触发 UserPromptSubmit. 设计已不依赖前两项的结果; Agent Team 在编排会话中默认禁用.

## 发版前手动测试

在临时仓库中用 `claude --plugin-dir ./plugins/waypoint` 逐项确认:

### 初始化与会话

1. 未初始化时回复 "初始设置"; 选 A 后完成自检, 选 B 不做任何修改. 自检通过后回复 "阶段提交", 三个选项各试一次; 在还没有提交的空仓库中, 选 A 完成首次提交后可以新建工单.
2. 接受工作区信任对话框之前与之后, 插件命令都不弹权限确认.
3. 新会话恢复进度, 原编排会话不能再写记录; 原编排会话收到消息时得到 "已不是编排会话" 的提醒, 重新调用技能后接管回来.
4. 在桌面应用中回退编排会话的一条消息后再发消息, 分叉出的会话得到 "已自动接管编排" 的提醒, 插件命令放行; 登记编排地址后, `status` 显示新地址.
5. 执行会话对齐之后, 在桌面应用中中断一条消息再重发: 分叉出的会话得到 "已沿用原执行登记" 的提醒, 对齐状态为已对齐, 能写回执与业务文件; 回退到开工对齐之前再发消息时, 对齐状态为未对齐. `status 2>&1 | head -40` 放行.
6. 上下文压缩后, 编排会话收到位置提醒. 新项目初始化之后, 编排会话收到下一条消息时得到登记编排地址的提醒, 登记后不再出现.
7. 卸载后 hook 与放行规则被移除, 记录保留.
8. 用 0.5.0 初始化的项目升级后, 原编排会话仍是编排会话, `state.json` 中不再有会话字段.
9. 用上一个版本初始化的项目调用技能: 下一动作写出带技能目录路径的 init 命令, 编排会话照抄, 输出的技能版本是新版本, `status` 不再提示较旧. 让编排会话用 `.navigator/bin/` 下的副本运行 `init`: 命令以错误结束, 版本文件没有变化.
10. 执行会话与普通会话运行 `order set` 等插件命令被拒, 运行 `status` 与 `template` 放行.

### 立项与选型

1. 新建项目的立项: 需求理解, 问题域调研, 调研报告, 头脑风暴的发散与收敛, 项目简报.
2. 已有项目的盘点, 含运行检查工单.
3. 规范对照: 矛盾条目每轮不超过 3 条, 选定注释语言, 写入 `.claude/rules/engineering.md`.
4. 选型回执的证据表: 执行会话用 `evidence check` 自查; 验收子代理运行 `evidence` 核对; 版本或路径写错时判为未验证, 工单不通过, 下一动作是新建选型工单.
5. 语言选型后登记代码检查命令; 登记之前实现工单发布被拒, 登记之后工单骨架预填检查判据, 验收子代理能运行检查命令.

### 工单往返

1. 工单往返各做一次文档汇报与消息汇报; 编排地址未登记时, 执行会话选消息汇报会改为写回执文件并提醒用户. 本机另开一个与编排会话同名的会话时, 消息汇报仍送到编排会话; 编排会话重启后没有重新登记时, 执行会话改为写回执文件. 用不带编号的地址运行 `address set` 被拒.
2. 写完工单先回复 "工单审阅", 各节与工单文件一致; 选 B 后修改再审阅; 选 A 后才能发布; 认可之后改工单文件, 发布被拒.
3. "工单发布" 选 B 时撤回工单, 修改后重新审阅发布, 执行会话需要重新开工对齐.
4. "工单发布" 选 A 后回复 "等待回执"; 回执未写入时选 A 再次回复 "等待回执"; 写入后选 A 进入测试授权或验收.
5. 执行会话对齐后用 Write 写 `artifacts/` 下的证据文件成功, 对齐前被拒; 项目忽略该文件类型时仍能入库; 验收子代理按回执引用的路径读取.
6. 执行受阻后修改工单重新发布, 执行会话需要重新开工对齐.
7. 执行会话在用户选 A 之前写业务文件被拒绝, 提交被拒绝; 开工对齐中有 "模块划分", 缺少时被打回.
8. 需要外部影响的测试先回复 "测试授权".
9. 验收子代理交回结论与证据, 它尝试写文件时被拒绝.
10. 验收通过与不通过各一次; 同一切片连续两次不通过时建议重新拆分; 判据核对中有未验证时, `reply review --option 1` 与 `order set accepted` 被拒.
11. 三种提交方式都经过 `commit-message`, 提交后对账为一致; 纳入范围之外的改动用文字询问.
12. 提交步骤中用 `-m` 被拒时, 拒绝理由列出放行的写法, 编排会话改用 heredoc 或 PowerShell 管道完成提交, 不转交用户.
13. 回执 "取证记录" 用到未登记的 MCP 工具时回复 "测试授权"; 选 A 后 `tools set` 登记, 验收子代理能调用该工具, 调用未登记的 MCP 工具被拒.
14. "测试授权" 选 B: 用户粘贴输出后写入 `user-tests.md` 成功, 改写输出被拒; 验收子代理按输出判定.
15. 工单要求接线一个项目 hook: 执行会话对齐后用 Edit 在 `.claude/settings.json` 的 `hooks` 中追加分组成功, 新 hook 立即生效; 删掉插件的分组, 改放行规则, 改 `.claude/settings.local.json` 都被拒, 理由写明能改什么. 提交后 `order set committed` 通过, 再次运行 `init` 保留这个 hook.

### 变更, 复查与异常

1. 需求变更, 里程复查 (含自动体检), 手动体检. "项目收尾" 选 A 后收尾记录经 "阶段提交" 入库, 之后回复 "项目完成", `git status` 干净; 选 B 后新里程回到阶段 5.
2. "项目完成" 选 B 时编排会话推送成功; 编排中途推送被拒, 理由写明可以请用户自己运行. 再次调用技能仍回复 "项目完成", 工作区保持干净.
3. 用户要求写一份问题报告, 编排会话回复 "自由答复", 正文含代码块也不被打回.
4. `git reset` 回退, squash 合并, 手工修改记录文件后, 都能进入对应的验收异常.
5. 编排会话工作中途, 用户 `git reset --hard` 回到上一次提交丢掉记录: 编排会话保持身份, 改变状态的命令被拒, `status` 报记录与快照不符, 恢复快照后继续.
6. 编排会话写代码, 装依赖, 使用提问框都被拒绝.
7. 回复版式违规被打回一次, 第二次放行.
8. 在编排会话中运行 `/waypoint:review` 并附一句说明: 回复为 "自由答复", 问题按事实写出; 缺陷记录写入 `.waypoint/defects/` 成功, 汇总脚本放行; 同一会话写业务文件仍被拒. 执行会话在开工对齐之前也能写缺陷记录.

## 已知限制

- 写作规则中的语义部分 (自造简称, 比喻, 指代不明) 只能靠提示词, 体检与禁用词表, 脚本检查是近似的.
- 打回时不合格的回复仍留在屏幕上.
- 命令行中的写入只能按命令文字粗查, 例如用脚本语言写文件无法识别. 其它会话运行插件命令也按命令文字识别, 用其它方式调用运行脚本 (例如在脚本中导入模块) 无法识别; 这类改动写入状态目录后, 由快照与对账发现. `.claude/` 下的配置不在快照范围内, 用脚本语言改写它们不会被发现, 只能在提交前的改动清单中看到.
- hook 不限制用户本人的操作; 用户手工改记录文件由对账发现.
- 每次工具调用多启动一次 Node.js, 本机实测约 70 毫秒, 只发生在已初始化的项目中.
- 取证工具查看的是外部工具中验收时的记录; 记录被清空或工具没有运行时, 相关判据只能判为未验证. 取证工具是否只读由用户在授权时判断, 守卫只按工具名放行.
- 用户测试输出的逐字核对只覆盖编排会话最近 20 条消息, 用 `!` 运行的命令输出需要用户粘贴.
- 源码证据只支持公开 git 仓库的 https 地址; 没有公开仓库的依赖只能判为未验证, 由用户决定. `evidence` 只核对被引用的行, 这些行是否真能支持 "说明" 仍由验收子代理判断.
