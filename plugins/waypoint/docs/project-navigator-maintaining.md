# project-navigator 维护文档

[English](project-navigator-maintaining.en.md) | 简体中文

本文面向维护者: 设计总览, 设计决策, 组件地图, 排查手册, 修改流程, 测试与实测结论. 仓库级的维护约定见 [MAINTAINING.md](../../../MAINTAINING.md).

## 设计总览

技能只负责五件事, 加任何功能之前先确认它属于其中之一:

1. 立项与路线: 从一句需求得到需求文件与按里程, 切片排列的路线.
2. 进度: 状态由脚本记录, 下一动作由脚本计算, 任何会话都能接上.
3. 切片循环: 编排会话写计划, 子代理实现, 另一个子代理独立验收.
4. 模块化约束: 单一数据源, 按职责分层, 模块化, 不提前抽通用模块; 模块的表达方式随项目形态变化.
5. 骨架与接线: 第一个切片是最小骨架, 每个切片都要给出接线证据.

技能由三层组成:

| 层       | 位置                                           | 职责                                        |
| -------- | ---------------------------------------------- | ------------------------------------------- |
| 规则     | `SKILL.md`, `references/`, `guide/executor.md` | 写给模型: 流程, 步骤, 怎么写计划与结果      |
| 运行脚本 | `runtime/navigator.mjs`, `runtime/hook.mjs`    | 命令修改状态并计算下一动作, hook 守写入边界 |
| 规格     | `spec/slice.json`, `standards/engineering.md`  | 切片文件的小节, 与工程规范默认包的唯一来源  |

插件层面的接线:

| 位置                        | 内容                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------ |
| `hooks/hooks.json`          | 三个事件 (PreToolUse 只匹配写入类工具, UserPromptSubmit, SessionStart) 都调用 `runtime/hook.mjs` |
| `bin/project-navigator`     | Bash 工具中的命令入口, `exec node .../navigator.mjs "$@"`                                        |
| `bin/project-navigator.cmd` | PowerShell 工具中的命令入口                                                                      |
| `agents/navigator-*.md`     | 实现与验收子代理                                                                                 |

在用户项目中, 技能会用到以下位置:

| 位置                           | 内容                                             | 是否入库 |
| ------------------------------ | ------------------------------------------------ | -------- |
| `.navigator/`                  | 状态文件, 路线视图, 需求, 决策, 待办, 切片, 结论 | 入库     |
| `.navigator/drafts/`           | 编排会话传给命令的 JSON 草稿                     | 不入库   |
| `.claude/settings.json`        | 放行规则                                         | 入库     |
| `.claude/settings.local.json`  | 放行规则的本机副本, 由 `.git/info/exclude` 排除  | 不入库   |
| `.claude/rules/engineering.md` | 项目规范, 由 `setup` 写入, 所有会话自动加载      | 入库     |

2.0.0 不在 `.git/` 下保存任何东西.

## 设计决策

每条写明决定, 原因, 以及改掉会怎样.

### 2.0.0 的取舍

1.x 的迭代几乎全部花在流程管控上 (工单状态机, 回复校验, 审阅绑定, 发布前核对), 而立项质量, 切片怎么切, 接线怎么查从首版之后没有再打磨. 2.0.0 把这个比例倒过来.

- **保留的:** 编排与实现分开; 独立验收; 工程规范写入项目; 状态与下一动作由脚本管; 记录入库并检查忽略规则; 提交走 commit-message; hook 放在插件级; 运行脚本只用 Node.js 内置模块; 细节与实际不符时按实际修正; 个别标准做不到时列为待定.
- **去掉的:** 工单, 回执, 验收报告三份文件与工单状态机; 约 20 种回复类型与回复结束时的校验; 工单审阅的摘要绑定与基准提交核对; 发布前核对子代理; 问题域调研子代理与头脑风暴存档; 术语表, 风险清单, 变更清单; 体检编号与语义体检; 规范对照流程; 选型的 `evidence` 命令与源码缓存; 子代理模型配置; 技能异常自检与问题报告; 写作规则校验; 按钮; 阶段编号 0 到 6; 生成文档这一步.
- **不迁移 1.x 的记录.** 两种记录的单位不同 (工单与切片), 迁移只能做成近似的, 而用 1.x 的项目很少. `init --archive` 把旧目录整个改名, 不删除. 改掉的后果: 要长期维护一份读旧结构的代码.

### 会话与执行

- **编排会话不写业务代码, 实现用后台子代理.** 目的不是防恶意, 是防角色坍塌: 用户一句 "顺手改一下", 模型就会自己写代码, 规划与进度的上下文从此被实现细节占掉. 改掉的后果: 编排会话逐渐变成实现会话, 长项目中途丢失主线.
- **交互式切片由编排会话直接做.** 逆向, 实测这类任务每一步都要用户配合, 而子代理不能与用户对话; 1.x 为此加了 "等待操作", 一个分析工单仍要来回多轮. 交互式切片只产出结论, 写在 `.navigator/findings/`, 本来就在编排会话的写入范围内, 守卫不需要新规则, "不写业务代码" 也不受影响. 只有 `findings` 切片可以是交互式: 写代码时不需要与用户对话. 改掉的后果: 回到每一步都要一轮交回.
- **不做 "另开执行会话" 的机制.** 0.x 就是这样做的, 身份登记, 分叉认领, 编排地址这一套是当时大部分故障的来源. 现在任何调用过技能的会话都是编排会话, 状态在文件里, 所以 "换一个会话接着做" 不需要任何机制. 改掉的后果: 回到登记与认领.
- **编排会话不做登记, 按转录中的编排标记认出.** `enter` 的输出带 "编排标记: project-navigator 编排标记 <编号>", 编号是项目路径 SHA-256 的前 12 位 (Windows 上先转小写); 输出注入技能内容, 技能内容记在会话转录中, hook 读 `transcript_path` 找这个标记. 源代码里只有前缀, 读源代码的会话不会被误认; `status` 不输出标记. 分叉出的会话复制了转录, 自然带着标记. 改掉的后果: 每次换会话编号都可能误判身份.
- **实现子代理不能提问, 所以只有一种中途交回.** 它结束本次运行, 最后一条消息第一行写 "交回: 需要回答" 或 "交回: 需要操作"; 编排会话转告用户, 再用 SendMessage 让原子代理继续 (实测 SendMessage 能带着上下文续接已结束的子代理). 切片状态一直是实现中. 1.x 有受阻, 等待操作, 待定判据三条通道, 各有自己的回复类型与状态转换. 改掉的后果: 每多一条通道, 多一组状态与判断.
- **委派提示词由脚本生成, 编排会话原样使用.** `brief exec` 与 `brief review` 是提示词的唯一来源, 其中的小节名取自规格. 改掉的后果: 提示词散落在规则文件里, 与切片文件的结构逐渐对不上.
- **子代理不写 `tools` (实现) 或只禁用写入工具 (验收), 验收固定用 Sonnet, 实现跟随会话.** 用户装的 MCP 工具可能用到, 所以不列 `tools`. 验收是逐条对照与取证, 不需要最强的模型, 模型写死在 `agents/navigator-reviewer.md` 的 `model` 中. 1.4.0 的模型配置命令去掉了: 多一条状态, 多一处出错; 要换模型时改这一行. 2.0.0 重写子代理定义时漏掉了这一行, 验收跟随了会话的模型, 2.0.1 补上. 改掉的后果: 列出 `tools` 时漏掉用户的工具; 去掉 `model` 时验收的开销与主模型相同.

### 切片与验收

- **工作单位是切片, 一个切片一份文件, 分三段.** 计划由编排会话写, 执行结果由实现方写, 验收由编排会话按验收子代理交回的内容写. 1.x 是三份文件, 各有固定结构, 读不出来流程就停. 改掉的后果: 回到三件套.
- **段的归属靠计划段的摘要保证.** 守卫只能按路径判断, 管不到文件里的段. `slice start` 记下计划段的摘要, `slice review` 比对, 不一致时拒绝送验; 是编排会话按用户的回答改的, 运行 `slice replan`. 摘要先去掉行首尾空白, 合并空白, 统一表格分隔行: 格式化 hook 重排表格时摘要不变. 这只能发现, 不能阻止; 实测中如果经常发生, 退路是把计划与执行结果分成两个文件.
- **脚本只读它需要的内容.** 完成标准 (编号列表), 需要决定与补做是否为 "无", 执行状态, 标准核对表 (结论只能取规格中的四种, 每行要有证据). 其余只检查 "不为空, 没有占位". 写入时不校验结构. 改掉的后果: 结构规则越多, 被拦下的次数越多.
- **默认只在验收之后请用户决定一次.** 计划的 "需要决定" 不是 "无" 时, `slice start` 拒绝, 用户回答后带 `--decided`. 1.x 每张工单固定两次 (审阅与验收), 而多数审阅用户只是点同意. 发布前核对也去掉了: 编排会话本来就能读代码, 写计划前自己读. 改掉的后果: 每个切片多一次没有信息量的确认.
- **硬约束与工作假设分两层.** 硬约束是目标, 完成标准, 明确不做, 模块安排; 其余是工作假设, 与实际不符时实现方取得证据后按实际做, 记进 "修正" 表, 由验收核对. 1.4.0 及之前把计划当合同, 细节不符就是一轮往返. 改掉的后果: 探索性的任务每发现一个细节就多一轮.
- **骨架是硬规则.** 第一个里程的第一个切片由脚本标为骨架, 种类必须是 `build`; 骨架通过之前 `slice plan` 拒绝其它切片; 骨架不能放弃. 改掉的后果: 回到 "先把各层横着写完, 最后发现接不上".
- **接线是验收的固定项.** 实现方在 "接线证据" 写出从入口到新代码的调用路径, 验收子代理自己再追一遍. 追不到时相关标准判不通过, 而不通过的切片只能补做或放弃, 所以没有接线的切片进不了下一个. 这条靠验收提示词与 `slice accept` 的拒绝共同保证, 脚本本身不判断接线.
- **同一时间只做一个切片.** `current` 只有一个位置. 改掉的后果: 基准提交与验收范围不再确定.
- **补做在同一份文件里进行.** `slice redo` 把执行状态改成 "补做中", 把现有的验收段标题加上轮次, 在文末追加一段空的验收段; 解析时同名的段取最后一个. 改掉的后果: 每轮一个文件, 或丢掉上一轮的验收记录.
- **用户亲手验过的标准记为 "用户已确认", 与通过同样对待.** 验收子代理看不到用户的屏幕, 靠运行才能确认的标准它只能判未验证. 2.0.1 及之前, 这类标准只能走 "接受现状" (`slice accept --accept-unverified`): 用户在游戏里看过效果并说了没问题, 回复里仍然写 "3 条未验证", 还要他再选一次. 现在编排会话在用户确认后把结论改成 "用户已确认" (规格 `verdicts.confirmed`), 证据写用户的原话, `slice accept` 不需要参数. 用户在送验之前已经看过的结果 (交互式切片常见), 验收子代理的证据以 "用户实测: " 开头 (规格 `userEvidencePrefix`), 编排会话直接改, 不让用户再做一遍. "接受现状" 只留给用户决定不验证的情况; 不通过的标准不能接受. 脚本不核对 "用户已确认" 是否属实, 这一条只靠规则. 改掉的后果: 用户做完验证还被告知 "未验证".
- **人工验证的前提在计划里问清楚.** 有完成标准要用户亲手验证时, 用到的账号, 角色, 物品, 设备写进计划的 "需要决定", 开工前问用户; 实现子代理只用确认过的前提准备步骤与材料. 实测中出现过: 实现子代理做好了要某件装扮才能测的补丁, 用户没有这件, 之后来回半小时找替代品. 改掉的后果: 步骤写得再清楚, 用户也做不了.
- **新增切片之前先问 "不做会怎样" 与 "有没有更省事的办法".** 规则在 `references/intake.md` 的 "新增切片之前", 里程复查与需求变更引用它; 提问时推荐最省事的办法. 实测中出现过: 用户随口提到一个现象, 编排会话排了一个逆向切片加一个接入切片, 把逆向标为推荐, 用户配合截了四张图之后才发现让使用者自己选就够了. 改掉的后果: 路线里混进没人需要的切片, 而且每个都要用户配合.
- **提交不是状态.** `slice accept` 之后编排会话按输出调用 commit-message, 状态文件随这次提交入库.

### 模块化约束

- **模块组织方式是登记的项目设置, 不是每次推断.** `directories` 或 `filters`, 立项时由脚本给出建议 (看仓库里有没有 `.sln`, `.vcxproj`, `.csproj`, `.vbproj`), 由用户确认. 工程规范默认包中两种写法各占一个带标记的块, `setup` 写入项目时只保留一块. 改掉的后果: 同一个项目里, 有的切片建目录, 有的建筛选器.
- **约束落在计划与验收两处固定项上, 不只是规则文本.** 计划的 "模块安排" (文件, 模块, 层, 说明, 唯一定义, 复用) 是硬约束; 验收的 "结构核对" 六项写在 `lib/briefs.mjs` 的 `STRUCTURE_CHECKS` 中. 1.x 只在验收里有一行 "规范核查". 改掉的后果: 规范只在出问题之后才被想起来.
- **筛选器检查是唯一确定性的模块化检查.** 用正则解析 `.vcxproj` 与 `.vcxproj.filters`: 每个源文件项要归入筛选器; 只有本切片新增的文件要求平铺 (与基准提交比较), 已有的子目录不追究; 项目目录之外的文件与带通配符或宏的项不检查. 不引入 XML 库: 运行脚本只用内置模块.
- **验证方式也是登记的项目设置.** `auto` 时验收子代理运行登记的命令; `manual` 与 `measured` 时提示词写明不构建, 不运行. 1.x 假定每个项目都有代码检查命令, 没有命令的项目要绕路登记 "原因".

### 状态与记录

- **`state.json` 是状态的唯一来源, 只由插件命令写入.** 写入比较版本号, 先写临时文件再改名. 结构版本 6; 更早的结构不读取.
- **下一动作只在 `lib/guidance.mjs` 中计算.** `status` 与 hook 的位置提醒共用. 它只需要状态, 以及从切片文件读出的三件事: 执行状态, 标准核对表的行数与归类. 改掉的后果: 命令输出, hook 与规则文件各说各的.
- **路线视图由脚本生成.** `.navigator/roadmap.md` 每次保存状态时重写, 守卫拒绝直接编辑.
- **决策条目由命令追加.** `decision add` 同时登记编号与追加正文, 两边不会对不上; 需求文件与待办由编排会话直接写.
- **中文内容用 `.navigator/drafts/` 下的 JSON 草稿传给命令.** Windows PowerShell 5.1 传中文参数会乱码.
- **不用快照与对账.** 记录在 Git 中, 回退与手工改动用 git 就能看到; 对不上时 `check` 给出问题, 由用户决定.

### 回复

- **回复有三种版式, 没有校验.** 版式只写在 `SKILL.md` 的 "回复" 一节: 等待, 报告, 要用户决定或操作. 1.x 的回复类型, 骨架命令与 Stop hook 都去掉了: 它们是为了从回复里识别用户的选择 (工单审阅的认可), 现在流程不再依赖回复的结构. 代价是版式只靠规则. 改掉的后果: 回到打回与重写.
- **要用户决定时, 问题与选项紧跟在第一段之后, 选项放在代码块里.** 2.0.0 的规则只有 "第一行结论, 第二行进展, 末尾列选项", 实际会话中出现了: 问题埋在长篇背景之后; 相邻的 "A. B. C." 三行被 Markdown 合并成一段; 进展行与第一行粘在一起; 立项时把全部疑点一次列给用户. 代码块中的换行不会被合并, 所以选项固定用代码块. 改掉的后果: 用户读完整条回复才知道要回答什么.
- **有提问框工具时必须用它, 但不依赖它.** 桌面应用在回合结束时提供提问框 (`wrap_up`), 终端里没有. 规则写成 "有这类工具时每次都用, 内容用简体中文, 按钮与代码块的选项对应", 代码块始终保留, 两种环境下回复都完整. 改掉的后果: 只写代码块时桌面应用里没有按钮可点; 只靠提问框时终端里看不到选项.
- **进展写在回复末尾, 有变化时才写.** 放在第二行时, 它每条回复都占着最显眼的位置, 而内容多数时候没有变化.
- **同一段内容只完整写一次; 送验时不转述实现方的自述.** 实测中, 送验时先复述一遍实现方报告的结果, 验收回来再报一遍, 同一批操作步骤整段发了两次.
- **用户打断或在选择之后提出疑问时, 先回答, 重新确认之前不改状态, 不提交.** 实测中, 用户选了 "接受并提交" 后立刻打断并提出疑问, 编排会话一边回答一边照样提交了.

### 安装

- **hook 放在插件级, 未初始化的项目中立即结束.** `hooks.json` 用不经过 shell 的写法 (`"command": "node"`, `"args": ["${CLAUDE_PLUGIN_ROOT}/..."]`). `hook.mjs` 读不到当前结构的状态文件, 或项目已卸载时直接结束; 所以 1.x 的记录在归档之前, hook 也不生效. 代价是装了插件的所有项目中, 每次写入类工具调用与每条消息都启动一次 Node.
- **命令经插件 `bin/` 调用, 写成 `project-navigator <命令>`.** 技能加载时的 `enter` 仍用 `node "${CLAUDE_SKILL_DIR}/runtime/navigator.mjs"`, 因为 `!` 命令的 PATH 没有文档保证; 为此 `SKILL.md` 设置了 `allowed-tools`.
- **参考文件与实现手册由 `ref <名称>` 输出.** 默认权限模式下, 用 Read 读取项目之外的插件文件需要用户批准. `ref executor` 在手册之后附上 `shared/punctuation.md`, 标点规则只在那一个文件中维护.
- **放行规则同时写进 `settings.json` 与 `settings.local.json`, 不放行宽泛的写入.** 规则是 `Bash(project-navigator *)`, `PowerShell(project-navigator *)` 与 `Edit(.navigator/**)`. 实现子代理写业务文件的确认按用户的权限模式处理.
- **`.navigator/` 除草稿外全部入库, 进入与初始化时检查忽略规则.** `.navigator/.gitignore` 重新纳入各级目录, `.md`, `.json` 与 `findings/` 下的全部文件, 最后排除 `drafts/`. `REQUIRED_TRACKED_PATHS` 中的路径被上级规则忽略时停下并报告是哪条规则.

## 实测结论

### 1.0.0 的设计依据 (Claude Code 2.1.321, Windows 10, 2026-11-10)

用只含 hook, `bin/` 与一个子代理的探针插件在 `claude -p --plugin-dir` 中实测, 路径含空格与中文. 2.0.0 仍依赖这些结论:

| 待验证点             | 结论                                                                                                                      |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 插件级 hook          | `hooks.json` 的 exec 写法与 shell 写法都触发, `${CLAUDE_PLUGIN_ROOT}` 展开正常                                            |
| 子代理身份           | 插件子代理的 PreToolUse 输入带 `agent_id` 与 `agent_type: "<插件>:<名称>"`                                                |
| 转录                 | PreToolUse 输入带 `transcript_path`; 第一次工具调用时转录已含本轮的标记; 约 0.5 MB 的转录扫描 1 至 2 毫秒                 |
| 插件 `bin/`          | Bash 工具能直接运行无扩展名的脚本 (Git Bash), PowerShell 工具运行同名的 `.cmd`                                            |
| 后台子代理           | 无头模式会等后台子代理结束并处理结果; 桌面应用中, 后台子代理的完成通知会自动唤醒主会话                                    |
| 子代理续接           | SendMessage 能让已结束的子代理带着原上下文继续                                                                            |
| 子代理的写入权限     | 无头模式下没有放行规则时写入被拒; 裸 `Edit` 规则没有放行 Write, `Edit(**)` 放行前台与后台子代理的写入                     |
| 桌面应用默认权限模式 | 后台子代理的写入确认弹在主会话 ("Allow Claude to write x.txt?", 不写明是子代理); "Always allow" 会把会话切到 Accept edits |

官方文档 (2026-11-10): 插件 `bin/` 在 Bash 工具的 PATH 中, 排在用户 PATH 之后; 插件子代理不支持 `hooks`, `mcpServers`, `permissionMode`; 技能的 `allowed-tools` 只在调用技能的那一轮有效.

### 更早的结论 (Claude Code 2.1.280 至 2.1.284)

| 待验证点            | 结论                                                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 技能中的 `!` 命令   | 不设 `allowed-tools` 时默认模式下整个调用中止; 不触发 PreToolUse                                                            |
| 技能的 `shell` 字段 | 子会话中找不到 Git Bash 时, `shell: bash` 的技能直接报错                                                                    |
| bypass 模式下的拒绝 | PreToolUse 的 `permissionDecision: "deny"` 仍然生效                                                                         |
| 上下文注入          | UserPromptSubmit 返回的 `additionalContext` 模型能读到; 斜杠命令也触发该事件                                                |
| 放行规则            | 项目 `settings.json` 的放行规则需要工作区信任, 无头模式不生效; `settings.local.json` 不需要; `Edit(...)` 规则同时覆盖 Write |
| 会话分叉            | `--fork-session` 与桌面应用中回退, 中断后重发都会换会话编号, 分叉出的转录复制了原会话的历史                                 |
| 并行 hook           | 同一事件的全部 hook 并行运行, Claude Code 等它们全部结束后再继续                                                            |

### 2.0.0 的冒烟 (Claude Code 2.1.319, Windows 10, 2026-11-12)

在临时仓库中用 `claude -p --plugin-dir` 与 `--continue` 走了一遍 "命令行待办工具": 初始化, 立项, 排路线, 第一个切片 (最小骨架) 的计划, 实现, 送验, 验收, 直到请用户决定.

| 待验证点                | 结论                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------- |
| 带 `init` 参数调用      | 直接初始化并提交; 最初的规则文字让模型仍先询问, 已在 `enter` 的下一动作与 `SKILL.md` 中写明    |
| 立项                    | 写入需求文件, 登记项目设置, 排出骨架加两个纵向切片的路线, 按提交步骤提交                       |
| 计划                    | "模块安排" 按物理目录写出文件, 模块, 层与唯一定义; 没有待定事项时直接开工                      |
| 实现子代理              | 只写了业务文件与 "执行结果" 段; "接线证据" 写出从入口到数据层的逐步调用路径; "修正" 表记了两行 |
| 计划摘要                | 格式化 hook 重排了计划段的表格, 摘要不变, `slice review` 照常通过                              |
| 验收                    | 验收子代理交回后, 编排会话写入验收段并请用户在两个选项中决定                                   |
| 回复                    | 没有校验时, 回复保持第一行结论, 第二行进展                                                     |
| 会话中断 (无头模式超时) | 下一轮 `--continue` 按状态恢复, 接着验收                                                       |

冒烟时要注意: 在已经装有本插件的会话里启动子进程, 子进程会继承 PATH 中已安装版本的 `bin/`, 实际运行的是旧命令. 先把那个目录从 PATH 中去掉.

没有在真实会话中验证的:

- 中途交回之后用 SendMessage 续接, 以及补做一轮.
- 交互式切片, 以及它对编排会话上下文的占用.
- 用筛选器分模块的 Visual Studio 项目.
- 验证方式为 `manual` 与 `measured` 的项目.
- 桌面应用中的表现.

发版后在真实项目中遇到的问题, 补进排查手册.

## 发版前手动测试

在临时仓库中用 `claude --plugin-dir ./plugins/waypoint` 逐项确认:

### 初始化与会话

1. 未初始化时技能询问是否初始化; 同意后 init 写入状态目录与放行规则, 按输出提交; 不同意时不做任何修改. 没有初始化的仓库中写文件不受任何限制.
2. `project-navigator` 命令在 Bash 与 PowerShell 中都能运行, 不弹权限确认.
3. 新会话调用技能, 按记录继续; 原会话照常可用.
4. 上下文压缩后, 编排会话收到位置提醒.
5. 卸载后放行规则被移除, 写业务文件不再被拒, 记录保留.
6. 在 1.5.0 初始化过的项目中调用技能: 说明不读取旧记录; 同意后 `init --archive`, 旧目录改名为 `.navigator-1.x/`, 内容不变.

### 立项

1. 技能复述需求, 逐个确认待定问题, 写入需求文件.
2. `setup` 的建议: 有 `.vcxproj` 的仓库建议 `filters`, 其余建议 `directories`; 登记后 `.claude/rules/engineering.md` 只含对应的一种写法.
3. 路线的第一个切片是最小骨架; 把第一个切片写成 `findings` 时被拒.

### 切片循环

1. 写计划前编排会话读了相关代码; 计划的 "模块安排" 按登记的组织方式写 (目录或筛选器).
2. 计划中没有待定事项时直接开工; 有时先问用户, 带 `--decided` 开工.
3. 实现子代理在后台工作时能继续与编排会话对话; 它结束后编排会话自动接着处理.
4. 实现子代理需要用户操作: 交回 "交回: 需要操作", 编排会话原样转告, 用户回复后原子代理继续, 切片状态一直是实现中.
5. 计划的 "工作假设" 故意写错一个细节: 实现子代理不交回, 按实际做完, "修正" 表有一行; 验收的 "修正核对" 写出这项修正.
6. 实现子代理尝试改计划段: `slice review` 拒绝送验.
7. 故意不把新代码接到入口上: 验收的接线核对指出来, 相关标准不通过; 补做后通过.
8. 验证方式为 `manual` 的项目: 验收子代理不构建, 不运行, 靠运行才能确认的标准判为未验证并写出步骤; 用户确认后编排会话把结论改成 "用户已确认", 不带参数通过.
9. Visual Studio 项目中新增一个没有归入筛选器的源文件: 验收提示词的筛选器检查指出来.
10. 交互式切片: 不派实现子代理, 编排会话直接做, 结论写进 `.navigator/findings/`; 新开会话调用技能能接着做; 编排会话写业务文件仍被拒.
11. 验收子代理尝试写文件时被拒.
12. 验收通过后提交; 用户选推送时一并推送.
13. 讨论中提到当前切片之外的想法: 被记进 `backlog.md`, 没有被顺手做掉.

### 里程, 变更与收尾

1. 一个里程的切片都结束后进入里程复查, 排出下一个里程的切片.
2. 需求变更: 更新需求文件与路线, 记一条决策; 已经开始的切片保留.
3. 全部里程完成后收尾, 按输出提交, `git status` 干净; 之后追加里程能继续.

## 已知限制

- 守卫只检查写入类工具的目标路径: 用命令行或脚本语言写文件, 安装依赖, 运行改变状态的插件命令都不检查, 只靠技能规则.
- 编排会话的认定依赖转录中的标记, 转录格式是 Claude Code 的内部格式; 读不到转录时规则 4 不生效 (放行).
- 段的归属只能事后发现: 实现子代理改了计划段, 要到 `slice review` 才被指出.
- 接线与结构核对 (筛选器检查除外) 由验收子代理判断, 不是确定性的.
- 写计划前是否读了代码, 没有脚本把关.
- 回复的格式只靠规则.
- 实现子代理属于启动它的会话, 会话关闭后它的工作中断; 新的子代理只能靠 "中途记录" 与工作区中已有的改动接着做.
- 后台子代理的写入确认不写明是子代理.
- 筛选器检查只覆盖正则能认出的写法.
- 插件的 hook 在所有项目中触发, 每次写入类工具调用与每条消息多启动一次 Node.js.
