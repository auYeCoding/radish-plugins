# project-navigator

[English](project-navigator.en.md) | 简体中文

[返回 WayPoint](../README.md)

引导一个大型项目从一句宏观需求开始: 确认需求, 排出按里程与纵向切片推进的路线, 先做从真实入口跑通的最小骨架, 再一个切片一个切片地丰满, 并把进度记在仓库里, 任何会话都能接着做.

本技能针对三个常见问题:

- **没有路线就开工.** 技能先和你把需求确认清楚, 再排路线; 只把当前里程排细, 后面的到了再排.
- **横向膨胀, 做到最后功能与界面没有接上.** 每个切片都是纵向的, 做完要能从入口或界面看到; 验收时必须给出从入口到新代码的调用路径, 没接上不能进入下一个切片. 当前切片之外的想法记进待办, 不顺手做.
- **换个会话就忘了进度.** 进度由脚本记录在 `.navigator/` 中, 下一步做什么由脚本计算, 不靠模型记忆.

调用本技能的会话称为编排会话, 只做规划, 记录与组织验收. 写代码由它在后台派出的实现子代理完成, 验收由验收子代理在全新上下文中完成.

## 适用场景

- 从零开始一个需要几周或更久的项目.
- 推进一个已有项目, 希望每一块改动都有明确的目标, 完成标准与验收.
- 逆向, 实测这类要边查边做的项目: 查证的部分可以排成只产出结论的切片.

以下场景不适合: 改一个错字, 修一个小 bug, 写一次性脚本. 这类小任务直接对 Claude 说即可.

## 使用前提

- [Git](https://git-scm.com): 项目必须是 Git 仓库. 还不是仓库时, 先运行 [`/waypoint:repo-init`](repo-init.md).
- [Node.js](https://nodejs.org) 22 或更高版本: hook 与命令都用 Node.js 运行.
- 在项目根目录启动 Claude Code.

## 调用方式

本技能只能显式调用, 不会被自然语言自动触发:

```text
/waypoint:project-navigator [init | check | uninstall | 初始需求]
```

- 不带参数: 查看当前进度, 按提示继续.
- `init`: 初始化项目.
- `check`: 自查记录是否与状态对得上.
- `uninstall`: 停用本技能, 保留全部记录.
- 其它文字: 作为初始需求, 例如 `/waypoint:project-navigator 做一个团队周报汇总工具`.

任何会话调用本技能, 都按记录中的状态继续, 不需要接管或登记.

## 快速上手

以 "做一个团队周报汇总工具" 为例, 从一个只有 README 的新仓库开始. 编排会话的每条回复第一行是结论, 第二行是进展; 需要你决定时, 末尾列出以字母开头的选项, 回复字母即可.

### 第一次调用

1. 在项目根目录启动 Claude Code, 输入 `/waypoint:project-navigator 做一个团队周报汇总工具`.
2. 技能询问是否在本项目初始化. 同意后, 它创建 `.navigator/`, 写入放行规则, 并调用 [`commit-message`](commit-message.md) 提交这些文件.

### 立项

1. 技能复述它对需求的理解, 指出含糊, 缺失, 冲突的地方, 把待定问题逐个问你. 它不会自行假设.
2. 需求确认后写成 `.navigator/requirements.md`, 这是需求的唯一权威来源.
3. 技能请你确认两项项目设置: 模块怎么组织, 完成之后怎么验证. 见下方 [项目设置](#项目设置).
4. 技能排出路线: 第一个里程的第一个切片是最小骨架, 之后的切片在骨架上各加一项能力. 你认可后提交, 立项完成.

### 一个切片

1. 技能先读相关代码, 再写这个切片的计划: 目标, 完成标准, 明确不做, 模块安排. 计划里有要你决定的事时先问你; 没有时直接开工, 不需要你先过目.
2. 技能在后台派出实现子代理. 你可以去做别的事, 或继续和编排会话说话.
3. 实现子代理需要你回答问题或亲手做一件事时, 技能把问题或步骤原样转给你; 你回复后, 原来的子代理接着做.
4. 做完后技能派验收子代理核对, 向你报告每条标准的结论, 接线与结构核对的结果, 以及需要你亲手验证的步骤.
5. 你决定: 通过并提交, 补做, 或放弃这个切片.

正常情况下, 一个切片只需要你做一次决定, 在验收之后.

### 之后每次打开

在项目根目录新开会话, 输入不带参数的 `/waypoint:project-navigator`. 技能给出当前位置与下一步, 接着做.

## 核心概念

### 里程与切片

- **里程:** 一个对你有意义的阶段成果.
- **切片:** 一次实现加一次验收能做完的一块纵向功能. 一个切片同时包含它需要的界面, 逻辑与数据, 不按层横着切.
- **最小骨架:** 第一个切片. 它从真实入口 (可执行文件, 导出函数, 页面) 进入, 经过规划中的每一层, 每层只做最少的事, 证明各层接得上. 骨架通过验收之前, 不做其它切片; 骨架不能放弃.
- 同一时间只做一个切片.

切片有两种:

| 种类       | 写法       | 做什么                                 | 由谁做                                |
| ---------- | ---------- | -------------------------------------- | ------------------------------------- |
| 改代码     | `build`    | 实现一块功能                           | 后台的实现子代理                      |
| 只产出结论 | `findings` | 逆向, 实测, 调研: 查清一件事并写下结论 | 默认由编排会话在对话中直接做 (交互式) |

### 交互式切片

逆向, 实测这类任务, 每一步都可能要你在被调试的程序里操作一下. 子代理不能和你对话, 所以这类切片不派子代理, 由你正在对话的会话直接做:

- 它只产出结论, 写在 `.navigator/findings/` 下, 不改业务代码.
- 每确认一条结论立即写入文件, 并写明宿主版本, 位置, 验证方法与验证时间.
- 调试输出把上下文占满时, 新开一个会话调用技能即可接着做: 结论在文件里, 进度在状态里.
- 做完后照常由验收子代理独立核对.

不需要你配合的调研 (纯读代码或读文档) 可以在路线中标为非交互, 交给后台的实现子代理.

### 项目设置

立项时登记两项, 之后每个切片的计划与验收都以它们为准:

**模块组织方式.** 模块化设计是同一套原则, 但表达方式因项目而异:

| 取值          | 模块怎么表达                                                                      | 适用                   |
| ------------- | --------------------------------------------------------------------------------- | ---------------------- |
| `directories` | 一个模块一个物理目录                                                              | Python, Web, Go 等项目 |
| `filters`     | 源码文件平铺在工程目录下, 用 Visual Studio 虚拟筛选器 (`.vcxproj.filters`) 分模块 | Visual Studio 项目     |

技能会按仓库中有没有 `.sln`, `.vcxproj` 等工程文件给出建议, 由你确认.

**验证方式.**

| 取值       | 含义                               | 验收时                                                 |
| ---------- | ---------------------------------- | ------------------------------------------------------ |
| `auto`     | 有能在仓库根目录直接运行的检查命令 | 验收子代理运行这些命令                                 |
| `manual`   | 要你亲手构建或运行才能确认         | 子代理不构建, 不运行; 把验证步骤列给你, 由你确认后接受 |
| `measured` | 要在真实环境中实测                 | 同上                                                   |

### 模块化约束

登记项目设置时, 技能把工程规范写入 `.claude/rules/engineering.md`, 项目内所有会话与子代理都会自动加载. 其中与模块化有关的要点:

- 常量, 类型, 配置, 规则只定义一次 (SSOT).
- 按职责分层, 跨层只通过接口.
- 优先复用已有实现; 没有两处真实重复之前, 不建通用模块, 不把代码下沉到公共层 (YAGNI).
- 模块与文件的粒度以职责清晰为准, 不为拆而拆.

这些不只是规则文本, 每个改代码的切片都有两处固定检查:

- 计划中的 "模块安排": 每个新增或改动的文件归哪个模块, 属于哪一层, 承担哪一件事; 新增的常量与类型的唯一定义放在哪里; 复用了什么.
- 验收中的 "结构核对": 验收子代理逐项回答: 新文件是否在计划写明的模块中; 是否只有一处定义; 跨层是否只通过接口; 是否重写了可以复用的实现; 是否新建了只有一处使用的通用模块; 是否迫使多个已有模块改动内部实现.

用筛选器分模块的项目另有一项脚本检查: 每个源文件都在 `.vcxproj.filters` 中归入了筛选器, 本切片新增的源文件没有放进物理子目录. 结果直接写进验收提示词, 也可以随时运行:

```bash
project-navigator check --filters
```

## 一个切片的往返

1. **写计划.** 编排会话读代码后, 在 `.navigator/slices/` 下建切片文件, 填写计划段. 目标, 完成标准, 明确不做, 模块安排是硬约束; 其余细节是工作假设.
2. **开工.** 计划中没有要你决定的事时直接开工. 脚本记下当时的提交与计划段的摘要.
3. **实现.** 实现子代理按计划做, 自测, 写执行结果段. 其中 "接线证据" 写出从程序入口到新代码的调用路径.
4. **中途交回.** 实现子代理不能向你提问. 需要你回答或操作时, 它把已查清的内容写进 "中途记录", 结束本次运行; 编排会话把问题原样转给你, 你回复后它接着做. 这个过程中切片状态不变, 不需要重新开工.
5. **修正与待定.** 计划中的细节与实际不符时, 实现子代理取得证据后按实际做, 逐条记进 "修正" 表, 不停下来问你. 个别完成标准按事实做不到时, 做完其余部分, 列为 "待定标准". 两者都在验收时由你一次看完.
6. **送验.** 脚本核对计划段在实现期间没有被改动, 执行结果已填好.
7. **验收.** 验收子代理在全新上下文中逐条核对, 结论只有通过, 不通过, 未验证三种, 每条都附证据. 它自己从入口追一遍接线, 不照抄实现方写的路径.
8. **你的决定.**

| 情况                 | 你可以选                          |
| -------------------- | --------------------------------- |
| 全部通过             | 通过并提交; 通过, 提交并推送      |
| 有未验证, 没有不通过 | 接受现状并提交; 补做              |
| 有不通过             | 补做; 放弃这个切片 (骨架只能补做) |

补做时, 编排会话把要补的内容写进计划, 本轮验收归档在同一份文件里, 实现子代理接着做, 之后重新验收.

通过后, 编排会话调用 commit-message, 把这个切片的代码改动与记录合成一条提交.

## 里程复查, 需求变更与收尾

- **里程复查:** 一个里程的切片全部结束后, 技能对照里程目标说明达成情况, 和你一起整理待办, 排出下一个里程的切片.
- **需求变更:** 随时可以提. 技能说明影响, 你确认后更新需求文件与路线, 并记一条决策: 决定了什么, 为什么, 放弃了什么. 已经开始的切片不会被改掉; 只是随口一提的想法记进待办.
- **收尾:** 全部里程完成后, 技能对照需求逐条说明成果, 你确认后收尾. 收尾之后还可以追加里程继续.

## 记录文件

```text
.navigator/
├── state.json          进度与编号, 只能由插件命令修改
├── roadmap.md          路线视图, 由状态生成
├── requirements.md     需求: 目标, 必须要做, 明确不做, 约束, 已确认的结论
├── decisions.md        决策记录, 只追加
├── backlog.md          待办: 当前切片之外的想法
├── slices/
│   └── 0003-export-csv.md    一个切片一份: 计划, 执行结果, 验收
└── findings/           只产出结论的切片写下的结论与取证脚本
```

- `.navigator/drafts/` 是编排会话给命令传内容用的草稿, 不入库. 其余全部入库.
- `.navigator/` 自带的 `.gitignore` 会把记录文件重新纳入; 初始化与每次调用技能时, 都按 Git 的全部忽略规则检查, 记录会被忽略时技能停下并指出是哪条规则.
- 记录都在 Git 中. 回退或手工改了记录后, 技能按当前记录继续.

## 角色与边界

| 角色       | 由谁担任                 | 做什么                                       | 能写什么                                |
| ---------- | ------------------------ | -------------------------------------------- | --------------------------------------- |
| 编排会话   | 调用本技能的会话         | 确认需求, 排路线, 写计划, 组织验收, 记进度   | 只写 `.navigator/`                      |
| 实现子代理 | 编排会话在后台派出       | 按一个切片的计划写代码, 自测, 写执行结果     | 业务文件, 进行中的切片文件, `findings/` |
| 验收子代理 | 编排会话派出, 上下文全新 | 逐条核对完成标准, 接线, 结构与范围, 交回证据 | 不写文件                                |
| 你         | 唯一拍板的人             | 需求, 取舍, 验收结论                         |                                         |

hook 只守四条写入边界: 任何人不直接改状态文件与路线视图; 验收子代理不写文件; 实现子代理在 `.navigator/` 下只写进行中的切片文件与结论目录; 编排会话不写 `.navigator/` 之外的文件. 其余靠技能规则, 不拦截. hook 由插件提供, 不写进项目配置; 没有初始化的项目中什么也不做.

编排会话不写业务代码, 是为了让它的上下文一直留给规划与进度: 你说 "顺手改一下" 时, 它会把这件事排进当前切片的计划或待办.

### 权限确认

实现子代理在后台写文件时, 默认权限模式下, 写入确认会弹在编排会话中. 一个切片常常要写很多文件, 实现期间可以把会话切到 "Accept edits" (自动接受文件编辑). 是否切换由你决定.

## 从 1.x 升级

2.0.0 是一次不兼容的重构: 工作单位从工单改成切片, 记录的结构完全不同. 它不读取 1.x 的记录, 也不迁移.

更新插件后在 1.x 初始化过的项目中调用技能, 技能会说明这一点. 你同意后它运行:

```bash
project-navigator init --archive
```

旧的 `.navigator/` 被整个改名为 `.navigator-1.x/`, 内容不动, 仍可查阅; 然后从立项重新开始. 立项时可以让技能读归档中的简报与决策, 不必从头口述.

不同意时技能结束, 不做任何修改. 想继续用 1.x 的流程, 把插件固定在 1.5.0.

## 常见问题

**为什么输入 "帮我规划一个项目" 没有触发本技能?**

本技能只能用 `/waypoint:project-navigator` 显式调用, 避免在普通对话中误启动一整套流程.

**编排会话能帮我写一段代码吗?**

不能. 编排会话写 `.navigator/` 之外的文件会被拒绝. 需要改代码时排进切片, 由实现子代理完成.

**实现子代理在工作, 我能继续和编排会话说话吗?**

能. 子代理在后台运行; 它做完时编排会话会被通知并接着处理.

**我关掉了编排会话, 实现子代理的工作会怎样?**

子代理属于启动它的会话, 会话关闭后它的工作中断. 新会话调用技能后会重新派出一个, 新的子代理靠切片文件的 "中途记录" 与工作区中已有的改动接着做.

**我的项目不能由 Claude 编译或运行, 能用吗?**

能. 立项时把验证方式登记为 `manual` 或 `measured`. 子代理不构建, 不运行, 只读代码核对接线与结构; 要运行才能确认的标准列成步骤交给你, 你确认后选择接受现状.

**想到一个新点子, 但不属于当前切片?**

直接说. 技能把它记进 `.navigator/backlog.md`, 里程复查时和你一起决定排进哪里.

**多个切片能并行吗?**

不能. 同一时间只做一个切片, 保证每个切片的基准提交与验收结果都是确定的.

**怎样停止使用?**

运行 `/waypoint:project-navigator uninstall`. 放行规则会被移除, 插件的 hook 在本项目中不再生效, `.navigator/` 中的记录全部保留, 之后可以重新初始化.

## 已知限制

- 使用本项目的每台机器都需要 Node.js 22 或更高版本.
- 插件的 hook 在所有项目中触发, 每次写入类工具调用与每条消息都会启动一次 Node.js; 未初始化的项目中脚本立即结束.
- 守卫只检查写入类工具的目标路径, 不检查命令行: 编排会话用命令行改代码或装依赖时, 只靠技能规则约束.
- 回复的格式 (结论先行, 一行进展) 只靠技能规则, 没有校验.
- 一份切片文件由编排会话与实现方分段写. 脚本靠计划段的摘要发现它在实现期间被改动, 能发现, 不能阻止.
- 写计划前编排会话是否真的读了代码, 没有脚本把关; 计划中的错误由实现子代理的 "修正" 与验收兜底.
- "结构核对" 中除筛选器检查之外的各项由验收子代理判断, 不是确定性的.
- 筛选器检查用正则解析工程文件, 只覆盖常见写法; 带通配符或 MSBuild 宏的项不检查, 只统计数量.
- 交互式切片会占用编排会话的上下文; 靠 "结论立即写入文件" 与 "随时可换会话" 缓解.
- 实现子代理工作期间不能向你提问, 只能结束本次运行后由编排会话转达.
