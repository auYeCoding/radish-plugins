# project-navigator

[English](project-navigator.en.md) | 简体中文

[返回 WayPoint](../README.md)

引导一个大型项目从一句宏观需求开始, 经过问题域调研, 立项, 技术选型与最小可运行骨架, 再按纵向切片与里程逐步推进, 并处理中途的需求与方向变更.

调用本技能的会话只做规划, 记录, 发布工单与组织验收, 称为编排会话. 写代码, 选型与测试交给你另开的会话完成, 称为执行会话. 每一步都记录在仓库里, 换一个会话也能接着推进.

## 适用场景

- 从零开始一个需要几周或更久的项目, 想先把问题, 范围与主线想清楚再动手.
- 推进一个已有项目, 希望每次改动都有明确的目标, 判据与验收.
- 项目中途需求变了, 需要评估影响并调整计划.

以下场景不适合: 改一个错字, 修一个小 bug, 写一次性脚本. 这类小任务直接对 Claude 说即可.

## 使用前提

- [Git](https://git-scm.com): 项目必须是 Git 仓库, 且至少有一次提交. 还不是仓库时, 先运行 [`/waypoint:repo-init`](repo-init.md).
- [Node.js](https://nodejs.org) 22 或更高版本: 防护 hook 与记录脚本都用 Node.js 运行.
- 在项目根目录启动 Claude Code, 执行会话不使用 worktree.
- 选型阶段要能访问所选依赖的公开 git 仓库 (https): 验收时从原仓库取回源码核对证据.

## 调用方式

本技能只能显式调用, 不会被自然语言自动触发:

```text
/waypoint:project-navigator [init | check | uninstall | 初始需求]
```

- 不带参数: 查看当前进度, 按提示继续.
- `init`: 初始化项目.
- `check`: 对记录文档做一次体检.
- `uninstall`: 移除防护 hook, 保留全部记录.
- 其它文字: 作为初始需求, 例如 `/waypoint:project-navigator 做一个团队周报汇总工具`.

任何新会话调用本技能, 都会接管编排并从上次的位置继续. 原来的编排会话随之失去编排权限.

## 快速上手

以 "做一个团队周报汇总工具" 为例, 从一个只有 README 的新仓库开始. 每条回复末尾都有选项块, 你只需回复字母; 需要补充时在字母后写明, 例如 `B 第 3 条假设不对, 我们用飞书`.

### 第一次调用

1. 在项目根目录启动 Claude Code, 输入 `/waypoint:project-navigator 做一个团队周报汇总工具`.
2. 技能回复 "初始设置", 列出检查结果与将要写入的内容. 回复 `A`. 默认权限模式下, Claude Code 会请你批准一次初始化命令.
3. 自检通过后, 技能回复 "首次接入". 新项目回复 `A`, 已有代码的项目回复 `B`.

### 立项与主线

1. "需求理解" 分开列出你的原话与技能的假设. 假设不对时回复 `B` 并指出编号, 没问题回复 `A`.
2. 技能派调研子代理查同类产品, 使用人群, 行业做法与约束, 然后回复 "调研报告". 调研需要联网, Claude Code 可能请你批准; 一次调研通常要几分钟.
3. "头脑风暴" 每轮最多问 3 个问题, 常附候选答案与推荐项, 按编号回答即可. 技能认为可以收敛时, 会先征得你同意.
4. 技能写好项目简报, 回复 "产出确认". 之后的主线流程与推进路线, 同样用 "产出确认" 请你确认.

### 选型与第一张工单

1. "规范对照" 列出互相矛盾的规范条目, 由你逐条决定, 最后选定代码注释的语言.
2. 每个选型问题会发布一张工单, 回复 "工单发布". 收到后:
   1. 在项目根目录新开一个 Claude Code 会话, 粘贴回复中 "后续操作" 里的启动提示词.
   2. 执行会话读完工单后回复 "开工对齐". 核对它的计划, 回复 `A` 后它才开始动手.
   3. 执行会话做完后回复 "执行完成". 回复 `A` 让它写回执文件, 然后回到编排会话, 说一句 "执行完成".
3. 编排会话派验收子代理核对, 回复 "验收报告", 列出请你亲手验证的步骤. 验证无误回复 `A`.
4. 在 "确认提交" 中选择只提交, 提交并推送, 或交给 commit-message.

骨架与之后的每个切片, 都按同样的工单往返推进.

### 之后每次打开

在项目根目录新开会话, 输入不带参数的 `/waypoint:project-navigator`. 技能先比对记录与仓库, 再回复 "恢复进度", 写明上次停在哪里, 下一步做什么.

## 初始化

第一次调用时, 技能会检查环境并询问是否设置. 你选 A 后, 技能会:

1. 创建状态目录 `.navigator/`: 状态文件, 执行手册, 术语表与运行脚本.
2. 在 `.claude/settings.json` 中加入防护 hook 与放行规则, 保留你已有的配置. 放行规则另存一份到本机的 `.claude/settings.local.json`, 这份文件不入库.
3. 做一次自检: 故意尝试一次被禁止的写入, 确认防护 hook 已经生效.

`.navigator/` 与 `.claude/settings.json` 都要纳入版本控制, 回退或换机器时记录才不会丢失. 为此初始化时会检查项目的忽略规则: `.navigator/` 自带的 `.gitignore` 会把插件文件重新纳入, 以防项目里 `lib/`, `bin/` 之类的规则误伤; 如果有规则把 `.navigator/` 整个忽略了, 技能会在改动任何配置之前停下, 指出是哪条规则, 请你改掉后再初始化.

## 角色分工

| 角色       | 由谁担任                     | 做什么                                                     |
| ---------- | ---------------------------- | ---------------------------------------------------------- |
| 编排会话   | 调用本技能的会话             | 规划, 记录, 写工单, 组织验收, 体检; 只写 `.navigator/`     |
| 执行会话   | 你新开并粘贴启动提示词的会话 | 按一张工单调研, 选型, 写代码, 测试, 写回执; 不提交, 不推送 |
| 验收子代理 | 编排会话派出, 上下文全新     | 逐条核对判据, 运行你授权的测试, 交回结论与证据, 只读       |
| 调研子代理 | 编排会话在立项时派出         | 调研问题域: 同类产品, 使用人群, 行业做法, 约束, 只读       |
| 你         | 唯一拍板的人                 | 所有决定, 测试授权, 亲手验收, 选择提交方式                 |

这些边界由项目中的 hook 执行. 例如编排会话尝试写业务代码, 或执行会话在你确认计划之前改文件, 都会被拒绝并说明原因.

## 阶段

| 编号 | 阶段 | 做什么                                                                                       |
| ---- | ---- | -------------------------------------------------------------------------------------------- |
| 0    | 盘点 | 仅已有项目: 读仓库, 运行检查, 写现状报告                                                     |
| 1    | 立项 | 需求理解, 问题域调研, 调研报告, 苏格拉底式头脑风暴, 项目简报                                 |
| 2    | 主线 | 写出核心场景的最短操作路径, 拆成里程与切片, 登记风险                                         |
| 3    | 选型 | 对照工程规范, 选定注释语言; 执行会话按选型守则选型, 附库源码证据, 验收时从原仓库取回源码核对 |
| 4    | 骨架 | 第一个切片: 主线从头到尾跑通的最小版本                                                       |
| 5    | 切片 | 逐个切片推进; 每个里程结束时复查                                                             |
| 6    | 收尾 | 对照简报总体验收, 统计与复盘                                                                 |

需求变更可以在任何阶段插入, 处理完回到原来的位置. 跳过某个阶段要由你明确认可, 并写明原因.

## 一张工单的往返

1. **发布.** 编排会话写好工单, 回复 "工单发布", 其中有一段启动提示词.
2. **开工.** 你在项目根目录新开一个 Claude Code 会话, 粘贴启动提示词. 执行会话读执行手册与工单, 核对提交与前提, 做计划, 然后回复 "开工对齐". 其中的 "模块划分" 列出要新建和改动的模块, 以及入口文件改什么, 选 A 之前先看这一节. 你选 A 之后它才能改动业务文件.
3. **汇报.** 执行会话做完或受阻时回复 "执行完成" 或 "执行受阻", 你选择汇报方式:
   - A. 文档汇报: 执行会话写回执文件, 你回到编排会话告诉它已完成.
   - B. 消息汇报: 执行会话把回执直接发给编排会话. 两个会话都要开着.
4. **验收.** 编排会话派验收子代理逐条核对判据, 结论只有通过, 不通过, 未验证三种. 全部通过时, 再请你按步骤亲手验证; 有不通过或未验证的判据时, 工单直接判为不通过, 不会请你手工补验. 需要真实账号或有外部影响的测试, 会先征得你同意.
5. **提交.** 验收通过后, 你选择只提交, 提交并推送, 或交给 [`commit-message`](commit-message.md). 本轮业务改动与记录合成一条提交.

工单严格一张接一张. 同一切片连续两次验收不通过时, 编排会话会建议把切片拆小.

会改动代码的工单都带一条固定判据 "代码检查通过". 检查命令在选型阶段确定, 用各语言成熟的检查工具, 打开函数长度与复杂度规则, 检查范围不含 `.navigator/` 与 `.claude/`. 检查不通过, 工单就不能验收通过.

选型工单的回执用一张表列出源码证据: 能力, 仓库, 版本, 路径, 行号, 说明. 验收子代理运行 `evidence` 命令, 从原仓库按版本取回这些行逐条核对, 不依赖执行会话手中的副本. 选型工单不通过时, 编排会话会新开一张选型工单补正.

## 回复的样子

编排会话的每条回复都是同一种结构: 类型标题, 当前进展, 几个固定的小节, 一个选项块, 最后一段不超过 80 字的总结. 例如:

````markdown
# 工单发布

## 当前进展

- 当前阶段: 5/6 (切片)
- 当前里程: 1/3 (导出报表)
- 当前切片: 2/4 (导出 CSV)
- 当前工单: 0007

## 工单概况

- 文件路径: .navigator/orders/0007-export-csv/order.md
- 任务目标: 在报表页点击 "导出" 后下载当月数据的 CSV 文件
- 判据数量: 0003
- 计划要求: 必须先计划

## 后续操作

在仓库根目录新开一个 Claude Code 会话, 粘贴下面的启动提示词.

```markdown
执行工单 0007.
(其余内容省略)
```

```
[如何继续]

A. 已发工单, 等待回执.
B. 修改工单, 请提需求.
```

```text
<- ++++++++++ ->
工单 0007 已发布: 导出当月 CSV, 3 条判据. 请新开会话粘贴启动提示词.
```
````

你只需回复选项字母; 需要补充时在字母后写明.

## 记录文件

```text
.navigator/
├── state.json          进度, 编号与状态, 只能由脚本修改
├── bin/                运行脚本与参考文件, 由 init 复制
├── guide/executor.md   执行手册
├── plan/               简报, 术语表, 调研, 头脑风暴, 主线, 推进路线, 风险, 决策, 变更, 复查, 体检
└── orders/0007-export-csv/
    ├── order.md        工单
    ├── receipt.md      回执
    └── review.md       验收记录
```

- `plan/roadmap.md` 与 `plan/risks.md` 由脚本根据状态生成, 不要手改.
- `.navigator/drafts/` 是编排会话给脚本传中文内容用的草稿, 不入库.
- 每次记录变化, 脚本都会把 `.navigator/` 备份到 Git 的隐藏引用 `refs/navigator/snapshots`. 这个引用不进入分支历史, `git reset` 与 `git checkout` 都不会删除它.

## 回退与异常

每次调用时, 技能会比对记录中的提交, 当前提交与最近的备份:

- 你回退了提交, 切换了分支, 或绕过编排做了提交: 回复 "验收异常", 由你选择把记录对齐仓库, 纳入新提交, 或重新盘点.
- 你手工改了 `.navigator/` 下的文件: 由你选择保留改动, 或恢复备份.
- 分支被 squash 合并后, 记录内容不变, 技能能识别出来, 由你确认纳入.

处理完之前, 编排会话暂停其它操作, 避免新的备份掩盖异常.

## 工程规范

选型阶段开始时, 编排会话会对照三处规范: 插件自带的通用工程规范, 项目已有的规范 (`CLAUDE.md`, `AGENTS.md`, `.claude/rules/`, 格式化配置), 你本机的全局规范. 互相矛盾的条目由你逐条决定以哪边为准, 每次最多 3 条. 结果写入 `.claude/rules/engineering.md`, 项目中的所有会话都会自动加载.

代码注释的语言默认中文, 你可以改选英文或其它语言. 执行会话每次开工对齐时都会显示一行注释语言, 提醒你确认.

## 体检

运行 `/waypoint:project-navigator check`, 或在每个里程复查时自动进行. 体检分两层:

- 脚本检查: 结构是否符合模板, 句子与段落是否过长, 列表是否过长或过深, 是否有黑话, 比喻, 翻译腔, 句首没有名词的 "它", "这是" 等.
- 语义检查: 由阅读子代理检查自造简称, 未定义术语, 指代不明, 空话套话等.

体检结果列成问题清单, 由你决定逐条修正, 还是只记录在案.

## 常见问题

**为什么输入 "帮我规划一个项目" 没有触发本技能?**

本技能只能用 `/waypoint:project-navigator` 显式调用, 避免在普通对话中误启动一整套流程.

**编排会话能帮我写一段代码吗?**

不能. 编排会话写业务代码会被 hook 拒绝. 需要改代码时, 编排会话会发布工单, 由执行会话完成.

**我能直接在编排会话里说 "帮我装个依赖" 吗?**

不能. 装依赖, 构建, 运行业务脚本都属于实现, 同样会被拒绝.

**多个工单能并行吗?**

不能. 工单严格一张接一张, 保证每张工单的基准提交与验收结果都是确定的.

**怎样停止使用?**

运行 `/waypoint:project-navigator uninstall`. hook 与放行规则会被移除, `.navigator/` 中的记录全部保留, 之后可以重新初始化.

## 已知限制

- 使用本项目的每台机器都需要 Node.js 22 或更高版本, 否则防护 hook 无法运行.
- 已初始化的项目中, 每次工具调用都会多启动一次 Node.js, 本机实测约 70 毫秒.
- 朴素中文等写作要求主要靠提示词与体检保证; 脚本检查是近似的, 可能漏报或误报.
- 版式不合格的回复会被打回重写一次, 但不合格的那一版仍会留在屏幕上.
- 用命令行改文件的操作只能粗略检查; hook 也不限制你本人在编辑器中的操作.
- 消息汇报要求编排会话与执行会话在同一台机器上同时开着.
- 源码证据只支持公开 git 仓库; 没有公开仓库的依赖会判为未验证, 由你决定是否接受这个风险.
