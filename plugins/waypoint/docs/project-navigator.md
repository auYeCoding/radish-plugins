# project-navigator

[English](project-navigator.en.md) | 简体中文

[返回 WayPoint](../README.md)

引导一个大型项目从一句宏观需求开始, 经过问题域调研, 立项, 技术选型与最小可运行骨架, 再按纵向切片与里程逐步推进, 并处理中途的需求与方向变更.

调用本技能的会话只做规划, 记录, 发布工单与组织验收, 称为编排会话. 写代码, 构建与测试由编排会话在后台派出的执行子代理完成, 验收由验收子代理在全新上下文中完成. 每一步都记录在仓库里, 换一个会话也能接着推进.

## 适用场景

- 从零开始一个需要几周或更久的项目, 想先把问题, 范围与主线想清楚再动手.
- 推进一个已有项目, 希望每次改动都有明确的目标, 判据与验收.
- 项目中途需求变了, 需要评估影响并调整计划.

以下场景不适合: 改一个错字, 修一个小 bug, 写一次性脚本. 这类小任务直接对 Claude 说即可.

## 使用前提

- [Git](https://git-scm.com): 项目必须是 Git 仓库. 还不是仓库时, 先运行 [`/waypoint:repo-init`](repo-init.md).
- [Node.js](https://nodejs.org) 22 或更高版本: hook 与命令都用 Node.js 运行.
- 在项目根目录启动 Claude Code.
- 选型阶段要能访问所选依赖的公开 git 仓库 (https): 验收时从原仓库取回源码核对证据.

## 调用方式

本技能只能显式调用, 不会被自然语言自动触发:

```text
/waypoint:project-navigator [init | check | uninstall | 初始需求]
```

- 不带参数: 查看当前进度, 按提示继续.
- `init`: 初始化项目, 或升级旧版本初始化的项目.
- `check`: 对记录文档做一次体检.
- `uninstall`: 停用本技能, 保留全部记录.
- 其它文字: 作为初始需求, 例如 `/waypoint:project-navigator 做一个团队周报汇总工具`.

任何会话调用本技能, 都按记录中的状态继续, 不需要接管或登记. 在桌面应用中回退或编辑消息之后, 会话照常继续.

## 快速上手

以 "做一个团队周报汇总工具" 为例, 从一个只有 README 的新仓库开始. 每条回复第一行是一句结论, 末尾是选项块, 你只需回复字母; 在 Claude 桌面应用中, 两个选项的回复还会在输入框上方显示两个按钮, 点一下等于回复对应的选项. 需要补充时在字母后写明, 例如 `B 第 3 条假设不对, 我们用飞书`.

### 第一次调用

1. 在项目根目录启动 Claude Code, 输入 `/waypoint:project-navigator 做一个团队周报汇总工具`.
2. 技能回复 "初始设置", 列出检查结果与将要写入的内容. 回复 `A`.
3. 技能初始化后调用 [`commit-message`](commit-message.md) 提交写入的文件, 然后回复 "首次接入". 新项目回复 `A`, 已有代码的项目回复 `B`.

### 立项与主线

1. "需求理解" 分开列出你的原话与技能的假设. 假设不对时回复 `B` 并指出编号, 没问题回复 `A`.
2. 技能派调研子代理查同类产品, 使用人群, 行业做法与约束, 然后回复 "调研报告". 调研需要联网, 通常要几分钟.
3. 你可以选 `A` 进入头脑风暴, 一起把问题, 人群, 范围想清楚; 已经想清楚或项目不大时选 `B`, 技能直接按调研结果写简报草稿给你改.
4. 技能写好项目简报, 回复 "产出确认". 之后的主线流程与推进路线, 同样用 "产出确认" 请你确认.
5. 每进入一个新阶段, 上一阶段写下的记录还没提交时, 技能会调用 commit-message 提交; 记录之外还有改动时, commit-message 会列出来问你.

### 选型与第一张工单

1. "规范对照" 列出互相矛盾的规范条目, 由你逐条决定, 最后选定代码注释的语言.
2. 技能可以根据调研给出技术建议; 语言, 框架, 核心库这类关键依赖, 写成选型工单核实.
3. 工单写好后, 技能回复 "工单审阅": 一句话目标, 需要你拍板的事, 明确不做的事, 以及为什么这样划分工单. 无误回复 `A`, 需要修改回复 `B` 并写明要求. 工单文件的完整内容在审阅要点下方给出的路径中.
4. 你选 `A` 后, 技能在后台派出执行子代理, 回复 "工单执行". 你可以去做别的事, 子代理做完时编排会话会自动接着处理.
5. 执行子代理受阻时 (例如需要你提供账号, 或在几种做法中选一种), 技能回复 "受阻处理" 请你决定; 处理完后子代理接着做.
6. 做完后技能派验收子代理核对, 回复 "验收报告". 全部通过时选 `A` 提交, 选 `B` 提交并推送, 发现问题选 `C`. 选型工单则由你决定采用还是换方案.

骨架与之后的每个切片, 都按同样的工单往返推进. 正常情况下, 一张工单只需要你做两次决定: 审阅时发布, 验收时通过并提交.

### 之后每次打开

在项目根目录新开会话, 输入不带参数的 `/waypoint:project-navigator`. 技能回复 "恢复进度", 写明上次停在哪里, 下一步做什么.

## 初始化

第一次调用时, 技能会检查环境并询问是否设置. 你选 A 后, 技能会:

1. 创建状态目录 `.navigator/`: 状态文件, 术语表, 以及计划与工单的目录.
2. 在 `.claude/settings.json` 中加入插件命令与记录写入的放行规则, 保留你已有的配置. 放行规则另存一份到本机的 `.claude/settings.local.json`, 这份文件不入库.

hook 由插件提供, 不写进项目配置; 没有初始化的项目中, 插件的 hook 什么也不做.

`.navigator/` 与 `.claude/settings.json` 都要纳入版本控制, 换机器或回退时记录才不会丢失. `.navigator/` 自带的 `.gitignore` 会把记录文件重新纳入; 初始化与每次调用技能时, 都按 Git 的全部忽略规则检查记录文件, 如果有规则把 `.navigator/` 整个忽略, 或忽略了 `.claude/` 下的配置, 技能会停下并指出是哪条规则.

### 从 0.x 升级

1.0.0 改了很多做法, 0.x 初始化的项目需要升级一次. 更新插件后调用技能, 技能提示项目由旧版本初始化, 回复 "初始设置"; 你选 A 后, 技能会:

- 从 `.claude/settings.json` 中移除旧的项目级 hook 与旧放行规则, 写入新的放行规则.
- 删除 `.navigator/bin/` 与 `.navigator/guide/` 下的副本, 清理本机 `.git/navigator/` 中旧的会话登记与快照记录.
- 已发布但还没有回执的工单撤回为起草中, 重新审阅后由执行子代理处理.

编排记录全部保留. 升级后的改动由 commit-message 提交.

## 角色分工

| 角色       | 由谁担任                 | 做什么                                                 |
| ---------- | ------------------------ | ------------------------------------------------------ |
| 编排会话   | 调用本技能的会话         | 规划, 记录, 写工单, 组织验收, 体检; 只写 `.navigator/` |
| 执行子代理 | 编排会话在后台派出       | 按一张工单写代码, 测试, 写回执; 不提交, 不推送         |
| 验收子代理 | 编排会话派出, 上下文全新 | 逐条核对判据, 运行代码检查与测试, 交回证据, 只读       |
| 调研子代理 | 编排会话在立项时派出     | 调研问题域: 同类产品, 使用人群, 行业做法, 约束, 只读   |
| 你         | 唯一拍板的人             | 所有决定: 发布工单, 处理受阻, 决定验收结果与提交方式   |

hook 只守几条边界: 编排会话不能写 `.navigator/` 之外的文件; 状态文件与脚本生成的视图只能由插件命令修改; 执行子代理在 `.navigator/` 下只能写本工单的回执与证据文件, 运行检查与分析工单不能改业务文件; 验收子代理不能写文件. 其余靠技能规则, 不拦截.

### 权限确认

执行子代理在后台写文件时, 默认权限模式下, 写入确认会弹在编排会话中. 一张工单常常要写很多文件, 执行期间可以把会话切到 "Accept edits" (自动接受文件编辑), 免得反复确认. 是否切换由你决定.

## 阶段

| 编号 | 阶段 | 做什么                                                                                 |
| ---- | ---- | -------------------------------------------------------------------------------------- |
| 0    | 盘点 | 仅已有项目: 读仓库, 运行检查, 写现状报告                                               |
| 1    | 立项 | 需求理解, 问题域调研, 调研报告, 头脑风暴 (可跳过), 项目简报                            |
| 2    | 主线 | 写出核心场景的最短操作路径, 拆成里程与切片, 登记风险                                   |
| 3    | 选型 | 对照工程规范, 选定注释语言; 关键依赖由执行子代理逐条回答能否实现需求, 附源码证据或测试 |
| 4    | 骨架 | 第一个切片: 主线从头到尾跑通的最小版本                                                 |
| 5    | 切片 | 逐个切片推进; 每个里程结束时复查                                                       |
| 6    | 收尾 | 对照简报总体验收, 统计与复盘                                                           |

需求变更可以在任何阶段插入, 处理完回到原来的位置. 跳过某个阶段要由你明确认可, 并写明原因.

## 一张工单的往返

1. **审阅.** 编排会话写好工单, 回复 "工单审阅", 只列审阅要点与工单文件路径. 你选 A 后工单才能发布; 选 A 之后工单再有改动, 要再审阅一次.
2. **执行.** 编排会话在后台派出执行子代理, 回复 "工单执行". 执行子代理核对提交与前提, 做计划, 实施, 自检, 写回执. "工单执行" 不需要你选择, 所以没有选项块; 中途想停下改工单时, 回复 "停止执行".
3. **受阻.** 执行子代理遇到规格问题, 需要你操作或决定时, 写回执说明并停下. 编排会话回复 "受阻处理"; 你处理完而工单不用改时, 原来的子代理接着做, 不需要重新审阅.
4. **验收.** 编排会话派验收子代理逐条核对判据, 结论只有通过, 不通过, 未验证三种. 验收子代理在后台核对时, 编排会话先回复 "工单验收" (没有选项块), 结果回来后回复 "验收报告"; 编排会话的建议只写在其中的 "处理建议" 一节. 回复 "验收报告" 时:
   - 全部通过: 你可以按 "人工验收" 的步骤亲手验证, 然后选择提交, 或提交并推送.
   - 有不通过: 编排会话先判断原因, 工单太大就拆小, 否则发修复工单.
   - 只有未验证: 由你决定接受现状并提交, 或补正; 接受的未验证判据登记为风险.
5. **提交.** 验收通过后, 编排会话调用 commit-message, 本轮业务改动与记录合成一条提交. 有回执之外的改动时, commit-message 会列出来问你是否纳入.

工单严格一张接一张. 工单的大小由编排会话按 "执行一次能做完, 验收能看清, 做完能运行, 高风险部分单独成工单" 判断, 默认一个切片一张, 审阅要点中写明划分依据.

运行检查工单与分析工单只产出记录: 运行检查按已有命令构建, 运行, 测试并记下结果; 分析用于逆向, 调研等需要动手查证的任务, 产出文档与证据脚本. 两者的执行子代理只能写回执与工单文件夹的 `artifacts/`; 不需要代码检查命令, 选型之前也能发. 验收不通过时重发同类工单.

会改动代码的工单都带一条固定判据 "代码检查通过". 检查命令在选型阶段确定, 用各语言成熟的检查工具, 打开函数长度与复杂度规则, 检查范围不含 `.navigator/` 与 `.claude/`.

需要真实账号, 会产生费用或外部副作用的测试, 执行子代理不运行, 写进回执的 "外部影响"; 验收子代理也不重跑, 按回执中的输出判断. 判据要靠抓包之类的 MCP 工具确认时, 执行子代理在回执中写明工具与查找位置, 验收子代理用同一工具做只读查询.

选型只回答 "选定的库能不能实现工单列出的每条需求". 回执中每条需求一行, 结论为能或不能, 依据是库的源码 (仓库, 版本, 路径, 行号), 源码看不出来时是临时测试. 验收子代理运行 `evidence` 命令从原仓库按版本取回源码核对. 选型工单由你决定采用或换方案; 没核对通过的需求登记为风险.

## 回复的样子

编排会话的每条回复都是同一种结构: 类型标题, 一行结论, 一行进展, 几个小节, 最后一个选项块 (不需要你选择的回复没有选项块, 例如 "工单执行"). 例如:

````markdown
# 工单审阅

结论: 工单 0007 补齐 HTTP/2 指纹, 需要你决定是否在仓库内维护 fhttp 补丁.

阶段 5/6 (切片) · 里程 3/5 (引擎跑通主线) · 切片 4/10 (HTTP/2 指纹) · 工单 0007 (起草中)

## 审阅要点

- 任务目标: 调用方用指纹配置控制 HTTP/2 层的全部维度
- 需要决定: 在仓库内维护 fhttp v0.7.3 的补丁, 实现伪头不索引
- 明确不做: HTTP/1.1 与头部大小写, 留给切片 0005
- 粒度依据: 整个切片一张工单, 改动集中在适配层与补丁
- 工单文件: .navigator/orders/0007-http2-fingerprint/order.md

```
[是否发布]

A. 发布工单, 开始执行.
B. 需要修改, 请提需求.
```
````

结论一行就能看出要你做什么; 细节在后面, 需要时再看. 进展行末尾的括号是工单所处的环节 (起草中, 执行中, 受阻, 验收中, 待你决定), 连续几条回复靠它区分先后.

## 记录文件

```text
.navigator/
├── state.json          进度, 编号与状态, 只能由插件命令修改
├── plan/               简报, 术语表, 调研, 头脑风暴, 主线, 推进路线, 风险, 决策, 变更, 复查, 体检
└── orders/0007-export-csv/
    ├── order.md        工单
    ├── receipt.md      回执
    ├── artifacts/      执行子代理留下的证据文件, 例如抓包原文, 复现脚本 (需要时才有)
    └── review.md       验收记录
```

- `plan/roadmap.md` 与 `plan/risks.md` 由插件命令根据状态生成, 不要手改.
- `.navigator/drafts/` 是编排会话给命令传中文内容用的草稿, 不入库.
- 你对工单审阅的选择登记在本机的 `.git/navigator/` 中, 不入库.
- 记录都在 Git 中. 回退或手工改了记录后, 技能按当前记录继续; 记录与实际情况对不上时, 技能会说明并请你决定以哪边为准.

## 工程规范

选型阶段开始时, 编排会话会对照三处规范: 插件自带的通用工程规范, 项目已有的规范 (`CLAUDE.md`, `AGENTS.md`, `.claude/rules/`, 格式化配置), 你本机的全局规范. 互相矛盾的条目由你逐条决定以哪边为准, 每次最多 3 条. 结果写入 `.claude/rules/engineering.md`, 项目中的所有会话都会自动加载. 代码注释的语言默认中文, 你可以改选英文或其它语言.

## 体检

运行 `/waypoint:project-navigator check`, 或在每个里程复查时自动进行. 体检分两层:

- 脚本检查: 结构是否符合模板, 句子与段落是否过长, 列表是否过长或过深, 是否有黑话, 比喻, 翻译腔, 句首没有名词的 "它", "这是" 等.
- 语义检查: 由阅读子代理检查自造简称, 未定义术语, 指代不明, 空话套话等.

体检结果列成问题清单, 由你决定逐条修正, 还是只记录在案.

## 常见问题

**为什么输入 "帮我规划一个项目" 没有触发本技能?**

本技能只能用 `/waypoint:project-navigator` 显式调用, 避免在普通对话中误启动一整套流程.

**编排会话能帮我写一段代码吗?**

不能. 编排会话写 `.navigator/` 之外的文件会被拒绝. 需要改代码时, 编排会话会发布工单, 由执行子代理完成.

**执行子代理在工作, 我能继续和编排会话说话吗?**

能. 子代理在后台运行, 你可以问问题或处理别的事; 子代理做完时编排会话会被通知并接着处理.

**我关掉了编排会话, 执行子代理的工作会怎样?**

子代理属于启动它的会话. 新会话调用技能后, 回执已写入就照常验收; 没写入时, 编排会话会重新派出执行子代理.

**技能本身出了问题怎么办?**

脚本会自己发现一部分问题: 命令或 hook 的内部错误, 不自洽的状态, 照 "下一动作" 运行却被拒绝的命令, 以及状态不变时反复给出的同一个 "下一动作". 编排会话自己发现规则对不上时也会上报. 这时它回复 "问题报告": 报告写入 `.navigator/drafts/reports/` (不入库), 全文放在回复的一个代码块中, 复制后交给插件的维护者即可. 报告只写遇到的情况: 环境, 状态摘要, 异常记录与经过; 不写原因推测与处理建议, 不含工单正文与业务代码, 本机路径会被隐去. 流程还能继续时选 `A` 继续; 无法继续时 (命令内部错误或状态不自洽) 编排会暂停, 等问题修复后再继续.

**我想让编排会话写一段流程之外的内容, 可以吗?**

可以. 直接提出要求, 编排会话回复 "自由答复", 在 "答复内容" 中按你要求的格式撰写, 可以含代码块. 看完选 `A` 回到流程.

**多个工单能并行吗?**

不能. 工单严格一张接一张, 保证每张工单的基准提交与验收结果都是确定的.

**怎样停止使用?**

运行 `/waypoint:project-navigator uninstall`. 放行规则会被移除, 插件的 hook 在本项目中不再生效, `.navigator/` 中的记录全部保留, 之后可以重新初始化.

## 已知限制

- 使用本项目的每台机器都需要 Node.js 22 或更高版本.
- 插件的 hook 在所有项目中触发, 每次写入类工具调用与每条消息都会启动一次 Node.js; 未初始化的项目中脚本立即结束, 本机实测约 70 毫秒.
- 守卫只检查写入类工具的目标路径, 不检查命令行: 编排会话用命令行改代码或装依赖时, 只靠技能规则约束.
- 朴素中文等写作要求主要靠提示词与体检保证, 回复结束时不按写作规则打回; 脚本检查是近似的.
- 结构不合格的回复会被打回重写一次, 但不合格的那一版仍会留在屏幕上.
- 执行子代理工作期间不能向你提问, 需要你决定的事只能以受阻结束后再处理.
- 源码证据只支持公开 git 仓库; 没有公开仓库的依赖会判为未验证, 由你决定是否接受这个风险.
- MCP 取证工具查看的是外部工具中当时的记录. 验收前记录被清空, 或工具没有运行, 相关判据会判为未验证.
