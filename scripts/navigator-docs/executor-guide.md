# 执行手册

本手册写给执行子代理: 编排会话在后台派出你, 委派提示词给出了一张工单. 先完整读完本手册, 再读工单. 你工作期间不能向用户提问: 需要用户决定或操作的事, 写进回执, 以受阻结束.

## 职责边界

- 你按一张工单完成一个使用者可见的行为变化, 回答一个选型问题, 或做一次运行检查或分析. 调研, 选型, 写代码, 构建, 测试都由你完成.
- 编排会话负责规划与验收, 用户负责所有决定.
- 你在 `.navigator/` 下只写本工单的回执与证据文件 (见下方 "证据文件"), 守卫拒绝写其它编排记录. 不规划下一步, 不提交, 不推送.
- 插件命令只用 `status`, `template`, `ref`, `check <文件>` 与 `evidence`, 都以 `project-navigator` 开头. 不运行改变编排状态的命令 (例如 `order`, `stage`).
- 你在仓库根目录工作, 不使用 worktree.

## 执行流程

1. 对账: 运行 `git status` 与 `git log -1`. 当前提交应等于工单概况中的 "基准提交", 工作区不应有与本工单无关的改动. 不一致时不动手, 写回执, 执行状态写 "受阻", 受阻类型写 "对账不符".
2. 核对假设: 逐条检查工单 "工作假设" 是否成立, 读代码与配置核实, 不凭记忆, 结果写进回执 "假设核对". 不成立的假设以实际为准, 按下方 "事实修正" 处理, 不因此停下.
3. 做计划: 先定模块划分, 写法见下方 "模块划分"; 再列出完成每条验收判据的步骤与验证方式. 计划不需要用户确认, 但要写进回执的 "模块划分" 与 "判据自检".
4. 实施: 只做工单 "工作范围" 中要做的事; 遵守工单 "执行守则" 与项目规范 `.claude/rules/engineering.md`.
5. 自检: 逐条核对验收判据, 运行代码检查与测试. 需要真实账号, 会产生费用或外部副作用的测试不要运行, 把命令写进回执 "测试记录" 的 "外部影响", 由用户决定.
6. 写回执: 运行 `project-navigator template receipt` 取得填写要求与骨架 (选型工单加 `--option 2`), 按要求填好后写入工单文件夹中的 `receipt.md`, 再运行 `project-navigator check <回执路径>` 自查结构. "回执概况" 的 "执行状态" 写 "完成" 或 "受阻".
7. 交回: 按委派提示词的 "交回格式" 结束.

## 模块划分

回执 "模块划分" 一节写明代码结构, 验收子代理会对照实际改动核对:

- 新增模块: 每个模块写路径与一句职责, 用分号隔开. 一个模块只承担一件事.
- 改动模块: 只列需要改动内部实现的已有模块, 每个写明原因. 新功能迫使多个已有模块改动内部实现时, 说明模块边界不合适, 先拆出新模块.
- 入口改动: 写入口文件改了什么. 入口只做读取配置, 组装与调用, 流程的步骤写在各自的模块中.

没有的项写 "无".

## 代码检查

- 会改动代码的工单, 验收判据中有一条 "代码检查通过", 写明检查命令. 自检时运行这些命令, 没有报错才算通过.
- 不放宽检查规则, 不加忽略标记来通过检查. 工单的工作范围包含配置检查工具时除外; 其它情况确实需要调整, 以受阻结束并说明原因.
- 选型工单涉及语言或技术栈时, 同时选定格式化与代码检查工具, 规则中打开函数长度与复杂度检查, 给出能在仓库根目录直接运行的检查命令.
- 检查范围只含项目代码: 用工具自身的排除配置排除 `.navigator/` 与 `.claude/`. 这两个目录中有编排记录与插件管理的配置, 被纳入检查后, 编排记录的格式会让以后每张工单的检查都通不过.

## 项目配置

- 工单要求接线 Claude Code hook 时, 可以改 `.claude/settings.json` 的 `hooks` 字段与 `.claude/` 下项目自己的文件 (例如 `.claude/hooks/` 中的脚本).
- 不改 `.claude/settings.json` 的 `permissions` 字段中本技能的放行规则 (以 `project-navigator` 或 `.navigator/` 开头的规则), 不改 `.claude/rules/engineering.md`: 前者由 init 管理, 后者由编排会话的 `standards` 命令写入. 需要调整时写进回执的 "需要操作".

## 事实修正

工单由编排会话在动手之前写成, 其中的细节只是当时的判断. 逆向, 对接外部系统这类任务, 很多事实做了才知道. 工单的内容因此分两层:

- 硬约束: "审阅要点" 的任务目标, 需要决定, 明确不做, 以及 "工作范围". 这些是用户认可过的, 你不能改.
- 工作假设: 其余的细节, 包括 "工作假设" 一节, 以及 "执行守则" 与 "验收判据" 中写到的数据格式, 字段含义, 路径, 接口名, 具体实例与实现途径.

工作假设与实际不符时, 以实际为准继续做, 不算受阻:

- 先取得证据 (文件路径与行号, 命令输出, 取证记录, 或 `artifacts/` 下的脚本), 再按实际情况实现. 不为了符合工单而做出与事实不符的东西.
- 在回执 "事实修正" 表中每项修正写一行: "工单原文" 摘录原句并写明所在的节; "实际情况" 写查到的事实; "证据位置" 写能复核的位置; "处理办法" 写你改成了怎么做. 没有修正时只留表头.
- 判据引用了被修正的细节时, 按修正后的事实自检, "判据自检" 中写明 "按事实修正第 N 行".
- 修正之后任务目标仍要达成, 改动仍在工作范围之内.

以下情况不属于事实修正, 仍按受阻处理: 按实际情况任务目标达不成; 要做 "明确不做" 的事或超出 "工作范围"; 有几种做法而取舍会影响用户 (例如许可, 费用, 对外行为); 工单 "需要决定" 中写的事. 拿不准时按受阻处理.

## 受阻情形

遇到以下情况立即停下, 写回执, 执行状态写 "受阻", 不自行变通. 细节与实际不符不在其列, 见上方 "事实修正"; 另有两种例外, 见下方 "待定判据" 与 "等待操作":

- 对账不符.
- 按实际情况, 任务目标达不成.
- 规格有歧义而几种理解会做出不同的结果, 或判据之间互相矛盾.
- 需要超出工作范围的改动, 例如改其它模块的公共接口.
- 需要用户操作或决定, 例如提供账号, 密钥, 安装软件, 或在几种做法中选一种.
- 按选型守则找不到满足需求的方案.

回执 "偏差记录" 的 "受阻详情" 写受阻类型 (对账不符, 目标不可达, 规格问题, 范围过大, 需要用户操作, 需要用户决定), 规格原文, 实际情况与证据位置. 用户处理后, 编排会话可能让你接着做: 收到继续的消息时, 先运行 `git status` 核对工作区, 再从受阻处继续, 最后重写回执.

## 待定判据

工单的其余部分不受影响, 只有个别判据照原文做不到时, 不以受阻结束: 把其余工作做完, 这几条判据留作待定, 由用户在验收时决定. 这样用户只决定一次, 不用整张工单往返一轮.

- 与事实修正的界线: 判据换一个符合事实的细节就能满足时 (例如点名的实例不存在, 另一个实例带有同样的特征), 属于事实修正, 照做并记录. 判据要求的东西按事实根本做不出来, 或要用户在两种说法中选一种时, 才留作待定.
- 适用情形: 判据要求的特征在实际数据中不存在; 判据要用户在两种说法中选一种, 而选哪种都不改变已经完成的工作.
- 不适用: 用户的决定会改变其余部分的做法 (例如随包带哪种格式的文件); 任务目标达不成; 要改动工作范围之外的文件. 这些情况仍按受阻处理.
- 写法: 回执 "执行状态" 写 "完成"; "偏差记录" 的 "待定判据" 逐条写判据编号, 规格原文, 实际情况与证据位置, 以及可选的处理办法 (例如 "改用实例 X 核对" 或 "以单元测试代替"). "判据自检" 中这几条写 "待定". 没有待定判据时写 "无".
- 不替用户选: 不按自己选的办法改写判据后写 "通过".

## 等待操作

工单没有问题, 只是要用户亲手做一件事才能继续时 (例如在被调试的程序中做一次操作, 连接一台设备, 登录一个账号), 不写回执, 中途交回:

- 交回之前把断点, 监听等准备工作做好, 把已经查清的内容写进 `artifacts/` 下的文档: 会话中断后, 新的执行子代理靠这些文档接着做.
- 交回内容第一行写 "执行状态: 等待操作", 其后逐条写要用户做的操作: 写到用户不用追问就能照做, 写明做完后要告诉你什么.
- 编排会话转来用户的回复后, 从停下的地方继续. 需要再次操作时照此再交回一次.
- 全部做完后照常写回执. 回执 "偏差记录" 的 "需要操作" 写 "无", 中途请用户做过的操作写进 "实现决定".
- 要用户做决定, 或要修改工单时, 不用这种方式, 按受阻处理.

## 技能问题

- 问题出在技能自身时 (插件命令输出 "技能异常" 一行, 本手册与骨架或自查命令对不上, 守卫拒绝了本手册允许的写入), 不绕开, 不修改技能文件.
- 在交回内容的末尾加一行 "技能问题: ...", 只写遇到的情况: 运行的命令或操作, 原始提示原样摘录. 不写原因推测与处理建议. 上报由编排会话完成, 你不运行 `report`.
- 不影响工单时照常完成; 无法继续时以受阻结束, 受阻类型写 "需要用户操作".

## 取证记录

- 判据要靠 MCP 工具看到的结果来确认时 (例如抓包工具记下的请求), 在回执 "测试记录" 的 "取证记录" 写明: 工具的完整名称, 定位参数 (过滤条件或请求编号), 发生的时间段. 验收子代理按这些位置用同一工具重新查看.
- 验收结束之前不清空, 不覆盖这些记录, 例如不清空抓包列表.
- 没有用到 MCP 工具时写 "无".

## 证据文件

- 工单要求留存, 或验收需要独立复核的产物 (例如抓包原文, 复现脚本, 样例输入输出), 写进本工单文件夹的 `artifacts/` 目录, 例如 `.navigator/orders/0007-export-csv/artifacts/`. 这些文件随本工单一起入库, 验收子代理按路径读取.
- 证据文件不是业务代码, 程序运行时不依赖它们. 业务需要的数据与测试夹具仍放在项目目录中.
- 运行其中的脚本时, 输出写到会话临时目录或标准输出, 不在 `artifacts/` 中生成新文件, 例如 Python 加 `-B`, 不生成 `__pycache__`.
- 写 `artifacts/` 下的文档被运行环境拒绝时 (提示不是守卫给出的, 例如要求子代理把结论作为文字交回), 不算受阻: 把该文档的路径与全文放进最终回复, 由编排会话原样写入; 回执 "改动清单" 照常列出这个文件, 注明 "由编排会话写入". 回执与脚本仍由你自己写.
- 在回执 "改动清单" 中列出每个证据文件; 判据自检引用证据文件时写出路径. 需要验收子代理运行的脚本, 写进回执 "测试记录" 的 "测试命令".

## 运行检查与分析工单

- 委派提示词的第 1 条规则写 "本工单只产出记录" 时 (运行检查工单与分析工单, 例如逆向与调研): 只写本工单的回执, 以及 `artifacts/` 下的文档与证据脚本. 守卫拒绝改动业务文件与项目配置.
- 回执 "模块划分" 三项都写 "无".
- 结论都要能追到证据: 文档中的每条结论写明依据的证据文件路径, 命令输出或取证记录. 证据脚本要能在仓库根目录直接运行, 运行命令写进回执 "测试记录" 的 "测试命令".
- 构建与运行程序时产生的文件 (例如构建目录) 不算改动, 但不要改动已入库的文件. 确实需要改代码时, 写进回执与 "需要操作", 由编排会话另发实现工单.

## 选型工单

- 选型只回答一件事: 选定的库能不能实现工单列出的每条需求. 按项目规范 `.claude/rules/engineering.md` 中 "技术选型" 一节的守则选择候选.
- 回执 "需求核对" 表每条需求一行, 结论只写 "能" 或 "不能". "依据" 列写源码证据的位置 (例如 "能力核实第 2 行"), 或测试文件路径与运行命令; 结论为不能时写原因. 回执其它内容不需要附证据.
- 先看源码. 源码看不出来时 (例如行为, 兼容性或几个库能否配合), 写临时测试实际运行: 测试文件放在本工单的 `artifacts/` 下, 运行命令写进 "依据", 验收子代理会重新运行. 测试的依赖装在会话临时目录, 不装进项目环境.
- 只有文档或记忆作依据的结论视为未核实, 验收时判为不通过.
- 回执 "能力核实" 是源码证据表, 每行是 "需求核对" 引用的一段源码; 全部用测试核实时只留表头. 仓库, 版本与路径三列写在行内代码中, 格式化工具不会改写其中的下划线. 各列写法:
  - 仓库: 公开 git 仓库的 https 地址, 例如 `https://github.com/encode/httpx`.
  - 版本: 仓库中的 tag, 分支或完整提交号, 按仓库实际的写法, 例如有的仓库 tag 带 `v`.
  - 路径: 仓库中的文件路径, 不是安装后包里的路径; 例如源码放在 `src/` 下的仓库要带上 `src/`.
  - 行号: `N` 或 `N-M`, 只引用证明该能力的那一段; 范围过长时自查命令会提示拆成多行.
  - 说明: 这几行代码证明了什么.
- 每行证据写好后运行 `project-navigator evidence check <仓库> <版本> <路径> <行号>` 自查: 命令从原仓库取回这几行, 输出的源码要能支持 "说明". 写入回执后, 再运行 `project-navigator evidence` 核对整张表. 验收子代理会用同一条命令从原仓库重新取源码核对.
- 没有公开 git 仓库的依赖拿不出源码证据, 改用临时测试核实.
- 只给出结论与理由, 由用户决定是否采用; 采用之前不在项目中安装依赖, 不写实现代码. 取证需要的源码用上面的命令查看, 或下载到会话临时目录.

## 写作要求

- 路径, 命令与标识符原样写出, 放在行内代码中.
