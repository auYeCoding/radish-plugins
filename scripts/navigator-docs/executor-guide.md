# 执行手册

本手册写给执行会话: 你由用户在仓库根目录新开, 用户粘贴了一张工单的启动提示词. 先完整读完本手册, 再读工单.

## 职责边界

- 你按一张工单完成一个使用者可见的行为变化, 或回答一个选型问题. 调研, 选型, 写代码, 构建, 测试都由你完成.
- 编排会话负责规划与验收, 用户负责所有决定.
- 你不改 `.navigator/` 下除本工单回执之外的文件, 不规划下一步, 不提交, 不推送. 这些操作会被守卫拒绝.
- 你必须在仓库根目录工作, 不使用 worktree: worktree 中看不到尚未入库的工单.

## 执行流程

读完本手册与工单文件 `order.md` 之后, 按以下步骤进行:

1. 对账: 运行 `git status` 与 `git log -1`. 当前提交应等于工单概况中的 "基准提交", 工作区不应有与本工单无关的改动. 不一致时不动手, 回复 "执行受阻", 受阻类型写 "对账不符".
2. 核对前提: 逐条检查工单 "前提假设" 是否成立, 读代码与配置核实, 不凭记忆. 不成立时回复 "执行受阻", 受阻类型写 "前提不符".
3. 做计划: 工单 "计划要求" 为 "必须先计划" 时, 进入计划模式写出计划, 附覆盖表 (验收判据, 完成它的步骤, 验证方式); 为 "免除计划" 时, 直接列出改动点.
4. 开工对齐: 回复 "开工对齐", 然后停下等用户选择. 用户选 A 之前不改动任何业务文件, 守卫会拒绝. 用户选 B 时, 按用户描述的问题调整计划, 再次回复 "开工对齐".
5. 实施: 只做工单 "工作范围" 中要做的事; 遵守工单 "执行守则" 与项目规范 `.claude/rules/engineering.md`.
6. 自检: 逐条核对验收判据, 运行测试. 需要真实账号, 会产生费用或外部副作用的测试, 先按下方 "测试边界" 询问.
7. 汇报: 回复 "执行完成" 或 "执行受阻", 由用户选择汇报方式:
   - A. 文档汇报: 运行 `node .navigator/bin/runtime/navigator.mjs template receipt` 取得回执骨架 (选型工单加 `--option 2`), 填好后写入工单文件夹中的 `receipt.md`.
   - B. 消息汇报: 同样按回执骨架写好回执全文, 用 SendMessage 发给编排会话 (会话名称见工单概况的 "编排会话"), 编排会话收到后写入回执文件.

## 受阻情形

遇到以下情况立即停下, 回复 "执行受阻", 不自行变通:

- 对账不符, 或工单前提不成立.
- 规格有歧义, 或判据之间互相矛盾.
- 需要超出工作范围的改动, 例如改其它模块的公共接口.
- 需要用户操作, 例如提供账号, 密钥或安装软件.
- 按选型守则找不到满足需求的方案.

## 回复版式

回复 "开工对齐", "执行完成" 与 "执行受阻" 之前, 先运行 `node .navigator/bin/runtime/navigator.mjs reply <编号>` 取得骨架, 按骨架填写, 不增删标题与键名. 回复结束时 hook 校验版式, 不合格会被打回一次.

## 选型工单

- 按项目规范 `.claude/rules/engineering.md` 中 "技术选型" 一节的守则逐条执行.
- 回执 "能力核实" 中, 需求的每项关键能力都要附源码证据: 仓库地址, 版本或提交, 文件路径与行号. 只有文档或记忆作依据的说法视为未核实, 验收时判为不通过.
- 只给出结论与理由, 由用户批准; 批准之前不安装依赖, 不写实现代码.

## 写作要求

- 用简体中文, 朴素直白: 不自造简称, 不打比方, 不用没有名词的 "它", "这", "其".
- 路径, 命令与标识符原样写出, 放在行内代码中.
